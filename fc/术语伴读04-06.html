4.1　射频（RF）：为什么是 2.4GHz，以及它带来了什么代价#

这一节回答一个问题：遥控为什么用 2.4GHz 而不是更低的频段？这个选择又要付什么代价？

① 它是怎么出现的#

🟢 确证：本工程用的 PN298 工作在 2400MHz ~ 2483MHz 的通用 ISM 频段 （《PN298 用户手册 V1.0》第 8 页 第 1 节"概述"）。

🟢 确证：同一页写明 PN298 集成发射机、接收机、频率发生器、GFSK 调制解调器， 发射机"支持功率可调（最大可达 10dBm）"，通信兼容 XN297L 数据包。 本工程选的就是 XN297L 增强模式（config_rf.h:179 的 __PN298_MODE = 0x0001）。

🟢 确证：手册第 8 页还写明"只需要 MCU 通过 SPI / I2C 外设接口对芯片少数几个寄存器 配置，即可实现数据的收发通信"。

🟡 通说：ISM（Industrial, Scientific and Medical，工业/科学/医疗）频段指 各国无线电管理机构开放给免许可低功率设备使用的一段频谱；2.4GHz 那一段 （约 2.400~2.4835GHz）在主要经济体都是免许可的，这是 WiFi、蓝牙、Zigbee 和 大量遥控器都挤在这里的直接原因。具体的管理机构名称、功率上限与许可条款各国不同，本文件不逐条引用。

② 它要解决什么问题（没有它会怎样）#

先看老频段这条路为什么走不通了。遥控模型早期用 27MHz / 40MHz / 72MHz 一类的 低频段（🟡 通说：这些频段在不同国家分给模型遥控的用途各不相同，有的需要申请、 有的是"次要用户"）。低频段有两个硬伤，都可以从物理直接算出来：

【硬伤 1：天线尺寸 ∝ 波长】

  偶极天线（dipole）的谐振长度 ≈ 半波长 λ/2；单极（monopole）≈ 四分之一波长 λ/4。
  波长 λ = c / f，c ≈ 3×10^8 m/s。

  🟡 通说：低频段的缩短型天线（加电感做电小天线）辐射效率很低，

     ✅ 这一条是本文件唯一一处靠"可观测事实"支撑的通说：
     公式本身 🟢（物理定义），"效率只有百分之几"的**具体数字**属 🟡，不要当设计依据。

【硬伤 2：低频段的可用带宽窄，容纳不了高刷新率】

  27MHz 频段总宽度往往只有几百 kHz 量级；2.4GHz ISM 有 83.5MHz。
  带宽 ÷ 每包比特数 = 每秒能塞多少包。
  遥控要 50Hz 刷新（本工程遥控器侧 `遥控器/user/main.c:224`
  用 loop50HzFlag 触发发送），一包 176 比特（见 4.5 的计算），
  再乘上 ACK 与重传，低频段会非常局促。
  🟡 这一段是从"带宽/包长/刷新率"三者关系推出来的，具体老频段的分配细则本文件不引用。

2.4GHz 解决了这两件事，但同时引入了两个新代价，这正是本节的标题所指：

示意图
【代价 1：波长只有 12.5cm —— 绕射能力差】

  🟡 通说（电磁波传播）：障碍物尺寸 >> 波长时，波几乎是"直线传播 + 反射"，
     绕射（diffraction，绕过障碍物边缘继续传播）很弱；
     障碍物尺寸 ≲ 波长时，波可以"抹过"它。

  把这条规则代入：

    72MHz  λ = 4.17m  ──►  人的身体（约 0.5m 厚）、树干、矮墙
                            都远小于波长 ⇒ 波能"糊"过去，人站在中间只是衰减一点

    2.4GHz λ = 0.125m ─►  人的身体（约 0.5m 厚）是波长的 4 倍
                            ⇒ 基本当一堵墙处理，站在遥控器和飞机之间就是硬遮挡

  【结论一句话】2.4GHz 换来"天线 3cm"，代价是"人和树都能当墙"。

【代价 2：2.4GHz 上挤满了别的东西】

  同一个 ISM 段里同时住着：WiFi（IEEE 802.11b/g/n）、蓝牙（Bluetooth）、
  Zigbee、无线鼠标键盘、微波炉（🟡 通说：微波炉工作在约 2.45GHz，泄漏会抬底噪）。
  而 2.4GHz 频段总共只有约 83.5MHz 宽，**WiFi 一个 20MHz 信道就吃掉四分之一**。
  ⇒ 干扰不是"可能发生"，而是"默认存在"。这就是 4.2 信道、4.6 ACK/重传、
     以及正文 4.3 那套信道切换机制存在的全部理由。

再补一条与"手册事实"直接相关的代价：

🟢 确证：手册第 11 页 表 2-4 RF 指标里有一条注释 —— "不推荐使用整数倍于 16MHz 的频道，如 2480MHz。因为接收机的灵敏度在这些信道中会降低约 2dB。"

这条注释的含义是：芯片内部有一个 16MHz 的参考时钟（同一页写 fXTAL 晶振频率 - 16 - MHz）， 当射频载波落在参考时钟的整数倍上时，接收机会被自己的参考泄漏干扰，灵敏度掉 2dB。 这是一个"越靠近芯片内部结构就越容易吃亏"的例子 —— 但它只影响选频点，不影响能不能通信。

本工程实际用的频点是不是 16MHz 整数倍？见下节算出来的 2436MHz：2436 ÷ 16 = 152.25， 不是整数倍 ⇒ 不落在这条"不推荐"名单里。🟢（除法可验算）

4.2　信道（Channel）：为什么分格子，以及"36"到底是多少 MHz#

这一节回答一个问题：2.4GHz 是一整段频谱，为什么还要分信道？分完以后代码里的数字怎么换算成频率？

① 它是怎么出现的#

先讲清"信道"这个概念是从哪来的。

示意图

🟢 确证：手册第 34 页 RF_CH 寄存器（地址 05，复位值 0x008E）：

  • RF_CH 7:0：设置 TX 使用频道为 Channel = RF_CH + 2336
  • HIGH_RF 8：RX 高频/低频选择：0 = 高频，通道 +2M；1 = 低频，通道 −2M

② 它要解决什么问题（没有它会怎样）#

没有信道（所有人都在同一个宽频带上发）：任何一台设备开机就会盖掉全场所有设备， 遥控器数量 ≥ 2 就没法用。有了信道但只有一条：同一场地上两台设备还是撞。 所以信道的真正价值是"让"撞"这件事变成可管理的、可绕开的"。

"同频干扰"到底是怎么表现的：

示意图
【图 4.2-2】同频干扰 = 两句话叠在一起，谁都不是"听不清"，而是"听成了别的字"

  飞机在 36 号信道（2436MHz）听着：

     遥控器A ──────┐
                   ├──► 空中的电磁场 = A 的波 + B 的波 叠加
     遥控器B ──────┘                    （线性叠加原理）

  叠加的结果不是"A 的声音小了一点"，而是：
     · 幅度足够大时 → 解调器判决出错 → **CRC 校验失败 → 整包丢弃**
     · 幅度接近、相位合适时 → 前导码被破坏 → **根本同步不上 → 当噪声忽略**

  ⇒ 硬件 CRC（见 4.5）保证了"被干扰的包不会变成错误的数据"，
     代价是它变成了"丢包"。
     **丢包是安全的结果；收到错数据才是危险的结果。** 这是射频设计的第一原则。

4.4　地址与管道（Address / Pipe）：同信道上还有别人怎么办#

这一节回答一个问题：已经选了信道，为什么还要一个 5 字节地址？它和信道分工在哪？

① 它是怎么出现的#

信道解决的是"频率"这一个维度上的冲突。但同一个频点上可以站很多设备。 如果只有信道，那么"同频段的任何一台遥控器发的包，飞机都会去解"，带来两个后果：

  • 解出来的数据可能是别人的 ⇒ 靠 CRC 只能保证"没被干扰"，不能保证"是给我的"；
  • CPU 与射频前端的时间被别人的包占满 ⇒ 自己的包反而丢。

所以需要一个"收件人姓名"。硬件层面把它做成地址匹配（address matching）： 接收机把解调出的地址字段和本地寄存器里的地址逐字节比较，不匹配就在极早期丢弃， 连 FIFO 都不占。

🟢 确证：手册第 8 页写明 PN298 的协议引擎"6 个接收数据通道构成 1：6 的星状网络"， 且最大支持 64 字节数据长度、支持自动应答及自动重传。 🟢 确证：手册第 23 页 表 5-3（增强模式数据包格式）里，地址字段宽度为 3~5 bytes。

所谓 Pipe（管道） 就是这 6 个接收通道：一个接收机可以同时"监听"6 个不同地址， 每个通道有自己的 RX_ADDR_Pn 寄存器、自己的 RX_PW_Pn（载荷宽度）、 自己的 EN_AA 使能位。"管道"这个词的来源是数据流比喻：6 根管子插进同一个 FIFO 里，哪根管子收到就算谁的。

② 它要解决什么问题（没有它会怎样）#

② 它要解决什么问题（没有它会怎样）#

见上面的逐字段反推表。把整节压缩成一句：没有"包"这个结构，空中就只有一串 连续的电磁波，"哪里是开头""这串是不是给我的""有没有被打坏"三个问题都答不出来。

再加一条 2.4GHz 特有的理由 —— 扰码（scrambling）：

🟢 确证：手册第 9 页 主要特性列明 PN298 "带自动扰码和 CRC 校验功能"。 🟢 确证：手册第 39 页 SCR_EN 位（在某个射频校准寄存器里）："扰码功能是否使能：1：使能 0：关闭"。 🟢 确证（本工程）：bsp_pn298.c:666-669 的注释说明：Nordic 协议族把扰码关掉， XN297L / BLE 把扰码打开；本工程是 XN297L 增强模式 ⇒ 扰码开。

🟡 推理（为什么需要扰码）：接收机靠"比特跳变"恢复时钟。如果载荷里出现 一长串 0 或一长串 1（比如某个通道值刚好是 0x0000，或按键字节全 0）， 接收端的时钟在长时间没有跳变后会漂移，恢复出的位就可能错位。 扰码就是"把数据流和一个伪随机序列异或"，让电路上看到的比特流总是"看起来随机"。 代价是收发两端必须用同一个扰码种子（本工程靠"同一模式"保证，见 bsp_pn298.c:669-670）。

高字节在前（Big-Endian，大端）。这么做的原因是跨平台/跨编译器一致性 🟡：

4.6　ACK 与自动重传：发送方怎么知道对方收到了#

这一节回答一个问题：单向广播和"可靠送达"差在哪里？硬件帮了多少忙？

① 它是怎么出现的#

两个角色先正名（手册第 7 页缩略语表里有）：

  • PTX（Primary Transmitter，主发端）：主动发起通信的一方 —— 本工程里遥控器。
  • PRX（Primary Receiver，主收端）：接收数据并响应的一方 —— 本工程里飞控。

🟢 确证：手册第 17 页 4.2 节（增强模式）原文：

"PTX 发出数据后等待应答信号，PRX 接收到有效数据后回应答信号。 PTX 规定时间内未收到应答信号，自动重新发送数据。 自动重传和自动应答功能为 PN298 芯片自带，无需 MCU 参与。 PTX 在发送数据后自动转到接收模式等待应答信号。如果没有在规定时间内收到正确的应答信号， PTX 将重发相同的数据包，直到收到应答信号，或传输次数超过 ARC 的值（SETUP_RETR 寄存器） 产生 MAX_RT 中断。PTX 收到应答信号，即认为数据已经发送成功（PRX 收到有效数据）， 清除 TX FIFO 中的数据并产生 TX_DS 中断。"

这段话里最有价值的一句是"无需 MCU 参与" —— 它说明整个"发→等→超时→重发"的状态机跑在芯片内部，MCU 只管最后看一眼中断标志。

🟢 确证：手册第 33 页 SETUP_RETR 寄存器（地址 04，复位默认值 0x03）：

🟢 确证：手册第 17 页 4.3 节（增强发送模式）给出了收发切换的标准动作序列：

1. SPI_CE 置 0，CONFIG 寄存器的 PRIM_RX 位先置 0。 2. 当发送数据时，发送地址（TX_ADDR）和有效数据（TX_PLD）通过 SPI 接口按字节写入…… 3. SPI_CE 从 0 置 1，启动发射（CE 至少持续置 1 在 30us 以上，该操作生效）。

⇒ 这两条把 CE 的物理含义讲透了：

  • CE 是"开始干活"的开关，不是"芯片上电"的开关（芯片一直有电、寄存器一直可读写）；
  • CE 保持高 ≥30µs 这个动作才生效 —— 因为芯片内部需要时间让 PLL 起振/锁定、

让 PA（Power Amplifier，功率放大器）稳定。这不是"软件随便延时一下"，是手册给的时序约束。

公式本身只有一行，真正的难点在"代进去的那个 LSI 频率到底有多准"：

示意图
【图 5.3-1】超时公式的推导（为什么是"预分频 × 重载 ÷ 频率"）

  ① LSI 是一个 32768Hz 的方波（周期 1/32768 s ≈ 30.5µs）

  ② 预分频器把它除以 32：
        f_counter = 32768 ÷ 32 = 1024 Hz
        ⇒ 计数器每滴答一次 = 1/1024 s ≈ 0.977 ms   ★记住这个数

  ③ 计数器从重载值开始往下数，数到 0 溢出：
        需要的滴答次数 = 512 次
        （注意：12 位计数器写 512 是合法的；手册没写"写 N 就是 N 次"，
          这里有 ±1 次的边界不确定性，相对 512 可忽略）

  ④ 总时间 = 512 × (1/1024) s = 0.5 s   ✅

  写成一条通式：
        T_dog = 预分频 × 重载 ÷ f_LSI
              = 32 × 512 ÷ 32768
              = 16384 ÷ 32768
              = 0.5 s（精确等于 0.5，因为 16384 = 32768/2）

关键在这一步：f_LSI 不是 32768，而是 32768 ± 一大堆。

  ⇒ 所以"对码期间既不喂狗、狗又已经启动 ⇒ 超过超时就不断复位、
     表现为'对码对不上、灯一直闪'"这个担心，**在本工程里不成立**。✅

  ⚠️ 正文 6.3 的"读代码时的检查点"警告的是这种情形：
     "对码循环里如果既没有喂狗、看门狗又已经启动……"
     —— 这是一个**通用的、正确的**排查思路，但用在本工程上会得出错误结论：
     本工程的顺序恰好是安全的（狗在最后启）。
     真正需要这个警告的是"先起狗、再对码"的那种写法。

第 6 章　对码 / 配对（Pairing）#

6.1　为什么需要"对码"#

这一节回答一个问题：多台设备共处一室，怎么做到"只跟我的遥控器说话"？

① 它是怎么出现的#

先讲清"不对码"这条路会怎样。三种"硬编码"的做法，各有各的崩法：

示意图
【图 6.1-1】不对码的三种做法，以及它们各自怎么崩

  ── 做法 A：所有设备用同一个出厂地址 ─────────────────────────────
     出厂：地址 = 0xCC 0xCC 0xCC 0xCC 0xCC（就是本工程的"缺省地址"）

     现场：飞机A、飞机B、遥控器C
       遥控器C ──► 飞机A 收到、飞机B 也收到 ⇒ **两台一起响应**
       ⇒ 串控。谁先起飞谁倒霉。
     ❗本工程对码之前的初始状态**就是这个状态**（config_rf.h:132-136 的 0xCC×5）。

  ── 做法 B：出厂写死一个"唯一的"地址 ─────────────────────────────
     出厂的每台设备地址不同 ⇒ 解决了串控
     但 ⇒ **遥控器和飞机怎么知道对方是谁？**
         包装上印序列号，用户手动输入 5 字节十六进制？（没人会做）
         ⇒ 退化为"拨码开关"（见 6.1 ④ 的对照表）

  ── 做法 C：靠"设备 ID"过滤，不做地址协商 ───────────────────────
     所有设备地址都一样，靠软件层的 device_id 过滤
     ⇒ 射频前端**必须先把所有包都收下来**（包括别人的），
        再靠 CPU 逐个比对 device_id 丢掉
     ⇒ 后果 1：CPU 和 FIFO 被别人的包占满，**自己的包反而丢**
        后果 2：`device_id` 只有 8 位（本工程 deal_pack.c:103 是 uint8_t），
                同场地 256 台设备就可能撞
     ⇒ 这就是为什么**地址协商（硬件过滤）比 ID 过滤（软件过滤）更根本**。

⇒ "对码"要做的，就是把"出厂写死的值"换成"现场协商的值"。

"同频干扰"和"串控"要分清楚（这两个词经常被混用）：

同频干扰串控
现象我的包被别人的信号压掉 → 丢包我的飞机执行了别人的指令
原因空中能量叠加地址/ID 没有区分开
检出方式硬件 CRC 校验失败 → 丢包 → ACK 超时无检出！飞机认为这是合法指令
后果抖、延迟、失联保护事故
解决换信道、跳频、ACK 重传、降速率增功率对码（地址协商） + device_id 二次过滤

⇒ "同频干扰只是变慢，串控才是危险"。 这条区分是本章存在的理由。

方案机制优势代价什么时候用
拨码开关 / 拨轮用户手工把收发双方拨到同一组开关位（老式 27/40MHz 遥控常见）不需要任何协议；不怕"对码失败"；一眼能看出设置位数少 ⇒ 组合少 ⇒ 人多就撞；用户要记住设置；不能自动老式设备、极低成本
按键进入配对模式（本工程）按住对码键 → 遥控器广播自己的地址 → 飞机抄下直观、可控、用户知道自己在干什么要用户操作；要防误触（遥控器/user/main.c:146 有 while(is_pair_key()){} 等松手）✅ 本工程
上电自动配对每次上电都重新协商一次用户零操作每次开机有窗口期可被"抢对"；飞行中若重连会中断玩具级产品
出厂固定地址 + 唯一序列号出厂烧唯一地址，标签上印配对关系零操作、零误配售后换件必须整对换；产线要管理配对表消费电子一次性产品
绑定表（多机）一个遥控器里存多台飞机的地址，可切换一控多机；换机不用重对遥控器 Flash 要放表；UI 要能选机一拖多场景
近场配对（NFC / 二维码 / 声波）用另一条信道交换密钥/地址可携带密钥，能升级为"认证配对"加硬件（NFC 天线 / 麦克风）需要真正安全性的产品

② 它要解决什么问题（没有它会怎样）#

对码流程本身要解决的是"把协商结果落到非易失存储"这件事。

示意图
【图 6.2-2】为什么必须写 Flash —— "对码"和"记住对码"是两件事

  只协商、不落盘：
     每次上电都要重新对码 ⇒ 用户每次飞之前按一次对码键
     ⇒ 现场体验差；更糟的是**忘记对码就起飞** ⇒ 用的是缺省地址 ⇒ 串控风险

  协商 + 落盘：
     对码一次，之后上电直接读 Flash 恢复 ⇒ 拿起就飞

  落盘的代价（Flash 的物理特性）：
     · Flash 只能把 1 写成 0，**不能把 0 写回 1** ⇒ 改一个字节也要整页擦除

     · 擦除会**挂起 CPU 取指**几十毫秒 ⇒ 绝对不能放在飞行中调用
     · 擦写次数有限（典型 10k~100k 次）⇒ 不能高频写

  ⇒ 所以本工程的做法是：
       把"对码结果 + 传感器零偏 + 设备 ID"打包成一个结构体，**一次整页写入**
       （user/flash.h:109-117 的 Pair_Code_Config）—— 一次擦写解决所有持久化需求。
     ❗`deal_pack.c:296` 的注释明确写了这条纪律：
       "这一步会挂起 CPU 取指几十毫秒，所以绝不能放在飞行过程中调用"

```text ① 遥控器发送侧（deal_data.c:52-62） [2..6] ← paircode[0..4] （循环 j=2..7，j-2=0..5 —— 注意这里有个细节） 等等，循环是 for(uint8_t j=2; j<8; j++)，即 j = 2,3,4,5,6,7 共 6 次 取的是 ((uint8_t)(&joystick_pair_str.paircode) + (j-2)) ⇒ j=2 → paircode[0]，j=3 → paircode[1]，...，j=6 → paircode[4]， j=7 → paircode 后面的第 6 个字节 = rf_ch（因为结构体里 rf_ch 紧跟 paircode） ⇒ 所以 [2..7] = {paircode[0..4], rf_ch} ✅ 与飞控的 6 字节读法完全对应 [8] = device_id ← 遥控器的 device_id 在这里 [9..11] = 0

⚠️ 上面这段推理修正了我最初的怀疑。 事实证明 deal_pack.c:292 的 rx_buff[8] 是对的 —— 因为遥控器在 [2..7] 里塞的是"paircode + rf_ch"共 6 字节， device_id 顺延到了 [8]。这两侧是刻意对齐的。

但这条"对"，靠的是三个地方同时正确： ① 遥控器结构体里 rf_ch 紧跟 paircode； ② 遥控器发送循环写满 6 字节（j<8）； ③ 飞控接收循环读满 6 字节（i<6）。 任何一处改动都会静默错位 —— 这就是"隐式布局约定"的风险。 本文件保留这段推理过程，因为它正好示范了本文件最想传达的态度： 不要凭"看起来不对"就下结论，要顺着两侧的字节偏移一格一格对。

另一条实实在在的隐患（这条是确凿的）： 🟢 确证：deal_pack.c:281 的 for(i=0;i<6;i++) 与 遥控器 deal_data.c:55 的 for(j=2;j<8;j++) 都硬编码了 6。 而"6"这个数字的物理含义是"5 字节地址 + 1 字节信道"。 paircode 的数组长度在 flash.h:112 是显式的 [5]， 如果哪天把地址宽度改成 3 或 4（PN298 支持 3~5 字节，见 4.4）， 这两个循环的硬编码 6 就必须一起改，否则会静默抄错。 建议的写法是 sizeof(pair_data.paircode) + 1，但本文件只建议，不修改代码。

     ⇒ 也就是**每 3~5ms 听一次**，足够接住遥控器 20ms 一包的广播 ✅

                   对码态                                飞行态

  ── 方案 B：状态机（推荐给复杂系统）────────────────────────────
     一个 while(1) 里跑所有状态，用状态变量切换

       main() {
           while(1) {
               switch(state) {
                   case ST_PAIRING: do_pairing();  if(pair_over_flag) state = ST_FLASH; break;
                   case ST_FLASH:   flash_read(); get_now_addr(); change_addr(); state = ST_FLIGHT; break;
                   case ST_FLIGHT:  decode_pack(); flight_ctrl(); feed_dog(); break;

       }

     优势：**看门狗可以从头到尾一直有效**；状态切换有统一出口；便于加状态
     代价：所有状态共享一个栈深度（要算最坏栈占用）；代码分支变多

  ── 方案 C：后台任务 / RTOS ───────────────────────────────────
     对码作为一个低优先级任务，飞行控制任务是高优先级但被"未对码"标志挡住

     优势：**看门狗可以监控所有任务**；对码期间 UI、日志、蓝牙调参都还能跑
     代价：要引入 RTOS；要处理优先级反转、栈占用、tick 精度

     ⚠️ 对本芯片（PY32F030x8：Cortex-M0+、**8KB SRAM**、无 FPU）
        跑 RTOS 是"能不能塞得下"的问题，而不是"想不想用"的问题。
        🟡 8KB SRAM 跑一个精简 RTOS 是可行的（FreeRTOS 最小配置通常几 KB），
           但会显著压缩姿态解算与控制算法的余量。**本文件不建议也不反对，只指出这个约束。**

6.4　跳频与对码的关系#

这一节回答一个问题：对码协商出来的信道，之后怎么用？会不会跳？

① 它是怎么出现的#

先分清两个容易混的概念：

示意图
【图 6.4-1】"对码时选信道" 与 "飞行时跳频" 是两件不同的事

  ── 对码时选信道（本工程有）────────────────────────────────────
     目的：**让收发双方站到同一个格子里**
     做法：遥控器随机生成 rf_ch（0~79）→ 通过 0xDB 包告诉飞机
     时机：只在配对那一刻发生一次

  ── 飞行时跳频（本工程**没有** AFH）────────────────────────────
     目的：**在已经被干扰之后还能继续通信**
     做法：双方按同一个伪随机序列，每隔几毫秒换一个信道；
           收不到 ACK 就把那个信道踢出跳频表（这就是 AFH 的"自适应"）
     时机：飞行全程持续进行
     🟢 手册第 17 页提到增强模式的一个特征就是"**更易开发跳频算法**" ——
        说明芯片层面是**支持**这么做的（重传不用 MCU 重写数据，MCU 有余力换频）。

附录 C　一句话总结#

第 4 章：2.4GHz 用"免许可 + 天线 3cm"换来了"易遮挡 + 同频设备多"。 剩下所有术语都是在给这个选择打补丁：信道解决"在哪说"， 地址解决"对谁说"，包结构解决"怎么说"，ACK/重传解决"说完怎么知道对方听见了"， CE 解决"什么时候轮到我说话"，软件 SPI 解决"我怎么跟芯片说"。 出问题的现象永远是同一句"收不到"，所以排查必须从物理层往应用层走。

第 5 章：看门狗是一切"程序还活着"的证明机制， 它的价值全部取决于两件事：时钟源（决定它能不能救时钟故障）和 喂狗点（决定它是不是形同虚设）。 IWDG 用 LSI，所以救得了"主时钟都乱了"；代价是 LSI 的 ±20% 全温区偏差 ⇒ 余量必须按最坏值算（本工程 400ms ÷ 101ms ≈ 4 倍，不是 5 倍）。 喂狗的位置只有一个判据："只有主流程正常推进才可能执行到"。

第 6 章：对码在协议上只是"交换信道 + 地址"，但在结构上它带来一个 阻塞状态（while(1)），而这个状态之所以安全，是因为 本工程把"起狗"排在了它之后。 真正隐蔽的风险不在流程里，而在存储布局：两侧靠"结构体前 6 字节布局相同" 这个隐式约定交换数据，没有版本号、没有 CRC， 任何一边调整字段顺序都会静默错位。 而"跳频"这件事，本工程的现状是：对码时在两个信道间交替（第二个值是 0，不是设计意图）， 飞行时固定在协商信道 —— 既不是设计文档说的"没有扫描"，也不是正文 4.3 说的"确实在跳频"。
