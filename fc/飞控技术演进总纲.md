## 1. 先看一张"层次图"：飞控由哪几层组成

这一节回答一个问题：**一块飞控板从上到下由哪些层拼起来，每层坏了会怎样？**

### 1.1 十一层纵向图

**从下往上读**：越下面越接近物理，越上面越接近飞行意图。
**任何一层坏了，它上面的所有层全部失效。**

```text
 ⑪ 遥控链路与失效保护  "对方还在吗？不在我该怎么办？"
    坏了 → 飞机带着最后的舵量飞走
    本工程：main.c:462 失联判据 / deal_pack.c:257 刷新时间戳
 ⑩ 执行输出            "把数字变成桨叶转速"
    坏了 → 算得再对也不动，或满油门失控
    本工程：bsp_pwm.c 的 motor_pwm_output()（TIM3 四通道 16kHz）
 ⑨ 控制律（串级 PID）  "姿态偏了，我该怎么修？"
    坏了 → 修过头（振荡）或修不动（漂走）
    本工程：pid.c 的 pid()（外环角度 / 内环角速度）
 ⑧ 姿态解算与滤波      "我现在到底是斜的还是平的？"
    坏了 → 飞的姿态和以为的姿态不一致
    本工程：imu.c 的 imuMahonyAHRSupdate() / filter.c 的 PT1、Biquad
 ⑦ 传感器与射频芯片    "把物理量变成数字、把电磁波变成字节"
    坏了 → 读数全 0/全 0xFF，或收不到包
    本工程：ICM42688（SPI1 1.5MHz）、BMP390、PN298
 ⑥ 驱动                "怎么跟这颗具体型号的芯片说话"
    坏了 → 能通但不工作（配错量程→削顶；配错 ODR→时序全错）
    本工程：icm426/icm42688.c、user/bmp3.c、bsp_pn298.c
 ⑤ BSP（板级支持包）   "这块板子引脚接哪儿、先初始化谁"
    坏了 → 对着空气说话（引脚没配）；本工程：bsp.c 的 bsp_init()
 ④ 外设（定时器/SPI/UART/ADC）  "让硬件自己重复干活"
    坏了 → 时序全错（波特率/频率算错）
    本工程：TIM16/TIM17/TIM3/TIM1、SPI1、USART、ADC1、IWDG
 ③ MCU 内核（Cortex-M0+）  "执行指令、响应中断"
    坏了 → HardFault → py32f0xx_it.c:105 死循环
    本工程：startup/startup_py32f030xx.s 的向量表 + Reset_Handler
 ② 时钟                "多久算一步？"
    坏了 → 所有时间相关的量等比缩放 → 全错
    本工程：main.c:120 SystemClock_Config()（HSI24M×2=48MHz）
 ① 电源                "有没有电？电压稳不稳？"
    坏了 → 欠压复位/跑飞；过压烧芯片；纹波污染 ADC 与射频
    本工程：板上 LDO CL9193A28L3M + 肖特基 1N5819WS（硬件）；
            代码侧观测点 adc.c 的 get_voltage()
```

> **一条读图纪律**：**自下而上排查，自上而下设计**。
> 现场"飞机不动"时，从 ① 往上查（有没有电 → 时钟对不对 → 中断进没进 →
> 传感器读得到吗 → 控制量算出来了吗 → PWM 有没有输出 → 遥控收到了吗），
> **而不是一上来就怀疑 PID 参数**。这条纪律在 6.2 节展开。

### 1.3 初始化顺序：为什么不能随便换

```text
 main()  main.c:214
  ├① HAL_Init()                     main.c:220  装 SysTick（此时按 8MHz 算周期）
  ├② SystemClock_Config()           main.c:223  HSI 24MHz → PLL ×2 → 48MHz
  │     ⚠ HAL_RCC_ClockConfig() 内部会**重装 SysTick**（py32f0xx_hal_rcc.c:933）
  │       → 1ms 时基到这里才真正准
  ├③ bsp_init()                     main.c:227 → bsp.c:92
  │     bsp_rfspi_init() → bsp_pn298_init() → bsp_uart_init() → spi_init()
  ├④ Led_Init / Timer17_UpdateIT_Init / TIM1 PWM / TIM3 PWM / ADC
  │     main.c:229 / :235 / :239 / :244 / :248
  ├⑤ accgyro_init() → imu_init() → BMP390_init()      main.c:255 / :258 / :261
  ├⑥ 对码 while(1)                  main.c:295  收到 0xDB → 存地址/信道/零偏 → Flash → break
  │     ⚠ 这段**阻塞**，此时看门狗还没启动（故意的，见 2.10）
  ├⑦ 读回 Flash 参数、切射频地址与信道                  main.c:332-343
  ├⑧ tim16_init()                   main.c:344  （1µs 时间戳从这里才有）
  ├⑨ WDG_init()                     main.c:347  （IWDG 启动后无法关闭）
  └⑩ while(1) 主循环                 main.c:371
```

| 顺序错误 | 现象 | 为什么 |
| --- | --- | --- |
| `spi_init()` 放到 `accgyro_init()` 之后 | IMU 读不到数据，姿态角永远是 0 | 外设没初始化，等于对着空气说话 |
| `bsp_rfspi_init()` 放到 `bsp_pn298_init()` 之后 | 射频寄存器读回全 0xFF，永远收不到对码包 | 软件模拟 SPI 用普通 GPIO，没配模式就推不动电平 |
| `SystemClock_Config()` 放到 `bsp_init()` 之后 | 波特率/PWM/心跳全按 8MHz 算（约 6 倍偏差） | 所有分频系数都相对 PCLK1 |
| `WDG_init()` 放到对码循环之前 | 约 0.5s 复位一次，"灯一直闪、就是配不上" | IWDG 停不掉，而对码循环里没喂狗 |
| `WDG_init()` 放到主循环之后 | 看门狗根本没启动 → **完全没有兜底** | 少调一次就是少一层保护 |
| `tim16_init()` 放到 `flight_ctrl()` 之后 | `deltaT` 算成 0 或巨大值 → PID 不收敛 | 时间戳外设没启动 |

### 1.4 "坏了会怎样"速查表

| 层 | 一句话职责 | 典型失效现象 |
| --- | --- | --- |
| ① 电源 | 供电 | 反复重启、射频距离骤短、ADC 读数乱跳 |
| ② 时钟 | 定节拍 | 串口乱码但换波特率就好；PWM 频率不对；控制周期不对 |
| ③ 内核 | 执行指令 | HardFault → 死循环 → 看门狗复位 → 飞机周期性重启 |
| ④ 外设 | 让硬件重复干活 | 定时器不中断、SPI 读不出、ADC 值不变 |
| ⑤ BSP | 引脚与顺序 | 寄存器读回全 0 或全 0xFF |
| ⑥ 驱动 | 型号专有配置 | 数据削顶、ODR 不匹配、校准失败 |
| ⑦ 传感器/射频 | 感知与通信 | 姿态不响应、遥控无反应 |
| ⑧ 姿态解算与滤波 | 原始值→姿态角 | 悬停时飞机慢慢歪；对振动敏感 |
| ⑨ 控制律 | 误差→修正量 | 电机嗡嗡响、机身发抖（D 大）或低频摆（P 小） |
| ⑩ 执行输出 | 数字→推力 | 解锁后电机无反应，或突然狂转 |
| ⑪ 遥控与失效保护 | 断链后的安全动作 | 遥控关机，飞机不降落，一直飞走 |

## 2. 一架"能飞的飞控"依次需要解决哪些问题

这一节回答一个问题：**如果从零开始做，问题会以什么顺序找上门？**

11 条按**依赖顺序**排，不按代码目录排。

### 2.1 怎么让芯片跑起来（时钟、启动、复位）

**没有这一步会怎样**：芯片根本不动；或者跑在一个你以为不是的频率上。

```text
 上电/复位
   │
   ├① 硬件从向量表取值（参考手册第 119 页 12.1.3）：
   │    0x00 → 栈顶值；0x04 → 复位向量 → Reset_Handler
   ├② Reset_Handler → SystemInit()   system_py32f0xx.c:134
   │    · HSI 设成出厂 8MHz 档（ICSCR 寄存器）· SCB->VTOR = FLASH_BASE
   │    ★ 这里【没有】配 PLL
   ├③ 拷贝 .data、清零 .bss（C 运行时启动）
   └④ main() → HAL_Init() → SystemClock_Config() → 48MHz
```

| 事实 | 依据 |
| --- | --- |
| 复位后默认系统时钟 = **HSI 8MHz** | 数据手册第 7 页 3.4 节原文 |
| `SystemInit()` 只设 HSI 档位与向量表，**不配 PLL** | `system_py32f0xx.c:134-145` |
| PLL 只支持对 HSI 或 HSE **2 倍频** | 数据手册第 1 页产品特性 |
| HAL 对 PLL 输入有 **16~24MHz** 硬约束 | `py32f0xx_hal_rcc.c` 的 `PLLSOURCE_FREQ_MIN/MAX` |
| 48MHz 下 Flash 要插 **1 个等待周期** | `main.c:170` 的 `FLASH_LATENCY_1` |

🟢 **"为什么 PLL 只做 2 倍频"**：石英晶振的基频不能随意做高（高频晶振难做、贵），
而 PLL 能用低频晶振合成高频。这里 2 倍就够，因为 HSI 本身能校准到 24MHz。

| 失效 | 现象 |
| --- | --- |
| 不配时钟，就用复位后的 8MHz | 波特率差 6 倍 → **全乱码**；PWM 差 6 倍 → 电调不认；1ms 中断变 6ms |
| `FLASH_LATENCY` 配 0 | 取指跟不上 → **偶尔跑飞 / HardFault**，现象随机、极难查 |
| 忘了使能外设时钟（如 `__HAL_RCC_TIM17_CLK_ENABLE()`） | 寄存器读写全是空操作 → "代码写对了就是没反应" |
| `Error_Handler()` 里不死循环而继续跑 | 带着错时钟起飞 → 必炸（所以 `main.c:499` 选择死循环等看门狗） |

### 2.2 怎么知道"现在是什么时候"（时基、SysTick、定时器）

**没有这一步会怎样**：`deltaT` 恒为 0 → 积分不累积、微分除以 0 → 控制完全失效；
所有超时判断永远不成立或立即成立。

```text
 ┌─ 时间线 A：SysTick（内核自带）──┐ ┌─ 时间线 B：TIM17（片上外设）──┐
 │ 谁配的：HAL_Init() 里           │ │ 谁配的：Timer17_UpdateIT_Init()│
 │ 时钟源：HCLK（48MHz）           │ │ 时钟源：PCLK1（48MHz）         │
 │ 周期  ：1ms                     │ │ 周期  ：/480/100 = 1ms         │
 │ 中断  ：SysTick_Handler()       │ │ 中断  ：TIM17_IRQHandler()     │
 │        py32f0xx_it.c:141        │ │        py32f0xx_it.c:166       │
 │ 干什么：HAL_IncTick() → uwTick++ │ │ 干什么：_cnt10ms/_cnt4ms/... ++ │
 │ 谁在用：HAL_GetTick/HAL_Delay    │ │ 谁在用：main.c 主循环调度       │
 │        失联 5s 判据             │ │        altitude.c 节奏、flip.c  │
 └── 用途：**绝对时间 / 超时** ─────┘ └── 用途：**任务节拍 / 调度** ────┘
 ┌─ 时间线 C：TIM16（微秒时间戳）──┐
 │ /48 → 1MHz，1 步 = 1µs          │
 │ 周期 0xFFFF（约 65.5ms 回绕）    │
 │ **不开中断**                     │
 │ 谁在用：micros16() → deltaT      │
 │   fc.c:79、imu.c:404、altitude.c:218 │
 └────────────────────────────────┘
```

**为什么不合并成一条**（🟢 可从代码推证）：都用 SysTick → `HAL_Delay()` 是阻塞的，
**一次阻塞会把控制节拍一起拖偏**；都用 TIM17 → HAL 库超时逻辑全依赖 `HAL_GetTick()`，改掉要动整个 HAL；
都用 TIM16 → 65.5ms 就回绕，做不了"5 秒失联"这种长超时。
所以本工程**故意分成三条**（`py32f0xx_it.c:158-161` 写了这个分工）。

| 失效 | 现象 |
| --- | --- |
| TIM16 误写成 `HAL_TIM_Base_Start_IT()` | 每 65.5ms 中断一次，白吃 CPU，严重时打乱 1ms 节拍 |
| `micros16()` 两次调用间隔 > 65.5ms | 计数器已绕圈，`(uint16_t)(now-last)` **少算 65536µs** → `deltaT` 突变 |
| 用 `int32_t` 直接相减而不转 `uint16_t` | 回绕瞬间得到负数 → 积分项反向猛冲 |
| 用 `if (now > last + 1000)` 代替 `now - last > 1000` | 32 位 `uwTick` 约 **49.7 天**回绕的瞬间判据失效 |
| LSI 拿来做串口波特率 | LSI 全温区偏差 **±20%**（数据手册第 44 页表 6-16）→ 完全不可用 |

> 🟢 **设计品味**：选时钟频率优先选**能被整除**的值 —— 48MHz 之于 1ms 很舒服，47.5MHz 不是。
> 本工程 48MHz 能被 48/480/4800/32 整除，所以能凑出整数微秒/毫秒（`main.c:111-112`）。

### 2.3 怎么读到传感器（总线、时序、量程、校准）

**没有这一步会怎样**：读数全 0 或全 0xFF → 姿态角永远是 0，
飞控以为飞机一直水平，于是不给任何修正。

```text
 ⑦ 传感器芯片（ICM42688）：量程、ODR、电源模式、FIFO
     ↑
 ⑥ 驱动（icm426/icm42688.c + InvenSense 官方驱动）：型号专有的寄存器序列
     ★ 官方驱动是跨平台的，它要求你提供 read_reg/write_reg 回调
       —— bsp.c:241 的 SetupMCUHardware()（函数指针 = 运行时多态）
     ↑
 ⑤ BSP + 外设（spi.c 的 SPI1）：模式 0（CPOL=0,CPHA=0）、MSB 先出、/32 → 1.5MHz
     ↑
 ④ 引脚（py32f0xx_hal_msp.c 的 HAL_SPI_MspInit）：使能 SPI1 时钟、引脚复用推挽
```

| 项目 | 值 | 出处 |  | 项目 | 值 | 出处 |
| --- | --- | --- | --- | --- | --- | --- |
| 加速度计量程 | **±8g** | `accgyro.c:64` | | 1g 对应原始值 | **4096** | `accgyro.c:35` |
| 陀螺仪量程 | **±2000dps** | `accgyro.c:65` | | 陀螺换算系数 | `0.03051756×2` | `flip.c:81` |
| 两轴 ODR | **200Hz** | `accgyro.c:65-66` | | 安装方向校正 | **CW90_DEG** | `accgyro.c:98-99` |

🟢 **"选量程"本身是一次取舍**：±8g 时分辨率 ≈ 8g/32768 ≈ 0.00024 g/LSB；
改 ±16g → 分辨率差一倍，但剧烈机动不削顶；改 ±2g → 分辨率更好，但稍大的振动就饱和，
姿态解算的输入变成方波（滤波器还以为是真的）。

🟢 **校准的物理前提是"静止且水平"**：陀螺仪静止时输出不为 0，这个非零值叫**零偏**，
随温度和时间缓慢变化，必须现场测出来再减掉（`accgyro.c:121`）。
代码用"陀螺仪输出抖动是否足够小"判断静止（`GYRO_CALI_DIFF_LIMIT = 40`）。
**校准时飞机在动 → 把"运动"当成零偏减掉了 → 一解锁就往一个方向偏。**

| 失效 | 现象 |
| --- | --- |
| SPI 分频配太小（速率过高），或模式（CPOL/CPHA）配错 | 读回数据错位 / 全 0xFF；或数据整体移位，"像数据但完全不对" |
| 量程配错但换算系数没跟着改 | 实际倾斜 30°，代码认为 15° |
| 没有零偏校准 | 陀螺积分持续漂移（见 2.5） |
| 忘了做安装方向校正 | 横滚与俯仰**装反**：想往前倾实际往右滚 → 一起飞就翻 |

### 2.4 怎么把噪声变成可用信号（滤波）

**没有这一步会怎样**，两条路径都可推证：

```text
 路径 A：噪声 → 微分项（D）被放大
   D 项本质是求变化率，求导就是把高频放大
   → PID 输出混进高频抖动 → 电机嗡嗡响、发热；机身高频发抖

 路径 B：噪声 → 陀螺积分 → 姿态角抖动
   振动频率远高于姿态解算带宽，被积分成"假的角度变化"
   → 飞控以为自己在晃，于是猛修 → 修出来的动作又产生新振动（正反馈）
```

| 位置 | 滤波器 | 参数 | 出处 |
| --- | --- | --- | --- |
| 陀螺仪 | **PT1 一阶低通** | 240Hz，时间常数 1.25ms | `accgyro.c:72`、`:127` |
| 加速度计 | **双二阶低通（Biquad）** | 30Hz，`sampleDeltaUs=1250`，Q=1/√2 | `accgyro.c:71`、`:126` |
| 姿态解算前 | **滑动平均** | `accSmooth = (accSmooth*7 + accData)/8` | `imu.c:426` |
| 气压计 | **中值 5 点 + 滑动平均** | `altitude.c:19`/`:88-90`、`:18`/`:123-139` | 见左列 |
| 高度 / 速度 | 低通 | 高度 α=0.1；速度低通 3/4；死区 100mm/s | `altitude.c:169`、`:174`、`:180` |
| PID 的 D 项 | 3 点滑动和 | —— | `pid.c:335-338` |
| 高度融合 | **互补滤波** | `accAlt*0.985 + BaroAlt*0.015` | `altitude.c:259` |

> ⚠ **"本工程用了陷波器"是不成立的**：`imu/filter.c:160-169` 有 `FILTER_NOTCH` 分支，
> 但**全工程没有调用者**；唯一的 biquad 初始化是 `accgyro.c:71` 的低通。
> 这是"实现了但没用"的一个例子（术语手册 11.5 节 C 组已记录）。🟢

🟢 **截止频率是"两头都会出事"的参数**：选高（400Hz）→ 响应快、手感跟手，但振动滤不掉，
D 项放大噪声；选低（80Hz）→ 干净、电机凉，但相位滞后大 → 飞机发飘、修正不及时，
严重时振荡发散。**没有标准答案，必须按机架实测。**

🟢 **一个必须记住的前提**：滤波器的系数是**按采样率算的**。
本工程 ODR 配 200Hz，而两个滤波器按 1250µs（=800Hz）设计（`accgyro.c:65-66` vs `:71-72`）
→ 同一份采样被重复滤波，**等效截止频率偏离标称的 30Hz / 240Hz**
（术语手册 11.5 节 B 组第 1 条）。改了 ODR 或调用周期，**必须回来复核滤波参数**。

🟡 **为什么加速度计用 Biquad 而陀螺用 PT1**：加速度计噪声更大、对振动更敏感，
需要更陡的衰减（Biquad 是 −40dB/十倍频，PT1 只有 −20dB）；
而陀螺仪是内环反馈信号，**相位滞后直接吃掉稳定裕度**，所以用滞后更小的 PT1。

| 失效 | 现象 |
| --- | --- |
| 完全不滤波 | 电机高频啸叫 + 机身发麻；D 项在正负之间狂跳 |
| 截止频率设太低 | 飞机"迟钝"、修正滞后；大幅机动后回正很慢，像泡在水里 |
| 只滤姿态角、不滤陀螺原始值 | 内环（角速度环）仍然吃噪声 → 抖动依旧 |

### 2.5 怎么由角速度得到姿态（积分漂移 → 互补 / 卡尔曼）

```text
 【只用陀螺仪：短期准、长期漂】
   angle(t) = ∫角速度 dt，零偏 b 也被一起积分 → angle(t) = 真实角度 + b·t
   b 哪怕只有 0.1°/s：1 分钟 = 6° 误差，10 分钟 = 60° 误差
   现象：刚起飞还行，飞一会儿开始自己往一边歪，而且【越修越歪】
        —— 因为飞控以为自己在歪，其实是它算错了

 【只用加速度计：长期准、短期抖】
   静止时能测出重力方向 → 绝对倾角，不会漂
   但它同时也测到"运动加速度"和"振动"
   现象：一加速飞控就以为在倾斜 → 猛修 → 抖

 【融合：让两者互相纠正】
   陀螺：短期准 ──┐
                  ├─► 用加速度计算出的重力方向去"慢慢纠正"陀螺的积分
   加速度计：长期准 ┘    （这就是 Mahony 互补滤波的核心思想）
```

| 环节 | 本工程实现 | 出处 |
| --- | --- | --- |
| 算法 | **Mahony AHRS（互补滤波）** | `imu.c:261` |
| 增益实测值 | **Kp = 0.25 / Ki = 0.0025** | `imu.c:457-458` |
| 上电快收敛 | 前 2 秒 Kp ×10 | `imu.c:239-256` + `bsp_timer.c:185-190` |
| 姿态表示 | **四元数** (q0,q1,q2,q3) → 旋转矩阵 `rMat` | `imu.c:5`、`:77` |
| 输出 | 欧拉角 `angle[3]`，单位 **度×100** | `imu.c:8`、`:372` |
| 偏航处理 | 加速度计 `useAcc` 门控；无磁力计 → 强制 `angle[2] = 0` | `imu.c:360`、`:440`；`pid.c:247` |
| 超时保护 | `if (deltaT > 0.2f) return;` | `imu.c:419` |

🟢 **为什么用四元数而不是欧拉角**：欧拉角在俯仰接近 ±90° 时**万向节死锁**
（横滚与偏航的旋转轴重合，数学上退化），而飞控要做空翻（`flip.c`），
必然经过 ±90°；四元数无死锁，只需 4 个数，且更新过程**不需要三角函数** ——
M0+ 没有 FPU 也扛得住。最终给人看时再换算成欧拉角。

| 失效 | 现象 |
| --- | --- |
| 完全不融合，只积分陀螺 | 飞机越飞越歪，最终侧翻；重新上电又正常（零偏重新校准了） |
| 融合权重太重（太信加速度计） | 一加速就抖；机架振动被当成姿态误差 |
| 融合权重太轻（几乎只信陀螺） | 退化成"只积分"，漂移照样发生 |
| 加速度计失效（如 SPI 断了）却仍参与纠正 | 姿态角被错误的重力方向拉走 → 突然自旋或侧翻 |
| `deltaT` 保护缺失 | 计数器回绕算出 65ms 的巨大 `deltaT` → 四元数跳变 → 姿态角瞬间跳几十度 |

### 2.6 怎么根据姿态决定动作（控制律、周期、限幅）

**没有这一步会怎样**：飞机只是一个"会飞的姿态显示器"，必须全程手动修正，风一吹就翻。

```text
 遥控摇杆 rcCommand[axis]（−500~+500）
   │ ×20 → −10000~+10000（对应 ±100 度，因为 angle[] 是"度×100"）
   ▼
 期望角度 = constrain(20·rcCommand, ±30000) + trim − angle[axis]   ← 减去实际角度 = 角度误差
   │ × PAngleToRate（ROLL/PITCH=1.0，YAW=0.3）
   ▼
 期望角速度 target_rate            ← 外环（角度环）的输出
   │ − accgyro.gyroData[axis]      ← 陀螺仪直接测出的真实角速度
   ▼
 角速度误差 → P（×PRate）+ I（×IRate×deltaT，限幅）+ D（限幅）
   ▼
 各轴修正量 → PIDMIX 混控 → motorPWMValue[4]
```

🟢 **"为什么串级"的物理理由**：单环（只有角度环）也能飞，但**响应慢** ——
等角度真的偏了才修，修的时候风已经把它推得更远。
内环用陀螺仪做反馈，**每 1ms 就有新值**，比角度环快得多。
外环负责"该转到什么角速度"，内环负责"立刻达到这个角速度"。

🟢 **控制周期是本工程最容易被误解的地方**：

```text
 ❌ 常见误解：控制周期由 TIM17 的 1ms 中断保证
 ✅ 代码事实：flight_ctrl() 在【主循环】里调用

 证据链：main.c:371 while(1) → main.c:399 altitude_ctrl()（注释标 2.1~3.873ms）
         → main.c:402 flight_ctrl()（注释标 2.493~3.446ms）→ fc.c:73
         → fc.c:82 if(deltaT >= 0.00125f) ← 这是"限频保护"，不是"周期保证"

 ⇒ 实际姿态控制周期 ≈ 主循环单圈耗时（≥ 约 4.6ms，视负载浮动），不是 1ms。
   fc.c:82 的 1.25ms 门槛只防"同一周期被重复执行"，
   它压不到 1.25ms —— 因为主循环本来就跑不了那么快。
```

这个事实带来三个结果：**①** PID 里的 `deltaT` 必须实测，不能写死 1ms
（代码正是这么做的，`fc.c:79-81`）；**②** 周期抖动直接体现在 I/D 项上 ——
`altitude_ctrl()` 耗时在 2.1~3.873ms 间浮动，意味着 `deltaT` 有约 1.8 倍抖动量；
**③** 想让姿态环真跑 1kHz，得把控制链搬进中断，但那会带来重入、栈、阻塞等新问题。

🟢 **限幅为什么必须有**：**积分饱和（windup）** —— 目标角速度长期达不到（比如被风顶住）时
积分项会一直累加，条件一反转就要很久才"退掉" → 猛冲过头再慢慢回来
（本工程限幅 `_imaxPR=350`、`_imaxYaw=228`，`pid.c:316-319`）。
**输出限幅** —— `motorPWMValue` 是 `uint16_t` 千分比，混控算出负值再赋给无符号数会回绕成
65436 → PWM 满油门。本工程只在 `bsp_pwm.c:152` 兜住**上界**，**没兜下界**
（`bsp_pwm.c:203-208` 有明确说明）。

### 2.7 怎么把动作输出给电机（PWM、频率、死区）

**没有这一步会怎样**：算得再对也不动；或者更糟 —— 四路不一致导致机身瞬间抖一下。

```text
 pid.c 混控 → motorPWMValue[4]（0~1000 千分比）
   ▼
 bsp_pwm.c:209 motor_pwm_output()   ★ 四路"连续写完"，中间不留空档
   ├ PWM1_ChangeDuty() → TIM3->CCR4 (PB1)   ├ PWM3_ChangeDuty() → TIM3->CCR1 (PB4)
   └ PWM2_ChangeDuty() → TIM3->CCR3 (PB0)   └ PWM4_ChangeDuty() → TIM3->CCR2 (PB5)
   ▼
 TIM3：Prescaler=3−1，Period=1000−1，PCLK1=48MHz → 48MHz/3/1000 = **16kHz**（main.c:244）
   ▼
 电调（ESC）→ 三相电流 → 电机 → 推力
```

🟢 **为什么"四路必须连续写完"**：本工程 `AutoReloadPreload = DISABLE`（`bsp_pwm.c:100`），
写 CCR **立即生效**，不等下一个 PWM 周期。如果分四次写、中间被打断，
在那个瞬间四个桨的推力组合既不是旧姿态也不是新姿态 → 机身"抽搐"一下。
16kHz 下周期只有 62.5µs，这个风险窗口相对更大。

🟡 **为什么是 16kHz**：太低（50~400Hz）→ 控制延迟大、电流纹波大，电机"啸叫+抖动"；
太高（>32kHz）→ 部分电调不认、MOS 开关损耗上升。**8~16kHz 是通行区间**（多数数字电调支持）。

| 失效 | 现象 |
| --- | --- |
| PWM 频率算错（按 24MHz 而非 48MHz 算） | 实际频率差一倍，部分电调不认 → 电机不转或间歇转 |
| 上电初值给 50% 而不是 0% | **上电瞬间电机狂转**（本工程特意设 `Pulse = 0`，`bsp_pwm.c:106`） |
| `CCR > ARR` | PWM 恒为高电平 → 电机满转，失控 |
| 混控算出负值直接赋给 `uint16_t` | 回绕成 65436 → 满油门 |
| 解锁标志初始化成 1 | 上电电机就转（`fc.c:109` 明确要求必须为 0） |

### 2.8 怎么接收操作指令（射频、跳频、对码）

| 项目 | 值 | 依据 |

| 芯片 | **PN298**，2.4GHz 无线 BLE 数据收发芯片 | PN298 手册第 8 页 |
| 频段 / 调制 | **2400~2483MHz** ISM / 集成 **GFSK** 调制解调器 | 手册第 8 页 |

🟢 **"对码"解决什么问题**：射频通信需要四方约定（信道、地址、速率、地址宽度）。
**全部写死** → 同场地多机互相串控；旁边有人用同款遥控器就能控制你的飞机。
**对码** → 现场协商一组地址各写进 Flash：解决多机冲突，
天然带"只有配过对的遥控器才能控制"的安全性，
还顺便把加速度/陀螺零偏一起传过来（省一次手动校准）。

| --- | --- |
| 地址写死 | 同场地互相串控；旁边同款遥控器能控制你的飞机 |
| 只改信道不改地址 | 换频点也没用，别人扫到你的频点照样串 |
| 关掉硬件 CRC | 噪声被当合法包 → 舵量乱跳（本工程**无软件校验和**，全靠硬件 CRC，`deal_pack.c:31-32`） |

### 2.9 怎么知道对方还活着（心跳、软定时器、失效保护）

**没有这一步会怎样 —— 这是最危险的失效模式**：

```text
 没有失效保护 → 遥控失联后飞控继续按【最后一次收到的舵量】输出
   → 飞机保持最后的油门与姿态一路飞走 → 直到电池耗尽或撞上东西
 俗称"放风筝"。

 本工程的完整链：
  ① 心跳产生：遥控器每约 10ms 发一包 0xAA 数据帧
  ② 心跳"验真" ★ 关键细节
     deal_pack.c:257  connection_nowtime = HAL_GetTick();
     这一句只在【解析出合法数据包】时才执行 ——
     判据不是"收到任意字节"，而是"收到帧头对、device_ID 对的完整包"。
     噪声字节不算 → 不会因为干扰而误判为"链路正常"。
  ③ 超时判定：main.c:462  if (HAL_GetTick() − connection_nowtime > 5000)
  ④ 安全动作：灯语 200ms 快闪 / fc.flags.bLanding = 1（交给状态机自动降落）
              / bsp_pn298_rx_mode()（射频切回接收，等于自动重连）
```

🟢 **"软定时器"为什么在这里出现** —— 硬件定时器不够，是**硬约束**不是风格偏好：

```text
 PY32F030 的定时器（数据手册第 1 页产品特性）：1 个高级控制定时器 TIM1 +
 4 个通用 16 位定时器 TIM3/14/16/17 + LPTIM/IWDG/WWDG/SysTick/IRTIM
 本工程已占用：TIM1→RGB 灯（main.c:239）、TIM3→电机 PWM（:244）、
              TIM16→1µs 时间戳（TIM16.c:107）、TIM17→1ms 节拍（:235）
 ⇒ 4 个通用定时器里 3 个已被占用，只剩 TIM14；
   而本工程需要的不同周期任务至少有 8 个 → 一个任务一个定时器根本无解。
 ⇒ 解法：只用一个 1ms 硬件中断当"表"，软件里数格子
     （bsp_timer.c:175-192 中断里只做 ++ ／ main.c:374-452 主循环比阈值、清零）
```

| 计数器 | 名义 | **实际** | 做的事 | 出处 |
| --- | --- | --- | --- | --- |
| 每一圈 | —— | ≥ 约 4.6ms | `altitude_ctrl()` + `flight_ctrl()` + 失联检测 | `main.c:399`/`:402`/`:462` |
| `_cnt4ms` | 4ms | **约 5ms** | `Mode_Controler()`（空翻状态机） | `main.c:390` |
| `_cnt10ms` | 10ms | **约 11ms** | `decode_pack()` + `annexCode()` | `main.c:374` |
| `_cnt100ms` | 100ms | **约 101ms** | **喂狗** + `Led_Process()` | `main.c:411` |
| `_cnt1s` | 1s | **约 1.001s** | `get_voltage()`（电池电压） | `main.c:445` |
| `_cnt20ms` | 20ms | 20ms | `calibrationEnbTimer`/`powerupTimer`（中断内自清） | `bsp_timer.c:185` |

> **为什么实际是 N+1ms**：判据是 `if(_cnt >= N){_cnt = 0;}`，而中断仍在同一毫秒内继续 `++`。
> 对灯语、喂狗无所谓；**时间敏感的地方必须实测** ——
> 这正是 `flip.c` 的 `dt` 按"两次调用间隔"实测取值（`flip.c:26-30`）而不是写死 4ms 的原因。

| 失效 | 现象 |
| --- | --- |
| 阈值太长（本工程 5 秒） | 飞手已失去控制，飞机还在按最后指令飞 5 秒 —— 已经飞出很远了 |
| 阈值太短（如 200ms） | 遥控器短暂遮挡就误触发降落 → 飞行中频繁"自己往下掉" |
| 判据用"收到任意字节"而非"合法包" | 干扰噪声就能让飞控以为链路正常 → **失效保护形同虚设** |
| 触发后只闪灯、不碰油门 | 报警好看，但飞机照样飞走 |
| 触发后直接停桨而不是降落 | 高空停桨 = 自由落体 → 摔机 |
| 触发后不能自动解除 | 一次干扰就永久告警（本工程 `bLanding` 只被置 1，`main.c:466-468` 有记录） |

### 2.10 怎么保证自己不卡死（看门狗、喂狗位置、复位源）

**没有这一步会怎样** —— 本工程真实存在的四种卡死风险：

```text
 ① 死等外设标志：bsp_pn298.c:965  while(!(状态 & TX_DS_FLAG));
 ② 除零/野指针 → HardFault → py32f0xx_it.c:105 的 while(1)
 ③ 栈溢出 → 覆盖返回地址 → 跑到随机地址 → HardFault
 ④ 某个循环的退出条件永远不成立

 没有看门狗 → 飞机保持卡死那一刻的电机输出，一路飞走或原地打转。
```

| IWDG 的性质（参考手册第 339 页） | 原文要点 | 为什么这样设计 |
| --- | --- | --- |
| 由 **LSI** 驱动，stop 模式也工作 | 「由 LSI 提供时钟（在 stop 模式也可以工作）」 | 主时钟坏了它照样计数 → **救得了"时钟都乱了"的场面** |
| **一旦运行不能停止** | 「一旦运行，则 IWDG 不能被停止。」 | 可被软件关掉的看门狗等于没有 |
| 写 `0xCCCC` 启动 / `0xAAAA` 喂狗 | 第 339 页 23.3.1、第 340 页 23.4.1 | 用魔法命令，避免误写普通值就改状态 |

```text
 超时 = 预分频 × 重载值 ÷ LSI = 32 × 512 ÷ 32768 = 0.5 秒          WDG.c:67-70
 LSI 精度（数据手册第 44 页表 6-16）：常温 ±3% / 全温区 ±20%
   → 实际 0.485~0.515 秒（常温）／0.40~0.60 秒（全温区）
 喂狗周期 ≈ 101ms（main.c:411）  → 最坏余量 = 0.40 / 0.101 ≈ **4 倍**

 ✅ 正确：主循环里、所有控制任务【都跑完之后】
    main.c:411-414  if(_cnt100ms >= 100){ _cnt100ms = 0;
                        HAL_IWDG_Refresh(&IwdgHandle);   // ← 唯一的喂狗点
                        Led_Process(); }
    放在这里意味着：只要"10ms 收遥控 / 4ms 特技 / 定高 / 姿态控制"这条链路
    的任何一环卡死，主循环就到不了这一句 → 狗咬 → 复位。
 ❌ 错误：在定时器中断里喂狗 —— 中断由硬件独立触发，主循环彻底卡死时中断照常发生
    → 看门狗永远不会触发 = **你花钱买的安全网，被自己剪断了**。
 判断标准一句话：喂狗的位置必须是"只有程序正常推进时才会执行到"的地方。
```

🟢 **为什么选 IWDG 而不是 WWDG**：IWDG 挂 **LSI**（独立 RC），主时钟坏了照样工作；
WWDG 挂 **PCLK**，主时钟没了它自己也停了，救不了。
另外 WWDG 要求**在窗口内**喂狗（太早也算错）—— 它防的不是"卡死"而是"**跑太快**"
（比如某个初始化循环被优化掉，程序 3ms 就冲过了本该走 100ms 的自检）。
**两种狗防的是不同故障，不是替代关系**（这是 4.2 节"可靠性主线"的一环）。

🟢 **复位源识别：怎么知道"刚才那次复位是谁干的"**（参考手册第 82 页 7.1.2）：
`RCC_CSR` 里有独立标志位 —— bit30 `WWDGRSTF`、bit29 `IWDGRSTF`（**"是不是狗咬的"就看这一位**）、
bit28 `SFTRSTF`、bit27 `PWRRSTF`（上电/掉电）、bit26 `PINRSTF`；写 `RMVF` 清零。
**这是本工程最有价值的"可观测性"入口之一**（见 6.3 第 3 关）。

| 失效 | 现象 |
| --- | --- |
| 没有看门狗 | 卡死后永久卡死，飞机带着最后的输出飞走 |
| 在中断里喂狗 | 主循环卡死也照样喂 → 看门狗看似"从没触发过"，其实是废的 |
| 超时太短（如 120ms） | 偶发长任务（Flash 擦写、对码）就误复位 → 飞机周期性重启 |
| 超时太长（如 10s） | 卡死后要等 10 秒才恢复，飞机早掉下来了 |
| 在初始化阶段就启动看门狗 | Flash 擦写可能超过超时 → 反复复位（本工程放在最后，`main.c:347`） |
| HardFault 处理里直接复位而不死循环 | 看不出故障现场（本工程的 `while(1)` 是**故意**的） |

## 3. 三次"能力跃迁"（每次都是被需求逼出来的）

这一节回答一个问题：**这套东西不是一条平滑的斜线，而是三个台阶。台阶是怎么被逼出来的？**

### 3.1 第一次跃迁：从"能飞"到"能自主" —— 为什么需要姿态解算

```text
 【跃迁前：人在回路里当控制器】
  飞手眼睛 ─看姿态─► 飞手大脑 ─算修正量─► 摇杆 ─► 飞控 ─► 电机
     ▲                                                    │
     └────────────── 飞机姿态变化 ◄────────────────────────┘
  优点：飞控极简单。  缺点：飞手必须【持续】修正。

 【跃迁后：飞控当内环控制器，人只给意图】
  飞手 ──给意图（要多斜/多快）──► 飞控 ──► 电机
                                  ▲  │
                                  │  ▼
                            姿态解算 ◄── 陀螺仪 + 加速度计（毫秒级闭环）
  人负责"去哪里、多快"（慢回路，秒级）；飞控负责"保持这个姿态"（快回路）
```

🟢 **为什么"人当控制器"撑不住**：人的反应时间约 0.2~0.3 秒（🟡 生理学通说）。
在这段时间里，一阵 3m/s 的侧风足以让小四轴倾斜十几度，而这十几度会继续带来水平速度
—— 误差是**累积**的。更本质的是：飞手看到的是"结果"（姿态歪了），
而修正需要"原因"（角速度多少、要抵消多少），人脑做这个反推有延迟，
延迟在闭环控制里直接降低稳定裕度。**在持续扰动（风）下，"人当控制器"的闭环带宽不够**
—— 这不是飞手技术问题，是物理限制。

🟢 **为什么这一步必然要求姿态解算**：要闭环控制姿态，先得**测出**姿态。
陀螺仪给角速度、可积分但会漂；加速度计给绝对倾角、不漂但噪声大且受运动加速度污染。
**两个都不够用 → 必须融合 → 这就是"姿态解算"这一层存在的必然性。**
换句话说：姿态解算不是"有人发明了一个算法"，而是"想要快回路闭环"逼出来的产物。

**连锁需求**：滤波（内环吃噪声 → D 放大 → 电机抖）、精确时基（积分微分都要 `dt`）、
零偏校准（不然积分必漂）、安装方向校正（芯片焊向与机体轴不一致）、
限幅（积分饱和与输出回绕）、更高主频（浮点 + 三角函数，且无 FPU）——
对应本工程 `filter.c`、`TIM16.c` 的 `micros16()`、`accgyro.c` 的校准与 `CW90_DEG`、
`pid.c:316`、`main.c:120` 的 48MHz。

### 3.2 第二次跃迁：从"一个定时器"到"多层时基" —— 为什么需要软定时器

```text
 【跃迁前：一个定时器干一件事】
  TIMx 中断（比如 1ms）→ 中断里直接干活：读传感器 → 算姿态 → 算 PID → 输出
  问题 1：中断里干活的时间不受控，姿态解算要几毫秒，这期间其它中断全被挡住
  问题 2：想再加"每 100ms 喂狗"？要么在 1ms 中断里数 100 次，要么再占一个定时器
  问题 3：有些活不能放中断（printf、Flash 擦写），太慢会破坏节拍
  问题 4：中断里调用的函数必须可重入，否则会和主循环互相踩

 【跃迁后：中断只打拍子，主循环干活】
  ┌── TIM17 中断（1ms）──┐        ┌──── 主循环 while(1) ────┐
  │ _cnt4ms++ / _cnt10ms++│        │ if(_cnt4ms>=4)   → 特技  │
  │ _cnt100ms++ / _cnt1s++│ ─────► │ if(_cnt10ms>=10) → 收遥控│
  │ baroUpdateTimer++     │ 共享   │ if(_cnt100ms>=100)→ 喂狗 │
  │ altitudeCtrlTimer++   │ 计数器 │ if(_cnt1s>=1000) → 电池  │
  │ （每 20ms）校准计时++  │        │ altitude_ctrl()/flight_ctrl()│
  └── 中断耗时：几微秒 ───┘        └── 耗时任务：几毫秒 ──────┘
```

| 维度 | 收益 | 代价 |
| --- | --- | --- |
| 硬件资源 | 一个定时器虚拟出任意多个周期任务 | 需要维护一堆计数器变量 |
| 实时性 | 中断极短，不阻塞其它中断 | **周期精度取决于主循环耗时**（本工程姿态环就是这样） |
| 并发安全 | 任务天然串行，无需考虑重入 | 慢任务会拖慢所有任务（头阻塞） |
| 精度 | 计数分频的抖动是"整毫秒级" | 拿不到亚毫秒级的精确定时 |
| 可读性 | 调度逻辑一眼看懂 | 任务多了以后"谁依赖谁"不直观 |

**这次跃迁埋下的三个坑**（🟢 本工程真实存在）：

| 坑 | 现象 | 本工程现状 |
| --- | --- | --- |
| 共享变量没加 `volatile` | 编译器把计数器缓存进寄存器 → 条件永远不成立 → 死等 | `bsp_timer.c:113-116` 的 `_cnt*` **没加**；靠"主循环里有大量函数调用"侥幸正确 |
| 丢掉更新（lost update） | 中断 `++` 与主循环 `= 0` 竞争 → 少计一次 | 靠"中断只加、主循环读完再清零"的**约定**避开 |
| 任务被饿死 / 重复执行 | 某圈耗时超过某计数器周期 → 条件"立刻又成立" → 连续执行两次 | `main.c:368-369` 明确记录了这个特性 |

> ⚠ **`volatile` 不保证原子性**：它只解决"编译器缓存"，不解决"读-改-写被打断"。
> Cortex-M0+ 上 `++` 编译成读-加-写三条指令，中断插在"读"和"写回"之间就会丢一次更新。
> 真要严格，应该用 `__disable_irq()/__enable_irq()` 包住临界区，
> 或者坚持"中断只置标志、主循环只清标志"的单向约定。🟢

### 3.3 第三次跃迁：从"能通信"到"可靠通信"

```text
 【跃迁前：单发】遥控器 ──发一包──► 飞控（不管对方收没收到）
  优点：简单、延迟最低。  缺点：丢一包就是丢一包，双方都不知道。

 【为什么在 2.4GHz ISM 撑不住】（🟢 从物理与法规推证）
  ① ISM 免许可 → 任何人任何设备都能用：Wi-Fi、蓝牙、无线键鼠、同款遥控器……
     → 你不是"独占"这个频段，冲突是常态而不是意外
  ② 2.4GHz 波长约 12.5cm，绕射弱、穿透差，人体/机身遮挡造成瞬时深衰落
  ③ ⇒ **必须假设"每一包都可能丢"**。这不是悲观，是频段属性决定的工程前提。
```

```text
 一整套可靠性机制，一层防一类故障：
 ⑧ 看门狗              防：连"判断失联"这段代码本身都卡死了     WDG.c + main.c:414
 ⑦ 失效保护（5000ms）  防：确认断了之后飞机还在按旧指令飞       main.c:462 → 自动降落
 ⑥ 心跳                防：链路"看起来通但其实早断了"           deal_pack.c:257
 ⑤ 帧头 + 设备 ID      防：别人的包被当成自己的                 deal_pack.c:120
 ④ PID 去重（每包 2 位）防：重传包被当成新包重复执行            手册第 19 页
 ③ 自动重传（ARC=3）   防：偶发丢包                            手册第 17、33 页
 ② ACK 应答            防：包丢了但发送方不知道
 ① 硬件 CRC + 自动扰码 防：比特被噪声改了却当成合法数据         手册第 9 页
```

| 层 | 它防的故障 | 它**不**防的故障 |
| --- | --- | --- |
| CRC | 数据被噪声改变 | 包整个丢了 |
| ACK + 重传 | 偶发丢包 | 持续干扰（重传 3 次全失败 → MAX_RT） |
| PID 去重 | 重传导致重复执行 | 包内容错误（那是 CRC 的活） |
| 帧头 + 设备 ID | 别人的包 | 自己的包内容过期 |
| 心跳 | 链路早已静默 | 收到的包合法但指令错误 |
| 失效保护 | 断链后继续按旧指令飞 | 飞控软件崩溃 |
| 看门狗 | 软件崩溃 / 卡死 | 传感器给出错误但"看起来合法"的数据 |

🟢 **"跳频"在本工程的实际状态**（需要澄清）：`main.c:80` 初始化
`ch_change_arr[2] = {36, 36}`（两个值相同，看起来不跳频），
但 `main.c:265` 会把 `ch_change_arr[1]` **覆盖成 Flash 里存的对码信道**。
所以**本工程确实会跳频** —— 两个候选频点分别是"出厂默认 36"和"对码时协商的信道"。
代码结构保留了"每 500ms 换一次信道扫描"的能力（`main.c:82-88`）。

| 机制 | 代价 |
| --- | --- |
| CRC | 每包多几个字节；算 CRC 要时间 |
| ACK | 收方必须在**很短的应答窗口内**回包 → 时序紧张（`bsp_pn298.c:1168` 用 `delay_us(30)` 卡窗口） |
| 自动重传 | 延迟不确定（ARC=3 ⇒ 最坏是单次的 4 倍），但量级约 1ms，与主循环 ≥4.6ms 同数量级，几乎无感 |
| 心跳 | 必须持续占用空口时间，即使没有指令要发 |
| 失效保护 | 阈值是"两头都错"的取舍（见 2.9 的表） |
| 看门狗 | 喂狗点必须精心选择；初始化顺序被约束（`WDG_init()` 必须在最后） |

## 4. 三条主线

这一节回答一个问题：**抛开模块划分，有哪几条线贯穿整个飞控？**

### 4.1 时间主线：硬件定时器 → SysTick → 软定时器 → 任务调度

```text
 精度 ▲
 高   │ ① 硬件定时器直接产生精确周期    TIM17：/480/100 → 1000.0Hz
      │    抖动：±几个时钟周期（纳秒级）
      │    └─ 只能有一个"最精确"的节拍
      │ ② 中断里只计数，不干活           bsp_timer.c:180-189（六条 ++ 指令）
      │    抖动：几乎不变（几微秒）
      │    └─ 主循环开始引入不确定性
      │ ③ 软定时器分频：N+1 ms 整毫秒抖动  _cnt4ms/_cnt10ms/_cnt100ms/_cnt1s
      │    抖动：±1 个主循环周期
      │    └─ 任务耗时开始互相影响
      │ ④ 主循环任务调度（本工程控制环在这里）
      │    altitude_ctrl() 2.1~3.873ms ／ flight_ctrl() 2.493~3.446ms
      │    抖动：约 ±1.8 倍
 低   │ ⑤（未采用）RTOS 任务 / 中断内控制环
      │    代价：栈内存、上下文切换、可重入要求、优先级反转、调试难度
      └──────────────────────────────────────────────────► 灵活性 高
```

🟢 **核心取舍一句话**：**越精确的方案越不灵活，越灵活的方案越不精确。**

| 层次 | 精度 | 灵活性 | 本工程 |
| --- | --- | --- | --- |
| 硬件定时器直驱 | 最高（纳秒） | 最差（一个定时器一个任务） | TIM17 = 系统节拍 |
| 中断内计数 | 高（微秒） | 中 | `bsp_timer.c` |
| 软定时器 | 中（整毫秒） | 好（任意多任务） | `main.c` 主循环 |
| 主循环直接调用 | 低（视负载） | 最好 | **`flight_ctrl()` 就在这一层** |
| RTOS | 中~高（视实现） | 最好 | 未采用 |

> **本工程最有意思的一点**：**最需要精确的那个环（姿态控制）恰恰放在了最不精确的那一层**。
> 代码作者在 `fc.c:15-20` 写的理由是"控制周期由硬件保证"，但那描述的是**中断**，
> 而 `flight_ctrl()` 实际在主循环里 —— 这是**设计意图与代码事实的偏差**（见 8.1 节）。

### 4.2 可靠性主线：CRC → ACK+重传 → 心跳 → 失效保护 → 看门狗

```text
 故障规模 ▲
 大      │ ⑤ 看门狗：整个软件卡死
         │    防：任何形式的程序失控（死循环/HardFault/栈溢出）；手段：硬件倒计时 + 复位
         │    ★ 必须在主循环喂，中断喂 = 废掉
         │ ④ 失效保护：链路确定断了
         │    防：飞机按最后指令继续飞（"放风筝"）；手段：超时判据 + 安全动作
         │ ③ 心跳：链路已静默一段时间
         │    防：以为链路还好，其实早就不通了；手段：周期性合法包 + 时间戳比对
         │ ② ACK + 重传 + PID 去重：偶发丢包
         │    防：单包丢失、重传被当新包；手段：应答窗口 + ARC=3 + 2 位 PID
 小      │ ① CRC + 扰码：单包内的比特错误
         │    防：噪声改了数据收方却当合法；手段：硬件 CRC + 自动扰码
         └──────────────────────────────────────────────► 代价（时间/复杂度/空口占用）
```

| 去掉哪一层 | 立刻出现的故障 |
| --- | --- |
| CRC | 噪声字节被当合法包 → 舵量随机跳 → **失控** |
| ACK | 发送方不知道包丢了 → 遥控"偶尔失灵"，且飞控不知道 |
| 重传 | 一次丢包就是一次指令缺失 → 指令序列出现空洞 |
| PID 去重 | 重传包被当新包执行两次 → 舵量被重复施加 |
| 心跳 | 链路断了飞控不知道 → 一直用旧指令 |
| 失效保护 | 知道断了但什么也不做 → 照样飞走 |
| 看门狗 | 判断"失联"的代码本身卡死 → 失效保护也不会执行 |

> **"纵深防御"的工程含义**：每一层都假设**下面那层会失效**。
> 这不是不信任，而是可靠性设计的基本姿态 —— 各层**失效模式不同**，
> 叠加起来能覆盖的故障类型远比单层多。

### 4.3 抽象主线：寄存器 → HAL → BSP → 驱动 → 应用

```text
 抽象层级 ▲
 高      │ ④ 应用层：飞行意图    pid.c / fc.c / flip.c / altitude.c
        │    它只知道"角度、角速度、油门"，不知道定时器是什么
        │ ③ 驱动层：这颗具体芯片怎么说话
        │    icm42688.c（量程/ODR/FIFO/校准）、bmp3.c、bsp_pn298.c
        │    ★ 官方驱动通过函数指针回调平台接口（bsp.c:241）
        │ ② BSP 层：这块板子引脚接哪儿、顺序是什么
        │    bsp.c:92 的 bsp_init()、py32f0xx_hal_msp.c 的 HAL_xxx_MspInit()
        │ ① HAL 层：寄存器 → 函数
        │    HAL_TIM_PWM_Start() / HAL_IWDG_Refresh() …；用 __weak 留覆盖点
        │ ⓪ 寄存器层：内存映射地址
 低      │    GPIOA 基址 0x5000_0000（参考手册第 22 页表 3-2）；
        │    ODR 偏移 0x14、BSRR 偏移 0x18（第 94 页）；
        │    Flash 0x0800_0000、SRAM 0x2000_0000（第 21 页）
        └──────────────────────────────────────► 可移植性 / 代码量 / 执行时间
```

| 加这一层 | 换来什么 | 付出什么 | 本工程的证据 |
| --- | --- | --- | --- |
| **寄存器 → HAL** | 跨芯片移植、不用背位定义 | **Flash 占用**、**执行时间**（层层判断）、**黑箱感** | Flash 已用到 95% 以上（`bsp.c:141-143`） |
| **HAL → BSP** | "这块板子"的差异被隔离在一处 | **隐性依赖**：顺序错了要在很远的地方才报错 | `bsp.c:231-237`："如果谁把 spi_init() 删掉，错误现场离真正的原因很远" |
| **BSP → 驱动** | 换传感器型号时上层不用改 | **回调间接层**：调试时调用栈变长 | `bsp.c:241` 的 `SetupMCUHardware()` |
| **驱动 → 应用** | 应用只关心物理量（度、度/秒、毫米） | **单位换算的魔法数字散落各处** | `flip.c:81` 的 `Gyro_G`、`accgyro.c:35` 的 `acc_1G`、`altitude.c:205` 的 `accVelScale` |

🟢 **"零开销抽象"在单片机上做不到，这是硬件事实**：HAL 库的每个"通用"分支都要占 Flash；
函数指针回调无法内联 → 多一次跳转 + 栈帧；无 FPU 时浮点全部软件模拟。
**本工程有一处非常典型的"为省 Flash 而放弃抽象"**：国际标准大气公式本来用 `powf()`，
但链接它会带入 4KB+ 的 libm 代码，Flash 装不下 → 改成 `altitude.c:150` 的窄区间幂函数
`baro_pow_0p295()`。这不是编程风格，是被 Flash 容量逼出来的。

## 5. 同一问题的多种实现方法（对照表）

这一节回答一个问题：**同一个需求，业界有哪些不同做法？我该怎么选？**

> 每张表四列：**做法 / 解决什么 / 适用场景 / 代价**。凡涉及本工程的另标一列。

### 5.1 系统时基：硬件定时器中断 / SysTick / 主循环计数 / RTOS tick

| 做法 | 解决什么 | 适用场景 | 代价 | 本工程 |
| --- | --- | --- | --- | --- |
| **硬件定时器中断** | 精确、独立的周期节拍 | 周期要确定、抖动要求高 | 占一个硬件定时器；优先级要安排；中断里不能长跑 | ✅ TIM17 → 1ms 任务节拍（`main.c:235`） |
| **SysTick** | 内核自带，不占外设 | HAL 时基、一般超时计时 | 只有**一个**；HAL 占了就不能另作他用 | ✅ `HAL_GetTick()` 的 1ms（`py32f0xx_it.c:141`） |
| **主循环计数** | 零硬件成本 | 对时间精度要求极低 | 精度取决于循环负载，负载变则周期变 | ⚠ 本工程的 `_cnt*` 属"中断计数 + 主循环判断"，介于两者之间 |
| **RTOS tick** | 统一节拍 + 抢占，给所有任务 | 任务多、有优先级与阻塞需求 | 栈内存、切换开销、可重入要求、优先级反转 | ❌ 未采用（`py32f0xx_it.c:121-126` 明确裸机） |

🟢 **为什么本工程同时用 TIM17 和 SysTick 两个都是 1ms 的节拍**：
都用 SysTick → `HAL_Delay()` 阻塞时会污染任务节拍；都用 TIM17 → HAL 的超时逻辑全依赖
`HAL_GetTick()`，改掉要动整个 HAL。**两个独立节拍 = 互不污染的"两个时钟"**，
代价是多占一个定时器 + 一次中断开销（`py32f0xx_it.c:158-161` 写了这个理由）。

> **失效现象（如果合成一个）**：初始化阶段（还没进主循环）若调用了 `HAL_Delay()`，
> 两个节拍合一时任务计数器会被"凭空推快"，表现为"上电后第一次控制周期异常短"
> → `deltaT` 异常 → 积分项第一次就冲高。

### 5.2 任务调度：超级循环 + 软定时器 / 时间片轮询 / RTOS 任务 / 中断驱动

| 做法 | 解决什么 | 适用场景 | 代价 | 本工程 |
| --- | --- | --- | --- | --- |
| **超级循环 + 软定时器** | 用最少资源跑多个周期任务 | 任务数少、耦合松、无阻塞需求 | 慢任务拖慢全部；周期精度受负载影响；共享变量要自己保证安全 | ✅ **就是本工程**（`main.c:371-489`） |
| **时间片轮询** | 每任务轮流得到固定时间片 | 任务粒度均匀、要"公平" | 需保存/恢复上下文；片太小则开销大 | ❌ 未采用 |
| **RTOS 任务** | 抢占式优先级、阻塞/唤醒语义 | 任务多、优先级明确、需要同步原语 | RAM（每任务一份栈）；切换开销；可重入与优先级反转；调试更难 | ❌ 未采用 |
| **中断驱动** | 事件一来立刻响应，延迟最小 | 硬实时、事件稀疏 | 中断里不能长跑；共享数据要原子；嵌套要设计 | 部分（TIM17/SysTick 只计数） |

🟢 **本工程的实际调度顺序**（`main.c:371-489`）：

```text
 ① if(_cnt10ms >= 10)   decode_pack() + annexCode()   约 11ms 一次
 ② if(_cnt4ms  >= 4)    Mode_Controler()              约 5ms 一次
 ③ altitude_ctrl()      ← 每圈都跑，耗时 2.1 ~ 3.873ms
 ④ flight_ctrl()        ← 每圈都跑，耗时 2.493 ~ 3.446ms
 ⑤ if(_cnt100ms>= 100)  喂狗 + Led_Process()          约 101ms 一次
 ⑥ if(_cnt1s   >= 1000) get_voltage()                 约 1.001s 一次
 ⑦ 失联检测            HAL_GetTick() − connection_nowtime > 5000

 ★ ③④ 每圈都跑 ⇒ 主循环一圈至少约 4.6ms
   ⇒ 实际"姿态控制周期"是 4.6ms 起，不是 1ms，且随 ①②⑤⑥ 是否触发而抖动
 ★ 头阻塞的具体例子：if(_cnt1s>=1000){get_voltage();} 里若 ADC/printf 卡住，
   下一圈的 altitude_ctrl()/flight_ctrl() 就被推迟 → 姿态环周期被拉长 → dt 变大
```

🟢 **周期抖动对控制环的具体危害**：I 项乘了实测 `deltaT`，所以累积量仍正确，
但**累积速率不均匀**；D 项是 `(err − err_last)/T`，T 不准 → D 的"力度"随周期波动
（周期短时被放大，可能激发振荡；周期长时被削弱，阻尼不足）。
**这就是 `flip.c` 的 `dt` 要实测而不是写死 4ms 的原因。**

**选型清单**：

```text
 用超级循环 + 软定时器，如果：任务数 ≲ 10；没有"必须阻塞等事件"的任务；
   每个任务都足够短（毫秒级以内）；团队小、需要一眼看懂整个调度。★ 本工程符合全部
 必须换 RTOS，如果：有任务需要阻塞等信号量/队列（忙碌等待浪费 CPU）；
   有明显不同的优先级需求；任务多到 if 链难维护；需要优先级继承避免优先级反转
 用纯中断驱动，如果：事件稀疏但要求极低延迟；事件处理极短（置标志/写 FIFO）
```

### 5.3 传感器读取：阻塞轮询 / 中断触发 / DMA / 定时器触发

| 做法 | 解决什么 | 适用场景 | 代价 | 本工程 |
| --- | --- | --- | --- | --- |
| **阻塞轮询** | 实现最简单，时序完全可控 | 低速传感器、初始化阶段、单任务环境 | **CPU 空转等待**；外设不响应就可能永久卡死 | ✅ 主路径（`accgyro.c:96`；射频也是轮询，`config_rf.h:72`） |
| **中断触发（DRDY）** | CPU 不用等，数据到了才醒 | 采样率不高、需要对采样时刻 | 多占一个引脚 + 一个中断 | ❌ 不用（`accgyro.c:16` 的 `USE_CLK_IN = 0`） |
| **DMA** | 外设与内存自动搬数据，CPU 不参与 | 高速/大批量传输 | 占 DMA 通道；缓冲一致性与半传输中断要处理；调试更抽象 | ❌ 不用（芯片只有 **3 通道 DMA**，参考手册第 20 页图 3-1） |
| **定时器触发** | 采样时刻由硬件决定，抖动最小 | 需要严格等间隔采样（滤波系数按固定采样率设计） | 需要定时器 + 触发路由；采样率被硬件固定 | ❌ 不用 |

🟢 **本工程的量级不匹配（必须知道）**：传感器 ODR 配的是 **200Hz**（`accgyro.c:65-66`）
＝ 每 5ms 一个新数据，而代码按主循环节拍（≥4.6ms）去读 → 有时读到同一个样本，有时跳过样本。
后果：滤波器按"1250Hz 采样率"初始化（`accgyro.c:71-72`），而实际读取节拍是"主循环节拍"，
两者不一致；`imu.c:426` 的滑动平均在数据没更新时等于把同一个值重复平均，平滑效果比预期强。
**这不是 bug 报告，而是"选了轮询就得不到严格等间隔采样"的必然结果。**

### 5.4 姿态解算：互补滤波 / Mahony / Madgwick / EKF / 余弦矩阵

| 做法 | 解决什么 | 适用场景 | 代价 | 本工程 |
| --- | --- | --- | --- | --- |
| **一阶互补滤波** | 最简单地融合"快的陀螺"与"准的加速度计" | 只要横滚/俯仰、MCU 极弱 | 只能处理两轴（欧拉角表示）；漂移抑制有限；有万向节死锁 | ❌ 姿态不用（但 `altitude.c:259` 的**高度**融合是同一思路） |
| **Mahony（互补 + 四元数）** | 四元数表示 + PI 反馈纠正陀螺漂移 | 需要 3 轴姿态、无磁力计或磁力计不可靠 | 要调 `dcm_kp`/`dcm_ki`；偏航无绝对基准（缓慢漂） | ✅ **本工程用它**（`imu.c:261`） |
| **Madgwick** | 梯度下降求最优姿态，收敛快 | 需要更好动态性能、计算资源稍宽裕 | 比 Mahony 多几步运算；增益也要调 | ❌ 未采用 |
| **EKF** | 显式建模噪声，理论最优估计 | 传感器多（磁力计/GPS/光流）、需要协方差 | 矩阵运算（**无 FPU** 时代价极大）；参数多难调；代码量大 | ❌ 未采用 |
| **余弦矩阵（DCM）直接更新** | 用旋转矩阵表示，配合正交化 | 需要避免四元数归一化漂移 | 9 个元素 vs 4 个；每次要正交化 | 部分（`imu.c:6` 的 `rMat` 由四元数算出，不是独立更新） |

🟢 **为什么选 Mahony 而不是 EKF**：① 本芯片**没有 FPU**（数据手册第 6 页特性表整段未提 FPU），
EKF 的矩阵乘法与求逆全是软件浮点，时间与 Flash 都撑不住（本工程 Flash 已 95%+）；
② 本工程**没有磁力计**（ICM42688 是 6 轴），偏航无绝对基准 ——
本工程的应对很干脆：`pid.c:247` 直接 `angle[2] = 0`，偏航只做角速度控制。

🟢 **"没有磁力计"的完整后果链**：6 轴 → 偏航无绝对参考 → 只能靠陀螺积分 → 持续漂移
→ `pid.c:245-247` 把 `angle[2]` 强制清零，偏航只做角速度控制 → 飞机不能"锁头"
（不能保持朝向），但能正常飞，因为偏航本来就靠目视手动修正。
**这不是"缺了个功能"，而是硬件选型决定的能力边界。**

### 5.5 高度融合：只用气压 / 互补 / 卡尔曼 / 超声辅助

| 做法 | 解决什么 | 适用场景 | 代价 | 本工程 |
| --- | --- | --- | --- | --- |
| **只用气压计** | 最简单，绝对高度可用 | 对高度响应要求不高、室内静风 | 受气流/舱盖/手遮挡影响大；响应慢 | 部分（气压是唯一绝对来源） |
| **互补滤波（气压 + 加速度积分）** | 加速度给快响应、气压给绝对基准 | 需要快速高度响应又不想用矩阵运算 | 权重（本工程 0.985）要调；加速度二次积分漂移快 | ✅ **本工程用它**（`altitude.c:259`） |

### 5.6 通信可靠性：单发 / ACK+重传 / 跳频 / 心跳+失效保护

| 做法 | 解决什么 | 适用场景 | 代价 | 本工程 |
| --- | --- | --- | --- | --- |
| **单发** | 延迟最低、最简单 | 允许丢包，或有别的机制兜底 | 丢包无人知道 | 部分（飞机侧基本只被动收 + 回 ACK，`bsp_pn298.c:952`） |
| **ACK + 重传** | 让发送方知道"到了没有" | 指令类数据（不能丢） | 应答窗口时序紧（`bsp_pn298.c:1168` 用 `delay_us(30)`）；重传延迟不确定 | ✅ ARD=250µs、**ARC=3**（手册第 33 页） |
| **跳频** | 避开被占用的频点、抗窄带干扰 | ISM 等拥挤频段 | 双方必须同步跳频序列；切换期间无法通信 | ✅ 出厂 36 + 对码协商信道（`main.c:265`） |
| **心跳 + 失效保护** | 确认链路"整体"还在，并定义断了之后做什么 | 任何无人值守的遥控系统 | 空口时间占用；阈值两头都错的取舍 | ✅ 5 秒超时 → 自动降落（`main.c:462`） |

🟢 **"重传 3 次"意味着什么延迟**：ARD=250µs、ARC=3（手册第 33 页）⇒
最坏 3 次重传 = 4 次发送尝试，单包最坏延迟 ≈ 3×250µs + 4 次传输时间（1Mbps 下每包几十 µs）
≈ **1ms 量级**。这与本工程"主循环 ≥4.6ms"同数量级 ⇒ 一次重传对控制节拍几乎无感；
但若 ARC 设成几十次，延迟就会明显到影响手感。

### 5.7 失效保护动作：保持舵量 / 回中 / 缓降 / 返航 / 断动力

| 做法 | 解决什么 | 适用场景 | 代价 / 风险 | 本工程 |
| --- | --- | --- | --- | --- |
| **保持舵量** | 什么都不做（默认行为） | 无 | **最危险**：按最后指令一直飞走 | ❌ 明确避免 |
| **回中** | 姿态回水平、油门保持 | 固定翼（回中=直线滑翔） | 多轴"回水平但仍带油门"→ 依然飘走 | ❌ 未采用 |
| **缓降 / 自动降落** | 可控下降，减小撞击能量 | 多轴（能悬停，可慢慢落） | 需要高度估计可靠；下降中仍随风漂移 | ✅ **本工程**（`bLanding=1` → `decode.c:123-139` 给 `setVelocity = −650`） |
| **返航（RTH）** | 飞回起飞点 | 有 GPS/光流等位置信息 | 需要位置估计 + 路径规划；本工程**无位置传感器**，做不到 | ❌ 无硬件条件 |
| **断动力（停桨）** | 立刻消除伤害源 | 有降落伞，或"宁可摔机不可飞走" | 高空停桨 = 自由落体；低空可能更安全 | ⚠ 本工程在**落地判定**时用（`decode.c:129-134`，Z 轴加速度 >6500 时上锁） |

🟡 **"选哪种动作"的决策树**：① 有位置传感器吗？有 → 可考虑返航；没有 → 只能做"原地"动作
（本工程属这一类）。② 能悬停吗？能 → 缓降/自动降落（本工程的选择）；不能 → 盘旋下降或滑翔。
③ 下降路上会撞到东西吗？会 → 应先悬停等待重连，超更长时间再降；不会 → 直接缓降。
**本工程把阈值定在 5 秒，这个数字本身就编码了上面决策树的答案**（`main.c:458-459` 有解释）。

### 5.8 看门狗喂狗：主循环 / 中断（错）/ 多任务各自喂 / 窗口看门狗

| 做法 | 解决什么 | 适用场景 | 代价 / 风险 | 本工程 |
| --- | --- | --- | --- | --- |
| **主循环末尾喂** | 证明"主循环完整跑完了一圈" | 超级循环结构 | 需保证喂狗点在所有关键任务之后 | ✅ `main.c:414`，唯一喂狗点 |
| **在定时器中断里喂** | （看似省事） | **没有合理的适用场景** | ☠ **彻底废掉看门狗** | ❌ 明确禁止（`WDG.c:25-26`、术语手册 5.4 节） |

| **窗口看门狗（WWDG）** | 额外防"跑太快跳过关键逻辑" | 有严格时序自检的场合 | 喂狗时机必须落在窗口内；时钟源是 PCLK，主时钟坏了救不了 | ❌ 未采用（`py32f0xx_hal_conf.h` 有使能宏但工程没用） |

## 6. 我该怎么理解和应用（可操作的建议）

这一节回答一个问题：**学完这些，我明天能拿它干什么？**

### 6.1 遇到一个新术语，问五个问题

这五问是本文全部内容的压缩。**任何一个飞控术语都能被这五问拆开。**

```text
 ① 它防的是什么故障？
    答不出来 → 它很可能只是"风格"而不是"机制"
    例：CRC 防"比特被噪声改变"；ACK 防"包丢了不知道"
 ② 没有它会怎样？（要具体到现象）
    答不出具体现象 → 说明还没真正理解它
    例：没有失效保护 → 遥控关机后飞机保持最后的油门一路飞走
 ③ 代价是什么？（时间/内存/Flash/复杂度/延迟）
    找不到代价 → 你漏了什么
    例：看门狗的代价是"喂狗点必须精心选择 + 初始化顺序被约束"
 ④ 什么时候【别】用它？
    最能区分"懂"和"背过"的一问
    例：EKF 姿态解算很好，但在无 FPU 的 M0+ 上不该用
 ⑤ 怎么验证它在工作？
    无法验证的机制 = 无法信任的机制
    例：看门狗 → 插一个死循环，看 0.5s 后是否复位 + 查 RCC_CSR 标志位
```

| 术语 | ① 防什么 | ② 没有会怎样 | ③ 代价 | ④ 何时别用 | ⑤ 怎么验证 |
| --- | --- | --- | --- | --- | --- |
| **CRC**（射频硬件） | 比特被噪声改 | 噪声被当合法包 → 舵量随机跳 → 失控 | 每包多几字节 + 计算时间 | 有更强的前向纠错且带宽极紧时 | 手册第 9 页列为特性；读寄存器确认 CRC 使能位 |
| **软定时器** | 硬件定时器数量不足 | 只能用 1ms 中断干所有事 → 长任务破坏节拍 | 周期精度降到"整毫秒 + 主循环抖动" | 需要亚毫秒精确定时（如 DShot 输出）时 | 在中断里翻转一个 GPIO，用示波器看间隔 |
| **失效保护** | 链路断了还在按旧指令飞 | 飞机飞走 | 阈值两头都错的取舍；误触发会中断任务 | 有更高级的自主返航能力时 | 把遥控器关机，计时看是否约 5 秒后进入降落 |

### 6.2 怎么用"故障反推法"读别人的飞控代码

**核心思想**：不要从 `main()` 顺着往下读（会被细节淹没），
而是**先找安全机制，再找算法**。因为安全机制的位置是**被约束死的**，
它们像"骨架上的关节"，找到了就能定位整个结构。

```text
 第 1 步：找失效保护
   关键词：failsafe / bLanding / connection / timeout / 超时
   本工程：main.c:462 的 HAL_GetTick() − connection_nowtime > 5000
   ★ 一找到它就知道：系统有"链路健康"这个概念 → 心跳一定在某处刷新
     → 刷新点就是"合法包解析成功"处（deal_pack.c:257）
     → 触发后干什么 = "安全动作"的定义
 第 2 步：找看门狗
   关键词：IWDG / WWDG / Refresh / 喂狗 / WDG_init
   本工程：WDG.c:63 的 WDG_init()、main.c:414 的 HAL_IWDG_Refresh()
   ★ 一找到它就知道：启动时机 = 初始化流程的终点；喂狗位置 = 调度结构的"一圈结束"；
     超时 ÷ 喂狗周期 = 系统的容错余量（本工程 4 倍）
     ⚠ 若发现喂狗在中断里 → 这个工程的看门狗是摆设，记一笔
 第 3 步：找初始化顺序
   关键词：init / Init / MspInit / 初始化
   本工程：main.c:214-347、bsp.c:92
   ★ 一找到它就知道：层次图的真实边界（谁必须在谁之前 = 谁依赖谁）；
     哪些初始化是"故意放最后"的（看门狗、射频切地址）
 第 4 步：找时基
   关键词：SysTick / Timer / Prescaler / Period / 1ms / tick
   本工程：main.c:120（时钟树）、TIM16.c（定时器配置）、bsp_timer.c（回调）
   ★ 一找到它就知道：所有"每 N ms"能不能对上（自己算一遍分频）；
     控制环到底在哪一层（中断里？主循环里？）★ 这一步最容易发现"注释与代码不符"
 第 5 步：找控制链
   关键词：pid / PID / mix / motor / PWM
   本工程：fc.c:73（串起 4 步）、pid.c:251（三个轴）、bsp_pwm.c:209
   ★ 一找到它就知道：控制周期是多少（看调用点 + 有没有限频门槛）；
     有没有限幅（积分限幅 + 输出限幅，两个都要有）
 第 6 步（最后）：读算法细节 —— 姿态解算 / 高度融合 / 滤波器参数
   ★ 为什么放最后：算法参数调错了飞机是"飞得不好"；
     前面四步错了飞机是"飞不起来"或"飞走了"。
     **先保证不失控，再追求飞得好。**
```

> **额外好处**：安全机制都有"必须满足的硬约束"（喂狗必须在主循环、看门狗启动必须在最后），

### 6.3 在本工程上练手的建议路径

**原则：从"能被观测到"的地方入手。** 改算法看不到效果，改观测点立刻有反馈。

```text
 ┌ 第 1 关：让串口说话（最低门槛，零风险）────────────────────────────┐
 │ 目标：确认你能改变程序行为并看到结果                                │
 │ 动作：在 main.c:214 之后加一句 printf 打印 SystemCoreClock（应为 48000000）│
 │       在 main.c:445 的 _cnt1s 分支里打印 HAL_GetTick()（每次约 +1000，   │
 │       但实际是 1.001s，所以打印值会缓慢偏移）                        │
 │ 能学到：时钟树的数值、软定时器的 N+1ms 偏差                          │
 │ ⚠ printf 很慢，只放 1s 节拍，别放主循环每圈                          │
 ├ 第 2 关：数心跳（理解中断与共享变量）─────────────────────────────┤
 │ 目标：亲眼看到"中断在跑、主循环在跑、两者频率不同"                   │
 │ 动作：在 bsp_timer.c:180 附近加自己的计数器 myTick++                 │
 │       在 1s 节拍里打印 myTick（预期约 1000；明显偏离说明长期关中断）  │
 │       然后把这个变量加/去掉 volatile，比较编译结果                    │
 │ 能学到：共享变量、volatile 的真实作用                                │
 ├ 第 3 关：看门狗复位源（理解"兜底"机制）───────────────────────────┤
 │ 目标：让看门狗真的咬你一次，并且你能证明是它咬的                     │
 │ 动作：上电时读 RCC_CSR 并打印复位标志（参考手册第 82 页）             │
 │       第一次上电应是 PWRRSTF（bit27），正常情况下 IWDGRSTF 应为 0     │
 │       然后在主循环里临时插入 while(1);                               │
 │       预期：约 0.5 秒后灯重新亮起，且 IWDGRSTF（bit29）= 1             │
 │       反面实验：先把喂狗点临时挪到 TIM17 中断里，再插死循环           │
 │       预期：**不再复位** —— 这就亲眼看到"中断里喂狗 = 废掉看门狗"     │
 │ ⚠ 一定要先备份、做完就改回来                                        │
 │ 能学到：复位源识别、喂狗位置为什么重要、超时余量是否真实             │
 ├ 第 4 关：量一量控制周期（验证架构事实）───────────────────────────┤
 │ 目标：亲手确认"控制环不在中断里"                                     │
 │ 动作：在 fc.c:88 的 motor_pwm_output() 之后翻转一个空闲 GPIO，        │
 │       或用一个变量累加 deltaT 与调用次数                             │
 │       在 1s 节拍里打印 → 预期平均 deltaT ≈ 4~6ms、约 160~250 次/秒    │
 │       **不是 1000 次/秒** —— 这就证实了控制环在主循环                 │
 │ 能学到：控制周期、deltaT 抖动、主循环负载                            │
 ├ 第 5 关：看丢包（理解射频可靠性）─────────────────────────────────┤
 │ 目标：看到重传与丢包计数的真实数值                                   │
 │ 动作：读 PN298 的 OBSERVE_TX(08)：PLOS_CNT 丢包计数、ARC_CNT 重传计数 │
 │       （手册第 35 页），在 1s 节拍里打印                              │
 │       然后人走远、或用手挡住天线，观察计数怎么变                      │
 │ 能学到：ARC=3 到底在做什么、"距离"如何转变成"重传次数"               │
 └──────────────────────────────────────────────────────────────────────┘
```

**练手纪律三条**：① **每次只改一个地方，并且知道"改之前应该看到什么"**
