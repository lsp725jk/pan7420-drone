## 0. 先给一张"全景地图"

飞控 = **一个每 1 毫秒必须醒一次、否则飞机就掉下来的小电脑**。
所有术语都在回答三个问题之一：

| 问题 | 相关术语 |
| --- | --- |
| **它怎么知道时间？** | 晶振、时钟树、PLL、预分频、SysTick、定时器、软定时器、心跳 |
| **它怎么和外界说话？** | 射频、信道、地址、payload、ACK、SPI、UART、对码、心跳包 |
| **它怎么保证不出事？** | 中断、优先级、volatile、看门狗、失联保护、板级初始化 |

把这棵树记住，后面每个名词都能挂上去：

```
                    ┌─ 时钟树 ──→ 定时器 ──→ 中断(1ms) ──→ 姿态控制(PID)
   HSI 校准到      ┤                                    └─→ 软定时器(10/100ms 任务)
   24MHz ─ PLL ×2 ─┤
   = 48MHz         └─ 外设时钟 ─→ SPI(读传感器) / UART(打印) / GPIO(驱动射频)
                                                        │
   遥控器 ──2.4G射频(信道/地址/payload/ACK)──→ 飞控 ───┘
                            │
                      对码(交换地址) ──→ 存 Flash
                            │
                      看门狗(兜底) ←── 喂狗(证明主循环还活着)
   （例外：看门狗用独立的 LSI 32768Hz，不来自 48MHz）
```

## 1. 晶振、时钟树、PLL、预分频

### 1.1 晶振（Crystal / Oscillator）

**定义**：给单片机提供"节拍"的元件。CPU 的每一条指令、每个外设的时序，都由它驱动。

**比方**：晶振 = 乐队的节拍器。没有它，所有人各弹各的。

**两种来源**：
| 类型 | 全称 | 特点 |
| --- | --- | --- |
| **HSI** | High Speed Internal（内部高速） | 芯片自带 RC 振荡器，**不用外接元件、启动快**，但精度差（±1~3%） |
| **HSE** | High Speed External（外部高速） | 外接晶振，精度高（±10~50ppm），但要焊元件、启动慢（ms 级） |
| **LSI** | Low Speed Internal（内部低速） | 约 32kHz，**专供看门狗和 RTC**，因为看门狗要求"即使主时钟坏了也能跑" |

**你工程里的实例**：本项目用的是 **HSI**（内部时钟），
所以 `main.c` 的 `SystemClock_Config()` 里把 `HSEState` 设成了 `RCC_HSE_OFF`，
也就没有"等待外部晶振起振"的代码。

> ⚠ **但注意别理解成"板子上没有晶振"**：**板上其实焊了一颗 16MHz 晶振**
> （`XL7EL89COI-111YLC-16M`，±10ppm），只是**代码没启用它**。
> 这两件事完全不同 —— 详见本手册第 13.2 节，那里有元件清单作证。
> 之前这里写成"板子上没有晶振也能跑"，是与 13.2 节自相矛盾的错误说法，已更正。

> **坑**：HSI 精度差意味着**串口波特率会有误差**。
> 115200 波特率下 ±2% 的误差就可能让某些 USB 转串口模块收错字节。
> 如果调试时串口打印乱码、但换波特率就好，通常就是这个原因。

### 1.2 时钟树（Clock Tree）

**定义**：从晶振出发，经过倍频/分频，把不同频率送到各个外设的一整套路径。

**比方**：时钟树 = 自来水管网。总水管（晶振）→ 加压泵（PLL）→
到厨房的水管（定时器）、到卫生间的水管（串口），各自口径不同。

**你工程里的时钟树**（这是理解全部定时逻辑的钥匙）：

```
① 复位后 SystemInit()：HSI 设为出厂 8MHz 档 + 向量表指向 Flash
   │   （注意：这一步【没有】配 PLL）
   ↓
② main.c 的 SystemClock_Config()：把 HSI 校准到 24MHz
   │   RCC_HSICALIBRATION_24MHz
   ↓
③ PLL 倍频：×2  →  SYSCLK 48MHz
   │   （倍频系数是芯片系统文件里硬编码的 2×，见 system_py32f0xx.c 的
   │     SystemCoreClock = 2 * HSIFreqTable[hsifs]）
   ↓
④ AHB 不分频、APB1 不分频
   → HCLK = PCLK1 = 定时器/串口/SPI 的时钟源 = 48MHz
   ↓
        ┌──────────────┬──────────────┬──────────────┬─────────────┐
        ↓              ↓              ↓              ↓             ↓
   TIM16: /48     TIM17: /480     SPI1: /32     TIM3: /3      TIM1: /4
   = 1MHz 计数    = 100kHz 计数   = 1.5MHz      再数 1000     再数 600
   1 微秒/步      再数 100 计数                  = 16kHz       = 20kHz
        │              │                       （四路电机）  （RGB 灯）
        ↓              ↓
   micros16()     每 1ms 中断一次
   约 65ms 回绕   → 飞行控制主循环

   ┌ 例外：IWDG（看门狗）不来自 48MHz，而来自独立的 LSI ≈ 32768Hz
```

**怎么算出来的**（自己动手推一遍就懂了）：
```
定时器计数频率 = 外设时钟 ÷ (预分频 + 1)
中断周期      = 1 ÷ (计数频率 ÷ 周期值)
             = 1 ÷ (100kHz ÷ 100) = 1 ÷ 1kHz = 1ms   ← TIM17
```
- TIM16：预分频 `48-1` → 48MHz/48 = **1MHz**，即 **1 步 = 1 微秒**（所以叫 `micros16()`）；周期 `0xFFFF` ⇒ 约 65.5ms 回绕
- TIM17：预分频 `480-1`、周期 `100-1` → 48MHz/480/100 = **1kHz**，即 **每 1 毫秒中断一次**
- SPI1：分频 `32` → 48MHz/32 = **1.5MHz**（ICM42688 有最高速率限制）
- TIM3（电机 PWM）：预分频 `3-1`、周期 `1000-1` → 48MHz/3/1000 = **16kHz**
- TIM1（RGB 灯 PWM）：预分频 `4-1`、周期 `600-1` → 48MHz/4/600 = **20kHz**

**为什么重要**：项目里所有"每 1ms""每 10ms"的说法，源头都在这里。
`pid()` 能自称 1kHz，是因为 TIM17 每 1ms 调它一次。

> **注意 `-1` 的坑**：预分频寄存器写 N 表示"除以 N+1"（因为从 0 开始数）。
> 所以想要 48 分频，必须写 `48-1 = 47`。写 48 会得到 49 分频。
> 你工程里代码写的时 `48 - 1`、`480 - 1`、`100 - 1` —— 这是对的写法，一眼看出意图。

> **⚠ 一个极容易搞错的地方（我一开始就搞错了）**：
> **PLL 的倍频不是从"标称 8MHz"开始的**。`SystemInit()` 里的 HSI 是 8MHz，
> 但 `SystemClock_Config()` 会先把 HSI 校准到 **24MHz**，再经 PLL **×2** 得到 48MHz。
> 所以"8MHz × 6 = 48MHz"这种算法**虽然数值巧合正确，过程是错的** ——
> 正确链路是 `24MHz × 2 = 48MHz`。
> 这也解释了一个连带事实：`py32f0xx_hal_conf.h` 里的 `HSI_VALUE = 8000000`
> 是"HSI 的原始频率"（给 HAL 库算 PLL 输入范围用），**不是**最终的系统频率。
> 两处必须一起理解，否则算出来的波特率/定时器周期会全错。

### 1.3 PLL（锁相环，Phase-Locked Loop）

**定义**：把低频时钟"倍频"成高频时钟的电路。

**比方**：齿轮组。小齿轮转 2 圈，大齿轮转 1 圈 → 用慢的输入得到快的输出。

**你工程里**：**HSI 校准到 24MHz × 2 = 48MHz**。

**⚠ 倍频系数在哪里、是多少**（这是个容易搞混的点）：
```c
/* startup/system_py32f0xx.c:106 —— SystemCoreClockUpdate() 里的 PLL 分支 */
SystemCoreClock = 2 * (HSIFreqTable[hsifs]);   /* ← 系数 2 是硬编码在这里的 */
```
```c
/* startup/system_py32f0xx.c:73 —— HSI 可校准档位表 */
const uint32_t HSIFreqTable[8] = {4000000U, 8000000U, 16000000U, 22120000U, 24000000U, 4000000U, 4000000U, 4000000U};
```
- 索引 4 = **24MHz**，正是 `RCC_HSICALIBRATION_24MHz` 对应的档位；
- `SystemCoreClock = 2 × 24MHz = 48MHz`。

**为什么 HSI 要校准到 24MHz 而不是直接用 8MHz**：
HAL 库对 PLL 输入频率有下限要求。你工程里的注释写"必须 12MHz 及以上"，
而 HAL 源码里的实际约束是 **16~24MHz**：
```c
/* drivers/PY32F0xx_HAL_Driver/Src/py32f0xx_hal_rcc.c */
#define PLLSOURCE_FREQ_MIN         (16000000U)
#define PLLSOURCE_FREQ_MAX         (24000000U)
```
所以 8MHz 太低、必须抬高；而 24MHz 是**贴着上限**的取值。

**为什么最终要 48MHz**：这是这颗芯片的额定最高主频，
而且 48 能被 48、480、4800、32 整除，**方便凑出整数微秒/毫秒**（见上面的算式）。

> **设计品味**：选时钟频率时优先选能被整除的值，可以避免累积误差。
> 48MHz 之于 1ms，比 47.5MHz 之于 1ms 舒服得多。

> **⚠ 顺带纠一个常见误解**：`user/py32f0xx_hal_conf.h` 里**没有** `RCC_HSI_ON`、
> 也没有任何 PLL 宏。那些全部在 **`user/main.c` 的 `SystemClock_Config()`** 里。
> hal_conf.h 只提供**标称频率宏**（`HSI_VALUE=8000000`、`HSE_VALUE=24000000`、
> `LSI_VALUE=32768`、`LSE_VALUE=32768`、`VDD_VALUE=3300`），
> 真正的时钟配置代码一行都不在那儿。找时钟配置时别翻错文件。

### 1.4 预分频（Prescaler）

**定义**：把输入频率按整数比例降低的分频器，让下游外设跑在合适的速率。

**比方**：减速带。不是所有路都适合开 120 码。

**你工程里的三处预分频**：
| 位置 | 值 | 效果 | 为什么要分频 |
| --- | --- | --- | --- |
| TIM16 预分频 | `48-1` | 48MHz → 1MHz（1µs/步） | 16 位计数器最大 65535，1MHz 下量程 65ms 够用 |
| TIM17 预分频 | `480-1` | 48MHz → 100kHz | 配合周期 100 得到正好 1kHz |
| SPI 分频 | 见 `spi.c` | 48MHz → 若干 MHz | ICM42688 的 SPI 有最高速率限制，超了读不出数据 |

> **为什么定时器要分频而不是直接用 48MHz**：
> 16 位计数器只能数到 65535。48MHz 下 65535 步只有 **1.36 毫秒**，
> 量程太短；分频到 1MHz 后量程变成 **65.5 毫秒**，够表示"微秒时间戳"了。

### 1.5 为什么"时钟"这词还出现在别的地方

| 说法 | 含义 | 你工程里的地方 |
| --- | --- | --- |
| **时钟树** | 上面讲的分频网络 | `system_py32f0xx.c` |
| **使能外设时钟** | 单片机为省电，外设默认断电，用前要开时钟 | `__HAL_RCC_TIM17_CLK_ENABLE()`、`UARTx_TX_GPIO_CLK_ENABLE()` |
| **时钟校准** | 校准传感器内部的时钟 | `icm426/helperClockCalib.c`（ICM42688 的时间戳换算） |
| **时钟极性/相位** | SPI 的采样边沿设置 | `spi.c` 的 `CLKPolarity` / `CLKPhase` |

> **新手最常犯的错**：忘了使能外设时钟。
> 症状是"代码明明写对了，寄存器却读不出东西/写不进去"。
> 因为外设没上电，寄存器读写全是空操作。

## 2. 中断、中断优先级、SysTick

### 2.1 中断（Interrupt）

**定义**：硬件事件打断 CPU 当前工作，让 CPU 立刻跳到一段专门的代码去处理，处理完再回来。

**比方**：你在写作业（主循环），电话响了（中断），你放下笔去接电话，
接完回来接着写——而且**笔还放在原来的位置**（寄存器/栈由硬件自动保存）。

**为什么飞控离不开中断**：控制周期必须是**精确的 1ms**。
如果放在主循环里，主循环里还有灯语、串口打印等杂事，
执行时间忽长忽短，控制周期就抖了 → PID 的积分和微分全部失准 → 飞机抖。

**你工程里的实例**：
```c
/* user/py32f0xx_it.c —— 中断服务函数（ISR） */
void TIM17_IRQHandler(void)
{
    HAL_TIM_IRQHandler(&TimHandle_17);      /* HAL 会再调回调 */
}
```
CPU 每 1ms 自动跳到这里，最终进入 `bsp_timer.c` 的
`HAL_TIM_PeriodElapsedCallback()`，把各种计数器 +1。

### 2.2 中断服务函数（ISR）的三条铁律

| 铁律 | 原因 | 你工程的做法 |
| --- | --- | --- |
| **函数名不能改** | 名字由启动文件的向量表按名字引用 | `TIM17_IRQHandler` 必须一字不差 |
| **必须短、不能阻塞** | ISR 执行期间主循环完全停摆 | 中断里只做 `xxxTimer++` |
| **共享变量要 `volatile`** | 否则编译器可能缓存到寄存器，永远读到旧值 | ⚠ 你工程的 `_cnt10ms` 等**漏了**（见 2.4） |

### 2.3 "中断打标记、主循环干活"——本项目最重要的设计模式

中断里**不做重活**，只改几个计数器；主循环看到"计数到了"再去做耗时的活。

**你工程里的实例**（TIM17 的 1ms 中断，简化版）：
```c
/* drivers/bsp/bsp_timer.c —— 中断里只加计数，几微秒就返回 */
if (htim->Instance == TIM17) {
    static uint8_t _cnt20ms;
    baroUpdateTimer++;          /* 气压计更新计时 */
    altitudeCtrlTimer++;        /* 高度环计时 */
    _cnt10ms++;                 /* 10ms 分频 */
    _cnt4ms++;                  /* 4ms 分频 */
    _cnt100ms++;                /* 100ms 分频 */
    _cnt1s++;                   /* 1s 分频 */
    if(++_cnt20ms >= 20) {      /* 20ms 分频 */
        _cnt20ms = 0;
        calibrationEnbTimer++;
        powerupTimer++;
    }
}
```

主循环里再按这些计数决定做什么：
```c
/* user/main.c —— 主循环，用软定时器分派任务 */
if(_cnt10ms  >= 10)  { _cnt10ms  = 0; decode_pack(); annexCode(); }   /* 10ms：收解码 */
if(_cnt4ms   >= 4)   { _cnt4ms   = 0; Mode_Controler(); }            /* 4ms：翻滚状态机 */
if(_cnt100ms >= 100) { _cnt100ms = 0; HAL_IWDG_Refresh(&hiwdg); Led_Process(); } /* 100ms：喂狗+灯 */
```

> **为什么这样设计**：`decode_pack()` 可能要跑几百微秒。
> 如果放进 1ms 中断，就会挤占姿态控制的时间，导致控制周期抖动。
> 放到主循环，它晚一点执行无所谓。

### 2.4 中断优先级（NVIC Priority）

**定义**：多个中断同时到来时，谁先执行；以及**高优先级中断可以打断低优先级中断**（嵌套）。

**比方**：医院分诊。心脏骤停（高优先级）能打断普通门诊（低优先级）。

**你工程里的实例**：
```c
/* drivers/bsp/TIM16.c */
HAL_NVIC_SetPriority(TIM17_IRQn, 0, 1);   /* 抢占优先级 0（最高）、子优先级 1 */
HAL_NVIC_EnableIRQ(TIM17_IRQn);
```
**为什么 TIM17 给最高优先级**：它驱动姿态控制。如果它被别的中断延迟，
控制周期就乱了。宁可让别的中断等它。

> **Cortex-M0+ 的限制**：只有 2 位优先级（0~3，共 4 级），比 M3/M4 少得多。
> 所以本项目只给 TIM17 最高优先级，别的用默认值，不做复杂分级。

### 2.5 SysTick（系统节拍定时器）

**定义**：Cortex-M 内核**自带**的一个 24 位递减定时器，常用于产生固定节拍（典型 1ms）。

**比方**：内核自带的"秒表"，不占用外设定时器资源。

**你工程里的实例**：`SysTick_Handler()` 存在，HAL 库用它来累加
`HAL_GetTick()`（毫秒级时间戳），`delay_ms()`、超时判断都靠它。

> **容易混的点**：本项目有**三套**计时来源，分工明确：
>
> | | SysTick + `HAL_GetTick()` | TIM16 + `micros16()` | TIM17 + 软定时器 |
> | --- | --- | --- | --- |
> | 精度 | 毫秒 | **微秒** | 1ms 节拍 |
> | 用途 | HAL 超时、`HAL_Delay`、LED 闪烁、失联判断、翻转 `dt` | 精确的控制周期 `deltaT` | 派生 4/10/100ms/1s 任务（`_cnt*`） |
> | 配置在哪 | HAL 库内部（`HAL_Init`） | `TIM16.c: tim16_init()` | `TIM16.c: Timer17_UpdateIT_Init()` |
> | 中断 | 有（`SysTick_Handler`，优先级最低） | **无**（`HAL_TIM_Base_Start`，不开中断） | 有（`TIM17_IRQHandler`，优先级最高） |
>
> **为什么控制周期不用 `HAL_GetTick()`**：1ms 精度不够 —— PID 的 `deltaT` 要算到微秒。
> **为什么失联判断用 `HAL_GetTick()` 而不用 TIM17 的计数**：失联是"秒级"判断，
> 毫秒精度足够；而且 `HAL_Delay()` 阻塞时 TIM17 计数照常走，两者互不干扰（这是刻意的分工）。
>
> **⚠ 命名陷阱**：**遥控器用的是 TIM16 做 1ms 节拍**（不是 TIM17），
> 而飞控用的是 TIM17。两边主频相同（都 48MHz），但节拍用的定时器不同 ——
> 对照看两边代码时别搞混。飞控的 TIM16 则是"只计数、不中断"的微秒表。

## 3. 板级支持包（BSP）、HAL、寄存器

这三个词描述的是**同一件事的三个抽象层次**：

```
你的业务代码        imu/pid.c、user/main.c        ← "我要飞机保持水平"
      ↓ 调用
硬件抽象层 HAL      HAL_UART_Transmit()           ← "帮我发一个字节"
      ↓ 调用
BSP 板级支持        bsp_uart_send()               ← "本板子的串口是 USART1、PB8"
      ↓ 调用
寄存器操作          USART1->TDR = data;           ← 直接写硬件寄存器
```

### 3.1 寄存器（Register）

**定义**：CPU 和外设打交道的"开关面板"。每个外设有一组寄存器，
读=看状态，写=下命令。地址是固定的（由芯片设计决定）。

**比方**：寄存器和外设的关系 = 遥控器和电视机。你按"音量+"（写寄存器），
电视执行；你想知道当前音量，读"音量寄存器"。

**你工程里的实例**：
```c
/* icm426/icm42688.c —— 手工拼字节读传感器（SPI 读时序） */
accRaw[0] = ((uint16_t)buffer[0] << 8) | buffer[1];   /* 高字节在前（大端） */

/* 位操作是寄存器编程的日常 */
bsp_pn298_read_reg(DEM_CAL) & 0x01;      /* 只取最低位 */
temp |= (1 << 5);                         /* 把第 5 位置 1 */
temp &= ~(0x01);                          /* 把第 0 位清 0 */
```

> **最重要的坑**：改寄存器里某一位时**必须用 `|=` / `&=~`**，不能直接 `=`。
> `REG = 0x08` 会把同一个寄存器里其它配置全部清零。
> 详见 `C_KEYWORDS_GUIDE.md` 第 12 节。

### 3.2 HAL（硬件抽象层，Hardware Abstraction Layer）

**定义**：芯片厂商提供的一层函数库，把"操作寄存器"包装成"调用函数"，
让你不查手册也能用外设，而且换芯片时改动小。

**比方**：HAL = 汽车的方向盘和踏板。你不用知道发动机怎么工作，踩油门就行。

**你工程里的实例**：`drivers/PY32F0xx_HAL_Driver/` 整个目录都是。
```c
HAL_UART_Transmit(&sUartxHandle, &data, 1, 2);   /* 发 1 字节，超时 2ms */
HAL_TIM_Base_Start_IT(&TimHandle_17);            /* 启动定时器并开中断 */
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_8, GPIO_PIN_SET);  /* 拉高引脚 */
```

**HAL 的核心机制：回调（Callback）+ 弱符号（`__weak`）**
HAL 在事件发生时调用一个"空函数"，你在自己代码里写同名函数把它**覆盖**掉：
```c
/* 库里的默认实现（py32f0xx_hal_tim.c） */
__weak void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) { }

/* 你的实现（drivers/bsp/bsp_timer.c）—— 同名即覆盖 */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) { ... }
```
> **注意**：这个函数**不能加 `static`**，也不能改名，否则变成另一个符号，
> 库就调不到你的实现，中断会"什么都不发生"——这是极难查的错误。

### 3.3 BSP（板级支持包，Board Support Package）

**定义**：**针对你这块具体板子**的驱动层。HAL 是"芯片通用"，
BSP 是"本板子专用"——比如"本板子的 LED 接在 PF4""本板子的串口是 PB8/PB2"。

**比方**：HAL 是"通用汽车零件"，BSP 是"这辆车的装配图"。

**你工程里的实例**：`drivers/bsp/` 目录就是 BSP 层：
| 文件 | 板级信息 |
| --- | --- |
| `bsp_uart.c` | 本板串口 = USART1，TX=PB8，RX=PB2，115200 8N1 |
| `bsp_pn298.c` | 本板射频芯片 = PN298，接在软件 SPI 上 |
| `bsp_rfspi_sw.c` | **软件模拟 SPI**（因为射频芯片时序特殊，硬件 SPI 不适用） |
| `bsp_timer.c` | 本板的 1ms 心跳中断在这里处理 |
| `bsp_delay.c` | 微秒级精确延时（用汇编循环实现） |
| `bsp.c` | 把所有 bsp 初始化串起来的总入口 |
| `config_rf.h` | 射频参数（信道、速率、功率、地址宽度、payload 长度） |

> **为什么要分 BSP 和 HAL 两层**：换一块板子（LED 换引脚、串口换外设），
> 只改 BSP，业务代码一行不用动。这是嵌入式工程的标准分层。

## 4. 射频（RF）、信道、地址、Payload、ACK

### 4.1 射频（RF，Radio Frequency）

**定义**：用无线电波传输数据。本项目用 **2.4GHz** 频段（和 WiFi、蓝牙同频段）。

**比方**：射频 = 对讲机。你和遥控器约定一个"频道"（信道）和一个"暗号"（地址），
对上了才能通话。

**为什么飞控用 2.4G 而不是 WiFi/蓝牙**：
- **延迟低且稳定**：WiFi 要握手、重传，延迟几十毫秒且抖动大；飞控需要稳定的几毫秒。
- **可控**：自己管理重传、跳频，不受路由器影响。
- **配对简单**：不需要网络配置。

**你工程里的芯片**：**PN298**（普冉的 2.4G 收发芯片）。
它的寄存器布局与经典的 **nRF24L01** 高度相似（所以你能在网上找到大量 nRF24L01 资料对照看）。

### 4.2 信道（Channel / Frequency）

**定义**：把 2.4GHz 频段切成很多窄带，每条叫一个信道。收发双方必须在同一个信道上。

**比方**：收音机的频道旋钮。调到 98.7 才能听到那个台。

**你工程里的实例**：
```c
/* drivers/bsp/config_rf.h —— 初始信道 36 */
#define CONF_DEFAULE_CNANNEL   36    /* 注意：这个宏名疑似拼写错误（CNANNEL） */

/* bsp_pn298.c —— 写寄存器时有 +64 的偏移 */
bsp_pn298_set_channel(chn);          /* 内部 chn += 64 → 实际写 100 */
```
**为什么有 `+64` 偏移**：**已查手册核对**。《PN298 用户手册 V1.0》第 34 页写明：

```
05  RF_CH   15:0   0x008E   通信频道设置
      HIGH_RF  8   RX 高频/低频选择：0 = 高频，通道 +2M；1 = 低频，通道 −2M
      RF_CH  7:0   设置 TX 使用频道为 Channel = RF_CH + 2336
```

也就是**实际频率(MHz) = RF_CH 寄存器低字节 + 2336**。代入工程代码验证：

| 代码调用 | 写入 RF_CH | 按手册算实际频率 |
| --- | --- | --- |
| `bsp_pn298_set_channel(36)` | 36 + 64 = **100** | 100 + 2336 = **2436 MHz = 2.436 GHz** ✅ |

这与工程注释里写的"36 = 2.436GHz"**完全吻合**，也落在手册标明的 ISM 频段
（2400~2483MHz）内。所以 **`+64` 这个偏移让"代码里的 36"对应到了 2.436GHz**。

> **但要留意两点**（手册核对出来的）：
> 1. **手册里并没有"信道号要加 64"这条规定** —— 它是驱动沿用的常量（很可能来自
>    XN297L 兼容系列的经验值），偏移本身没有手册依据。工程注释说"是芯片的信道编码要求"，
>    严格讲**不够准确**：真正的手册依据是上面那条 `+2336`。
> 2. **RF_CH 寄存器是 16 位**（低 8 位频道 + 高位 HIGH_RF 选择 ±2MHz）。
>    而 `set_channel()` 只写 1 个字节，也就是只改了低 8 位、没动 HIGH_RF 位。
>    想用"−2MHz"那一档（HIGH_RF=1）必须写 16 位。
>
> **实用结论**：改信道时只要保证**收发两端用同一个 `+64` 偏移**，
> 链路就能通；换算实际频率用 `寄存器值 + 2336`。

> **为什么选 36**：2.4GHz 里 WiFi 常用 1/6/11 信道（2.412/2.437/2.462GHz）。
> 36 附近与它们重叠较少，属于相对"干净"的频点。
> 但周围如果有一堆 WiFi，还是可能被干扰——这也是**跳频**存在的原因。

### 4.3（原"跳频"一节，已按代码事实更正）

**定义**：不断切换信道发送，避开被干扰的频点。

**比方**：两个人约定"每隔一句话换个频道说"，偷听者跟不上。

**你工程里的实际行为（这里我一开始判断错了，已核实更正）**：

```c
/* user/main.c:81 —— 候选信道表的初值 */
uint8_t ch_change_arr[2] = {36,36};

/* user/main.c:265 —— 进入对码循环【之前】，第 2 个元素被改掉了！ */
ch_change_arr[1] = pair_data.rf_ch;
```
对码循环里每 500ms 在这两个元素间交替：
```c
/* user/main.c 对码循环内 */
if(HAL_GetTick()-ch_change_time>500) {
    ch_change_count = !ch_change_count;
    bsp_pn298_set_channel(ch_change_arr[ch_change_count]);
    ch_change_time = HAL_GetTick();
}
```

**结论（更正）**：
- `ch_change_arr[1]` 在对码前被赋值成 **Flash 里存过的信道 `pair_data.rf_ch`**；
- 所以只要**以前对过码**（Flash 里有值），这段代码就是**真的在"信道 36"与"上次的信道"之间每 500ms 交替扫描** —— **它确实在跳频**；
- 只有当**从未对过码**（Flash 为 0xFF）时，两个元素才都是 36，表现为"原地重设同一信道"。

> **⚠ 但代码注释写的是"两个元素都是 36，实际不换频，但代码结构保留了跳频能力"——
> 这个注释是错的**（它只看了初值，没注意到 `main.c:265` 的覆盖）。
> 这正好是一个"注释不可信、要以代码为准"的实例。
> 读这类扫描逻辑时，一定要往**进入循环之前**多看几行，看初值有没有被改过。

### 4.4 地址（Address / Pipe）

**定义**：射频包的"收件人暗号"。只有地址匹配的接收方才理会这个包。

**比方**：信封上的收件人姓名。名字不对，你就不拆。

**你工程里的实例**：
```c
/* 5 字节地址，来自对码时遥控器发过来的 paircode */
uint8_t pair_addr_arr[5];        /* user/deal_pack.c 定义 */
...
extern uint8_t pair_addr_arr[];  /* user/main.c、bsp_pn298.c 声明 */
/* 初始化时写进 RX_ADDR_P0，这样飞机只认这一台遥控器 */
```
**"多机同场"问题**：如果两台飞机用同一个地址，就会互相串控。
所以对码时要交换一个唯一的 5 字节地址（通常含芯片 ID 或随机数）。

### 4.5 数据包（Packet）与载荷（Payload）

**定义**：一次无线传输的完整数据结构。
**Payload（载荷）** = 包里"真正要传的数据"部分（不含包头/校验）。

**比方**：快递 = Packet，包裹里的东西 = Payload，面单上的信息 = 包头。

**你工程里的 payload 结构（12 字节）**：
```
字节 0     : 帧头（0xAA = 正常数据包；0xDB = 对码包）
字节 1     : device_ID（本机设备号，用于二次过滤）
字节 2~3   : 通道 0 = 横滚（大端：高字节在前）
字节 4~5   : 通道 1 = 俯仰
字节 6~7   : 通道 2 = 油门
字节 8~9   : 通道 3 = 偏航
字节 10    : 按键位（一个字节装 6 个按键，用 union+位域拆）
字节 11    : 翻滚方向（低 4 位）
```
**"大端"（Big-Endian）**：高位字节在前。
16 位数据 `0x1234` 先发 `0x12` 再发 `0x34`。
组装代码：
```c
ch_value[i] = ((uint16_t)rx_buff[index] << 8) | ((uint16_t)(rx_buff[index+1]));
/*            高字节左移 8 位            或上 低字节                     */
```
> **Cortex-M 内部是小端**，但无线/网络协议惯例是大端。
> 所以收发两端都要显式"拼/拆"字节，不能直接把内存里的多字节变量丢过去。

### 4.6 ACK（应答）、自动重传（Auto Retransmit）

**定义**：
- **ACK**：接收方收到包后自动回一个确认包，发送方据此知道"送到了"。
- **ARD / ARC**：自动重传的**间隔**（Auto Retransmit Delay）和**次数**（Auto Retransmit Count）。

**比方**：ACK = 对方说"收到"；重传 = 你没听到"收到"就再说一遍。

**为什么必须开**：2.4GHz 环境干扰多，单次发送成功率不是 100%。
不做确认和重传，遥控指令就会丢，表现为"偶尔不响应"。

**你工程里的实例**：
```c
/* bsp_pn298.c 的 set_mode 里配置 SETUP_RETR(0x04) = 0x03 */
/* 这个值的含义曾经有歧义（作者注释写"若失败不自动重传"），
 * 现已查《PN298 用户手册 V1.0》第 33 页确认：
 *     04  SETUP_RETR  7:0  默认 0x03   自动传输设置
 *           ARD 7:4 = 0000 → 自动传输延时 250µs
 *           ARC 3:0 = 0011 → 自动传输次数 3 次
 * 写成 0x03 = ARD 0、ARC 3，即"失败后每 250µs 重传一次、最多 3 次"。
 * → 作者注释是错的，实际是"重传 3 次"，对 ACK 可靠性有利。 */
```

### 4.7 收发模式与 CE 引脚

**定义**：射频芯片有"发射/接收"两种模式，用 **CE（Chip Enable）**引脚切换。

**比方**：对讲机上的"按住说话"按钮——按住是发射，松开是接收。

**你工程里的实例**：
```c
/* 典型的模式切换：改 CONFIG 寄存器的 bit0（PRIM_RX） */
temp |= 0x01;      /* 进接收模式 */
temp &= ~(0x01);   /* 进发送模式（清掉 PRIM_RX） */
```
**时序要点**：CE 拉高/拉低之后要**等一小段时间**模式才真正生效（芯片内部要起振、稳定）。
所以你会在代码里看到 `delay_us(20)`、`delay_us(200)` 这类等待。

> **你工程里一个已知的不精确处**（`drivers/bsp/bsp_delay.c` 与 `bsp_delay.h`）：
> - `delay_ms(x)` 按 7980 次循环凑 1ms，与 48MHz 吻合，**是准的**；
> - `delay_us(x)` 用 `x<<4`（16 次循环/微秒）标定，实际**约为请求值的 2 倍**，
>   另加约 30~40µs 固定开销。
> 这在射频时序里反而"歪打正着"——延时宁长勿短，链路仍能工作。
> 但如果哪天需要精确定时，应该改用 TIM16 的 `micros16()` 来等。

### 4.8 软件模拟 SPI（Bit-Banging）

**定义**：不用硬件 SPI 外设，而是**用普通 GPIO 手动翻转时钟和数据线**来模拟 SPI 时序。

**比方**：硬件 SPI = 自动挡；软件 SPI = 手动挡，你自己控制每一次换挡时机。

**为什么需要**：有些芯片的 SPI 时序不标准（比如要求 CS 拉低后延迟特定时间、
或时钟空闲电平特殊），硬件 SPI 外设无法满足。射频芯片经常是这种情况。

**你工程里的实例**：`drivers/bsp/bsp_rfspi_sw.c` 就是干这个的。
代价是**慢且吃 CPU**（每次翻转都要几条指令），而且**必须在中断外或极短时间内完成**。

## 5. 看门狗（Watchdog, WDG）

### 5.1 定义

**一个独立运行的倒计时器：如果程序在超时前没有"喂"它，它就强制复位整个单片机。**

**比方**：一个定时炸弹，你必须每隔一段时间按一下"解除"按钮。
如果你卡住了（程序跑飞、死循环），按不了按钮 → 炸弹爆炸 → 设备重启。

**为什么必须有**：飞控如果卡死，飞机会失控坠落。看门狗是**最后一道防线**：
宁可重启（重启后电机停转、飞机掉下来但不会飞走），也不要带着错误状态继续飞。

### 5.2 两种看门狗

| 类型 | 全称 | 特点 | 你工程里 |
| --- | --- | --- | --- |
| **IWDG** | Independent WDG（独立看门狗） | 用**独立的 LSI 时钟**（约 32kHz），主时钟坏了它照样工作。**一旦启动无法关闭** | ✅ 本工程用这个 |
| **WWDG** | Window WDG（窗口看门狗） | 用主时钟。必须在**一个时间窗口内**喂狗：太早喂也算错！（防止程序跑太快跳过关键逻辑） | 见 `py32f0xx_hal_conf.h` 的使能宏 |

### 5.3 超时时间怎么算

```
超时 = 预分频系数 × 重装载值 ÷ LSI时钟频率
```

**你工程里的实际配置**（`user/WDG.c`）：
```c
IwdgHandle.Instance      = IWDG;
IwdgHandle.Init.Prescaler = IWDG_PRESCALER_32;   /* 预分频 32 */
IwdgHandle.Init.Reload    = (512);               /* 重装载 512 */
```
代入公式（LSI = **32768Hz**，已由数据手册确认）：
```
超时 = 32 × 512 ÷ 32768 = 16384 / 32768 = 0.5 秒（精确值 0.5s）
```

**LSI 频率的来源**（工程定义 + 数据手册双重确认）：
```c
/* user/py32f0xx_hal_conf.h:139 */
#define LSI_VALUE               ((uint32_t)32768)    /*!< LSI Typical Value in Hz */
```
《PY32F030 datasheet Rev.1.4》第 1 页产品特性也明确写着：
> — 内部 **32.768KHz** RC 振荡器(LSI)

**LSI 的实际精度（数据手册表 6-16）—— 这决定看门狗的余量**：

| 参数 | 条件 | 偏差 |
| --- | --- | --- |
| fLSI 频率 | TA=25°C, VCC=3.3V | **±3%** |
| 频率温度漂移 | VCC=1.6~5.5V，TJ=0~85°C | **±10%** |
| 频率温度漂移 | VCC=1.6~5.5V，TJ=−40~85°C | **±20%** |

所以实际超时时间：
```
常温：     0.5s × (1 ± 3%)   ≈ 0.485 ~ 0.515 秒
全温区：   0.5s × (1 ± 20%)  ≈ 0.40  ~ 0.60  秒
```
而喂狗周期约 101ms，所以**最坏情况下仍有 4 倍余量**（0.4s / 101ms ≈ 4）。

> **这修正了一个常见误解**：很多人以为内部 RC 振荡器精度很差（±50% 那种）。
> 这颗芯片的 LSI 在常温下只有 ±3%，全温区 ±20% —— 对手表、看门狗这类应用足够。
> **但绝不能用它做精确计时**（比如串口波特率），那需要外部晶振。
> 想测真实值，只能实测（写一个"只喂一次狗然后死循环"的程序，用串口计时看多久复位）。

**为什么选 0.5 秒**：主循环每约 100ms 喂一次狗，0.5s 给了 **5 倍余量**。
余量太小（比如 120ms）会因为偶发的长任务误复位；
余量太大（比如 10s）则卡死后要等很久才恢复，飞机已经掉下来了。

> **发现一处注释与代码不一致**（只记录，未改动）：
> `WDG.c` 里原作者注释写的是"Set IWDG counter reload value to 1024, 1s"，
> 而代码实际值是 `512`、约 0.5 秒。疑似改过参数没同步改注释。
> **读代码时以代码为准，不要相信注释里的数字。**

### 5.4 喂狗位置的选择——这里有个大坑

**你工程里的实例**：
```c
/* user/main.c 主循环 —— 真正的喂狗位置 */
if(_cnt100ms >= 100)
{
    _cnt100ms = 0;
    HAL_IWDG_Refresh(&IwdgHandle);   //喂狗
    Led_Process();                   /* 灯语刷新 */
}
```

**⚠ 大坑**：**绝对不要在主循环以外的地方喂狗**，尤其不要在定时器中断里喂。

**为什么**：中断是由硬件独立触发的。就算主循环**彻底卡死**（比如某个 `while` 死等），
中断依然会照常发生。如果在中断里喂狗，看门狗就永远不会触发——
**你花钱买的安全网，被自己剪断了**。

**正确的判断标准**：喂狗的位置必须是"**只有程序正常推进时才会执行到**"的地方。
主循环末尾（或主循环里某个必须经过的分支）就是标准答案。

> **反面教材在你工程里是存在的**（只记录未改动）：
> `bsp_pn298_tx_data()` / `tx_data_ack()` 里有
> `while(!(状态 & TX_DS_FLAG));` 这种**无超时的死等**。
> 对端不在时会卡死主循环 —— 这时**全靠看门狗复位来救**。
> 这也反过来说明：喂狗点选在主循环是对的，否则这里卡死就没人救了。

## 6. 对码 / 配对（Pairing）

### 6.1 为什么需要"对码"

射频通信需要三个约定：**信道（频点）、地址（暗号）、速率、地址宽度**。
两台设备必须完全一致才能通信。

**如果写死**：所有人的飞机都用一个地址 → 同一个场地多台飞机就互相串控，
而且旁边有人用同款遥控器就能控制你的飞机。

**如果对码**：遥控器和飞机现场协商一组地址，写进各自的 Flash。
既解决多机冲突，又带有"只有配过对的遥控器才能控制"的安全性。

**比方**：对码 = 蓝牙配对。不配对连不上，配过之后就记住了。

### 6.2 对码流程（你工程里的实际逻辑）

```
【遥控器侧】按对码键
   ↓ 发"对码包"：send_pn298_pack[0]=0xDB（0xDB = 对码帧头，区别于 0xAA 数据帧）
   ↓ 包里带上自己的 paircode[5]（5 字节地址）和 device_id
【飞控侧】开机后进入对码循环，等待 0xDB 包
   ↓ 收到后把地址存进 pair_addr_arr[5]，写进射频芯片的 RX_ADDR_P0
   ↓ 同时把整个参数结构写进 Flash 最后一页（0x0800F000）
   ↓ 点亮 LED 提示"对码成功"，退出对码循环，进入正常飞行模式
【之后】飞机只认这个地址的包，其他遥控器的包直接丢弃
```

**你工程里的关键代码位置**：
| 环节 | 位置 |
| --- | --- |
| 飞控开机对码循环 | `user/main.c` 的 `while(1)`（对码阶段，`main.c:279`） |
| 帧头区分（0xAA 数据 / 0xDB 对码） | `user/deal_pack.c:154` 与 `:274` |
| 地址存取 | `pair_addr_arr[5]`、`pair_data.paircode[5]` |
| 存储结构 | `user/flash.h` 的 `Pair_Code_Config`（内存布局 = Flash 格式） |
| Flash 地址 | `FLASH_USER_START_ADDR = 0x800F000`（64KB 的最后一页） |
| 跳出对码循环的标志 | `pair_over_flag`（RAM 标志，`deal_pack.c:82`） |
| 收到正常包也置对码标志 | `user/deal_pack.c:155`（含义是"通信链路已建立"） |

> **⚠ 一个必须澄清的点：`Pair_Code_Config.pairflag` 是"死字段"。**
> `flash.h:111` 声明了 `uint16_t pairflag;` 并注释"是否第一次写入"，
> 但**全工程没有任何一处代码读它或写它**（我逐文件搜过，只在注释和文档里出现）。
> 所以：
> - **"是否已配对"不是靠 pairflag 判断的**；
> - 实际表达"通信已建立"的是 **`pair_over_flag`（RAM 里的标志）**，
>   以及 Flash 里 `paircode`/`device_id` 是否为 0xFF（隐式表达）。
> 文档和注释里若写"pairflag 标记为已配对"，那是**设计意图**，不是代码事实。
> 这又是一个"注释/字段名会误导人"的例子。

### 6.3 "对码循环"为什么是 `while(1)`

```c
/* user/main.c 结构（示意） */
while(1) {                       /* ← 对码循环：一直等到对码成功才出去 */
    Led_Process();               /* 灯语提示"正在等待对码" */
    if (收到 0xDB 对码包) {
        /* 存地址、写 Flash、亮灯 */
        break;                   /* ← 跳出对码循环 */
    }
}
/* ...进入正常飞行主循环... */
```
**理解要点**：这是一个**阻塞式状态**。
飞机在对码期间**不做任何飞行控制**（因为还没有可用的遥控链路）。
所以放在这里死等是合理的 —— 但**必须保证看门狗不被饿死**，
或者对码期间干脆不启动看门狗。

> **读代码时的检查点**：对码循环里如果既没有喂狗、看门狗又已经启动，
> 那么对码超过看门狗超时时间就会不断复位，表现为"对码对不上、灯一直闪"。
> 这类问题排查时，要同时看**对码循环**和**看门狗启动时机**。

### 6.4 跳频与对码的关系

对码阶段常常顺便做**频点扫描**：在几个候选信道上轮流发对码包，
找到一个能通的就定下来。这样能避开被占用的频点。

**你工程里的现状**：`ch_change_arr[2] = {36, 36}` —— 两个值相同，
所以实际上**没有扫描**（见 4.3 节）。这不算 bug（功能仍能用），
但如果现场干扰严重，扫描两个不同频点会明显更可靠。

## 7. 心跳、软定时器、失联保护

### 7.1 心跳（Heartbeat）

**定义**：周期性的信号，用来证明"我还活着、还在正常工作"。
在飞控里有两层含义，**别搞混**：

| 层面 | 含义 | 你工程里的地方 |
| --- | --- | --- |
| **硬件心跳** | 定时器每 1ms 产生的中断，是整个系统的时间基准 | TIM17 的 1ms 中断 |
| **通信心跳** | 遥控器周期性发数据包，飞机据此判断链路是否还在 | 数据帧头 0xAA 的正常包 |
| **视觉心跳** | LED 周期性闪烁，给用户看"工作正常" | `user/led.c` 的 `Led_Process()` |

### 7.2 软定时器（Soft Timer）

**定义**：**用"计数中断次数"来实现多个不同周期的任务**，
而不必为每个周期单独占用一个硬件定时器。

**比方**：你只有一块表（1ms 心跳），但你要做"每 10ms 收一次信""每 100ms 喂一次狗"。
你就在纸上记：收到 1 次划一道，划满 10 道就收信。

**你工程里的实例**（这是理解主循环结构的钥匙，取自 `user/main.c` 与 `drivers/bsp/bsp_timer.c`）：

| 计数器 | 类型 | 中断里怎么加 | 主循环里怎么用 | 实际周期 | 做的事 |
| --- | --- | --- | --- | --- | --- |
| `_cnt4ms` | `uint8_t` | 每 1ms +1 | `if(_cnt4ms >= 4)` → 清零 | ≈5ms | 翻滚状态机 `Mode_Controler()` |
| `_cnt10ms` | `uint8_t` | 每 1ms +1 | `if(_cnt10ms >= 10)` → 清零 | ≈11ms | 收遥控数据 `decode_pack()` + 按键解释 `annexCode()` |
| `_cnt100ms` | `uint8_t` | 每 1ms +1 | `if(_cnt100ms >= 100)` → 清零 | ≈101ms | **喂狗** `HAL_IWDG_Refresh()` + 灯语 `Led_Process()` |
| `_cnt1s` | `uint16_t` | 每 1ms +1 | `if(_cnt1s >= 1000)` → 清零 | ≈1.001s | 电池电压检测 `get_voltage()` |
| `_cnt20ms` | `uint8_t` | 中断内 `if(++_cnt20ms >= 20)` 自清 | **不加到主循环** | 20ms | 在中断里直接给 `calibrationEnbTimer`、`powerupTimer` 提供节拍 |
| `baroUpdateTimer` | — | 每 1ms +1 | 由 `altitude.c` / `common.c` 内部读 | 1ms 基数 | 气压计更新节奏 |
| `altitudeCtrlTimer` | — | 每 1ms +1 | 由高度环内部读 | 1ms 基数 | 高度控制节奏 |

**中断里的原文**（`bsp_timer.c`，极短）：
```c
if (htim->Instance == TIM17) {
    static uint8_t _cnt20ms;
    baroUpdateTimer++;
    altitudeCtrlTimer++;
    _cnt10ms++;
    _cnt4ms++;
    _cnt100ms++;
    _cnt1s++;
    if(++_cnt20ms >= 20) {          /* 20ms 分频，注意是 ++ 前缀自增 */
        _cnt20ms = 0;
        calibrationEnbTimer++;      //校准时间
        powerupTimer++;
    }
}
```

> **注意"实际周期是 N+1 ms"**：因为判断和清零的顺序，
> `if(_cnt4ms >= 4) { _cnt4ms = 0; ... }` 实际是第 5 次中断才触发。
> 工程注释自己也承认了这点（`main.c`：
> "_cnt4ms>=4 实际约 5ms、_cnt100ms>=100 实际约 101ms、_cnt1s>=1000 实际约 1.001s"）。
> 对灯语、喂狗这类任务无所谓；**但这也正是 `flip.c` 里 `dt` 按"两次调用间隔"实测取值、
> 而不是写死 4ms 的原因** —— 时间敏感的地方要实测，不要假设。

> **为什么不全用硬件定时器**：芯片只有有限的定时器（TIM1/16/17 等）。
> 用软定时器，一个硬件 1ms 中断就能"虚拟"出任意多个周期任务 —— 这是标准做法。

### 7.3 失联保护 / 失控保护（Failsafe）

**定义**：当飞机检测到"一段时间没收到遥控数据"时，主动采取安全动作
（通常是**降低油门/停转电机/自动降落**），避免飞机飞走或伤人。

**为什么必须做**：遥控器没电、超出距离、天线被挡住 → 数据断了。
如果飞机继续按最后的油门飞，就会飞走（"放风筝"）。

**你工程里的实例**（⚠ 注意实际阈值是 **5 秒**，不是 1 秒）：
```c
/* user/main.c —— 用 HAL_GetTick() 做毫秒级超时判断 */
if (HAL_GetTick() - connection_nowtime > 5000) {   /* 超过 5000ms 没收到合法包 */
    /* ...失联处理... */
}
```
其中 `connection_nowtime` 只在**解析出合法数据包**时被刷新：
```c
/* user/deal_pack.c 的 decode_pack() 里 */
connection_nowtime = HAL_GetTick();
```
**这个细节很关键**：判据不是"收到任意字节"，而是"收到**校验通过的完整包**"。
收到噪声字节不算，所以不会因为干扰而误判为"链路正常"。

**读代码时的检查点**：
1. 超时阈值是多少（这里是 **5000ms = 5 秒**，对飞控来说偏长，
   意味着遥控器关掉后飞机还会按最后指令飞 5 秒 —— 值得你评估是否符合预期）；
2. 触发后具体做什么（闪灯只是提示，关键是有没有**动油门**）；
3. 恢复通信后能不能自动解除（否则一次干扰就永久告警）。

> **`HAL_GetTick()` 相减写法的坑**：它内部是 32 位毫秒计数，
> 约 49.7 天回绕一次。`当前 - 上次` 用无符号相减，只要间隔小于 49 天结果就是对的 ——
> **不要改成 `if (now > last + 1000)`**，那样回绕瞬间会失效。

## 8. 传感器、姿态、滤波、姿态解算

### 8.1 IMU（惯性测量单元）

**定义**：把**加速度计 + 陀螺仪**（有时还有磁力计）封装在一起的芯片。
本工程用 **ICM42688**（6 轴：3 轴加速度 + 3 轴陀螺仪，无磁力计）。

| 传感器 | 测什么 | 单位的直观理解 | 优缺点 |
| --- | --- | --- | --- |
| **加速度计** | 加速度（含重力） | 静止水平时 Z 轴 ≈ 1g | 长期准（不会漂），但**噪声大、对振动敏感** |
| **陀螺仪** | 角速度（转多快） | 单位 °/s | 短期准、响应快，但**积分会漂移** |

**关键洞察**：两者互补！
- 陀螺仪积分得到角度，短期准、长期漂（几分钟就漂几十度）；
- 加速度计能算出绝对倾角，长期准、短期抖。
→ 所以要把两者**融合**（见 8.3）。

### 8.2 量程、分辨率、零偏、校准

| 术语 | 含义 | 你工程里的体现 |
| --- | --- | --- |
| **量程 / FSR**（Full Scale Range） | 传感器能测的最大值。选小了会饱和削顶，选大了分辨率变差 | `accgyro.c` / ICM42688 配置 |
| **分辨率 / LSB** | 每个数字量对应的物理量。**本工程是 ±8g 档 → `acc_1G = 4096`**（即 4096 LSB/g，`imu/accgyro.c:35`）；陀螺是 ±2000dps → **16.4 LSB/(°/s)**（`accgyro.c:36`） | 换算原始值 → 物理量 |
| **零偏（Bias / Offset）** | 静止时输出不为 0 的那部分。陀螺仪零偏会让角度持续漂移 | `accRaw_offset[]`、`gyroRaw_offset[]` |
| **校准（Calibration）** | 测量并记录零偏，之后从原始值里减掉 | `accgyro.c` 的校准流程、`fc.flags.bAccGyroCalibrationEnb` |
| **噪声密度** | 传感器本底噪声，决定滤波参数怎么选 | 决定了 PT1/双二阶滤波器的截止频率 |

**校准的物理前提**：校准时飞机必须**静止且水平**。
所以代码里要先判断"是否静止"（看陀螺仪输出是否足够小），
静止判定阈值就是个典型的"魔法数字"：
```c
#define GYRO_CALI_DIFF_LIMIT    50      /* imu/accgyro.c:222 —— 代码里这一行原本没有注释 */
```

### 8.3 姿态解算（Attitude Estimation）

**定义**：把传感器原始数据变成**姿态角**（俯仰/横滚/偏航）的过程。

**你工程里用的算法**：**Mahony 互补滤波**（`imu/imu.c` 的 `imuMahonyAHRSupdate`）。
原理一句话：**用加速度计"慢慢纠正"陀螺仪的漂移**。

```
陀螺仪积分 → 得到角度（快，但会漂）
加速度计   → 算出重力方向（慢，但不会漂）
两者做差 → 得到一个"误差" → 用这个误差去修正陀螺仪的积分
```

**四元数（Quaternion）**：姿态的数学表示法，用 4 个数 (w,x,y,z) 表示旋转。
**为什么不用欧拉角**：欧拉角在俯仰 ±90° 附近有**万向节死锁**（gimbal lock），
数学上会退化；四元数没有这个问题，且计算量小（无三角函数）。
**欧拉角**：最终给人看的"俯仰/横滚/偏航"角度。**注意它是由旋转矩阵 `rMat` 算出来的**，
不是直接由四元数换算：`imuUpdateEulerAngles()`（`imu/imu.c:372-387`）用的是
`atan2_approx(rMat[2][1], rMat[2][2])` 这类式子。
（`imu.c` 里另有一个 `to_euler()`（`:161-185`）确实做四元数→欧拉角，
但它只被内部使用，**不产生全局 `angle[]`**。）
全局 `angle[]` 的单位是"度×100"（`imu/imu.h:48`）。

### 8.4 滤波（Filter）

**定义**：去掉信号里的噪声。飞控里滤波是**能不能飞稳**的关键。

**为什么必须滤**：PID 的 D 项（微分）对噪声极其敏感，
一点噪声经过微分就被放大成电机的高频抖动 → 飞机嗡嗡响、电机发热。

| 滤波器 | 特点 | 你工程里的地方 |
| --- | --- | --- |
| **PT1 一阶低通** | 简单、快、相位滞后小 | `imu/filter.c` 的 `pt1FilterApply()`，用于陀螺仪 |
| **双二阶（Biquad）** | 衰减陡（-40dB/十倍频），可做陷波 | `biquadFilterApply()`，用于加速度计 |
| **陷波（Notch）** | 只掐掉某个窄频段（如电机转速对应的振动） | ⚠ **本工程实现了但没在用**：`FILTER_NOTCH` 分支存在（`imu/filter.c:160-169`），但**全工程没有任何调用者**；唯一的 biquad 初始化点是 `biquadFilterInitLPF(&accFilter[axis], 30, 1250)`（`accgyro.c:71`，固定低通 30Hz） |
| **中值滤波** | 取中间值，抗突发野值 | `mlib.c` 的 `quickMedianFilter3/5/7`，用于气压计 |

**截止频率（Cutoff Frequency）**：低于它通过、高于它衰减。
选大了噪声滤不干净，选小了响应变慢（相位滞后）→ 飞机"发飘"。
这是**调参的核心取舍**。

### 8.5 气压计与定高

**定义**：气压计测大气压，气压随高度降低 → 反推高度。
**你工程里**：BMP390（`user/bmp3.c`）+ `imu/altitude.c` 的高度解算。

**为什么用国际标准大气模型**：气压 → 高度不是线性的，标准公式是
```
高度 = 44330000 × (1 - (P / 101325)^0.190295)   /* 单位毫米 */
```
你工程里的实现（注意这里用了**自研的窄区间幂函数**替代 `powf`，
因为链接 `powf` 会带入 4KB+ 的 libm 代码，Flash 装不下）：
```c
/* imu/altitude.c */
baroGroundAltitude = (1.0f - baro_pow_0p295((baroGroundPressure / 10.0f) / 101325.0f)) * 44330000.0f; //in mm
```

**定高的控制结构**：注意这里有**两条独立的串级**，不是一条嵌套的（容易看错）：

- **高度通道**：位置环 → 速度环（`imu/altitude.c:312` → `:367`）
- **姿态通道**：角度环 → 角速度环（`imu/pid.c:259` → `:304`）

两者在混控 `PIDMIX`（`pid.c:118-127`）处**相加**，而不是谁套在谁里面。
```
目标高度 ─[高度环 PID]→ 目标垂直速度 ─→ 油门修正量(BaroPID)
                                              ↓
遥控器摇杆 ─────────────────────────→ PIDMIX 里叠加到 1500 中位油门上
```
你工程里 `altitude_mode` 决定用哪种油门基准（手动 1500+BaroPID / 定高用摇杆值）。

> **气压计的固有难点**：气流、开关舱盖、手挡住都会让气压突变。
> 所以要**中值滤波去野值** + 低通滤波平滑，而且要用"起飞点气压作为基准"
> （`baroGroundPressure`），算**相对高度**而不是绝对海拔。

### 11.6 写《飞控技术演进总纲》时又查出的一批（第三批）

**A. 🔴 最重要的一条：控制环不在 1ms 中断里，而在主循环**

这是**理解整个工程时序的关键**，之前手册和相关注释都写错了。

| 原来的说法 | 代码事实 |
| --- | --- |
| "`flight_ctrl()` 每 1 毫秒执行一次，由 TIM17 的 1ms 更新中断调用" | **唯一调用点是 `user/main.c:410`，在主循环里** |
| "TIM17 中断 → flight_ctrl()" | TIM17 中断回调（`drivers/bsp/bsp_timer.c:168-194`）**只做计数器自增**，不调用任何控制函数 |

**核实依据**：
1. 全工程搜 `flight_ctrl` 的非注释调用点，只有 `user/main.c:410` 一处；
2. `bsp_timer.c:48-51` 自己写着"中断里调用 `flight_ctrl()` 这类耗时函数会破坏 1ms 节拍"
   —— 说明设计上就没打算放中断里；
3. `main.c:410` 的注释本身就标了耗时 **2.493ms~3.446ms**，紧邻的
   `altitude_ctrl()`（`main.c:407`）标 **2.1ms~3.873ms**
   ⇒ **主循环一圈约 4.6ms 量级**，控制环频率远低于 1kHz。

> **为什么这条重要**：1ms 是**时基与计数器**的节拍，不是控制环周期。
> 把两者混淆，会导致对"PID 该按多快调"、"滤波器系数按什么采样率算"、
> "失联判据为什么用 5 秒"这些问题的判断全线偏移。
> （`imu/fc.c:82` 的 `deltaT >= 0.00125f` 是个**下限门槛**，不是实际周期。）

**已修正的错误注释**（只改注释，代码未动）：`imu/fc.c:6`、`imu/fc.c:10`、
`imu/fc.h:10`、`imu/pid.c:28`、`imu/pid.c:46`、`imu/pid.c:166`、`imu/pid.h:48`。

**B. 电机 PWM 的规格写成了通用电调标准**

| --- | --- |
| "**本工程是 16kHz 固定频率 + 0~1000 千分比占空比**（不是 1000~2000µs 的舵机信号）" | 本工程是 **16kHz 固定频率 + 0~1000 千分比占空比** |

**D. 一个被漏收的时钟错误**

`drivers/bsp/bsp_pwm.c:33`、`:69-70` 的注释也写成 **"PCLK1 = 24MHz"**，
与 `user/main.c:166` 的 `RCC_HCLK_DIV1`（实际 **48MHz**）矛盾。
11.1 节的纠错表原先漏了这个文件，现已补上。

**E. 软定时器那条要补一个同量级因素**

7.2 节写的"实际周期是 N+1 ms"**是对的**，但漏了一句：
**主循环一圈本身就要 4.6ms 量级**，所以任何挂在主循环上的任务，
其真实抖动是"主循环周期"这个量级 —— 比 N+1 那个 +1 影响大得多。
换句话说：**软定时器的精度上限由主循环一圈的耗时决定**，不是由 1ms 时基决定。

遥控器板（`7420遥控器_V1.1.xlsx` BOM）也是同样格局：
**PAN742 + 16MHz 晶振 + 无 32.768kHz 晶振**，另有 2 个摇杆、8+2 个按键、蜂鸣器。

### 13.2 ⚠ **板上焊了 16MHz 晶振，但代码把 HSE 关掉了**

这是对照硬件后发现的**最值得注意的一处**：

```c
/* user/main.c 的 SystemClock_Config() —— 代码里明确关闭外部晶振 */
RCC_OscInitStruct.HSEState = RCC_HSE_OFF;                /* 本板无外部高速晶振 ← 【这句错了】 */
RCC_OscInitStruct.LSEState = RCC_LSE_OFF;                /* 无外部低速晶振 ← 这句是对的（板上确实没有 32.768kHz） */
```

**但硬件证据表明板上是有 16MHz 晶振的**：
- EasyEDA 元件清单里有 `xl7el89coi-111ylc-16m`，参数描述明确写"频率:16MHz;常温频差:±10ppm;负载电容:12pF"；
- 遥控器板的 BOM 也写着 `16MHz` / `X1` / `CRYSTAL-SMD_4P-L2.0-W1.6-BL`。

**如果要把 HSE 用起来，有三件事必须一起改（缺一不可）**：
1. `main.c`：`HSEState` 改成 `RCC_HSE_ON`；
2. `py32f0xx_hal_conf.h`：**`HSE_VALUE` 目前写的是 24000000（24MHz），而板上是 16MHz**
   —— 不改这个，HAL 算出来的分频/波特率全会错；
3. PLL 源可以改用 HSE（`RCC_PLLSOURCE_HSE`），这样系统时钟不再依赖内部 RC 的精度。

**为什么值得改**：现在系统时钟来自 **HSI（内部 RC）**，而内部 RC 的频率偏差
（datasheet 里 HSI 常温 ±1% 量级）会直接体现在**串口波特率**上 ——
115200 波特率下偏差过大会让某些 USB 转串口模块收到乱码。
换成外部 16MHz 晶振（±10ppm）就几乎没这个问题。

> **这是"只理解、先不改"的范围**：代码没动，仅记录。
> 如果你以后要动时钟，记得**先确认真实晶振频率**（板上丝印或 BOM），
> 再把 `HSE_VALUE` 和 `HSEState` 一起改 —— 只改一处会得到一个"看起来能跑但时序全错"的固件。
