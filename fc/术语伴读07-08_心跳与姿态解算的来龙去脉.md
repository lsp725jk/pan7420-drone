# 第 7 章　心跳、软定时器、失效保护

> **本章主线**：这三样东西解决的是同一个大问题的三个侧面 ——
> **"我怎么知道对方/自己还活着？"**
>
> - **心跳**：判断**别人**（遥控器）还活着 → 通信层的"生命体征"；
> - **软定时器**：判断**自己**的时间到了没有 → 一个时基撑起几十个周期任务；
> - **失效保护**：判断出"对方不在了"之后**怎么办** → 把"通信故障"翻译成"安全动作"。
>
> 三者的关系是**串联**的：心跳提供判据，软定时器提供计时，失效保护消费判据做出动作。缺任何一环，
> 另外两环都落不了地。

## 7.1 心跳（Heartbeat）

> **这一节回答什么问题**：接收方怎么知道"对方还在"，而不是"只是这一帧没收到"？

### ① 它是怎么出现的

🟡 **通说**：单向无线链路有一个绕不开的困境 —— 接收方**没有**任何直接手段确认发送方是否存活。
它手上只有一件事：**"到目前为止，还没有收到下一帧。"** 而这一件事至少有三种成因：

1. 发送方死了（没电、程序卡死、被关掉）；
2. 链路暂时断了（距离太远、被遮挡、天线朝向变了、同频干扰）；
3. 帧正在路上，还没到（正常延迟）。

🟢 **确证（本工程的通信前提）**：本工程用的是 PN298 这类 2.4GHz 无线收发芯片，
`_术语事实清单.md` 记明它支持**自动重传**（`SETUP_RETR` 默认 `ARD=250µs`、`ARC=3` 次重传，
超限产生 `MAX_RT` 中断；手册第 17、33 页），并且每包带 **2 位 PID**（Packet ID，包序号；手册第 19 页）用于识别重发包。
换句话说：**"这一帧没收到"这件事，射频芯片自己已经帮你区分了一部分** ——
重传 3 次仍然失败才会报 `MAX_RT`。但**它仍然无法回答"对方是死了还是暂时不通"**，
因为两种情况在芯片看来都是"没 ACK"。

→ 于是需要一个**主动的、周期性的、可被超时判定的**信号。这就是心跳。

### ② 它要解决什么问题（没有它会怎样）

心跳要解决的核心问题，用一句话说：

> **把"一次收不到"（不可判定）变成"连续 N 次收不到"（可判定）。**

要做到这个判定，链路两端必须**事先约定三件事**，缺一不可：

| 要素 | 作用 | 没有它会怎样 |
| --- | --- | --- |
| **周期 T**（多久发一次） | 给"连续"下一个定义 | 无法定义"多久算久"，只能永远等下去 |
| **接收方本地时钟** | 度量"已经过去多久" | 没有时间轴，就没有"超时"这个概念 |
| **阈值 N**（多少个 T） | 把"概率"翻译成"判决" | 阈值太短 → 丢一帧就报警；太长 → 危险窗口大 |

🟢 **确证（本工程的三个要素都齐）**：

- **周期 T**：遥控器由 TIM16 中断节拍驱动发包（`遥控器/user_driver/tim16.c:48-90`）；
- **本地时钟**：飞控侧用 `HAL_GetTick()`（SysTick 驱动的 1ms 毫秒计数，`main.c:462`），
  遥控器侧用 TIM16 的 1ms 中断计数（`遥控器/user_driver/tim16.c:76-87`）；
- **阈值 N**：飞控侧 5000、遥控器侧 1000（详见 7.3）。


**这张图要看出的一点**：情形 B 和情形 C 在**前几个周期里长得一模一样**。
心跳机制的全部意义，就是**用"连续 N 次"把两者分开**。
这与《第 5 章 看门狗》是同一类思路 —— 只不过看门狗判断的是"自己没卡死"，
心跳判断的是"别人还活着"。两者的对照见本节末尾的表 7-1-3。

#### 7.1.2 本工程的通信心跳是"隐式"的，而且带双向确认

🟢 **确证**：本工程**没有**单独的心跳包。心跳功能是**寄生在数据帧上的**：

- 遥控器每轮发一包 12 字节的遥控数据（帧头 `0xAA` + 设备 ID）；
- 飞控每收到一包就刷新一次时间戳（`deal_pack.c:257`）；
- **"一直有数据"本身就等价于"对方还活着"** —— 这叫**隐式心跳**（implicit heartbeat）。

🟢 **确证（本工程更值得注意的一点）**：这条链路**不是单向的**。
飞控收到包之后，会在射频芯片给的应答窗口里**回填一包 ACK 载荷**：

```c
/* drivers/bsp/bsp_pn298.c:1202-1206 —— 收包与回 ACK 在同一个函数里，顺序不能换 */
if(ack)
{
    bsp_pn298_write_reg(FLUSH_TX, 0);                     // 先清发送缓冲
    bsp_pn298_write_buf(W_ACK_PAYLOAD, ack_data, len);    // 把 ack_data 装进 ACK 载荷
}
delay_us(30);                                             // 留出"组织 ACK、切到发射"的时间
bsp_pn298_read_buf(R_RX_PAYLOAD, rx_data, len);           // 然后才读收到的包
```

而飞控传进去的 `ack_data` 就是 `temp_buff[]`（`user/deal_pack.c:148` 的第二个实参）。
于是这一包 ACK 同时干了两件事：

1. **告诉遥控器"飞机还在"** —— 遥控器只有拿到 ACK 才清零它的失联计时
   （`遥控器/user_driver/pn298/bsp_pn298.c:424-431`，看到 `RX_TX_FLAG` 就 `sign_timer_running = 0`）；
2. **顺便当遥测下行通道** —— 例如低电标志就搭这个车上传：
   `adc.c:245` 写 `temp_buff[1] = 2`，遥控器侧 `遥控器/user/user/main.c:243` 读 `ack_buff[0]==LOW_VOL` 就响蜂鸣器。

```text
图 3　一次心跳往返（一个"来回"里套了心跳 + 遥控 + 遥测三件事）

   遥控器                                          飞控
     │                                              │
     │  ① 发 12 字节遥控包（0xAA + device_ID + 通道值）│
     │ ────────────────────────────────────────────► │
     │                                              │ ② 帧头 + 设备 ID 双重校验
     │                                              │    （deal_pack.c:154）
     │                                              │ ③ 刷新 connection_nowtime
     │                                              │    （deal_pack.c:257）
     │  ④ ACK 载荷 = temp_buff[]（含低电标志）        │
     │ ◄──────────────────────────────────────────── │
     │                                              │
     ▼                                              │
   收到 ACK ⇒ sign_timer_running = 0                  │
   计时清零，信号正常                                  │
   （遥控器 bsp_pn298.c:429-431）                      │
     │                                              │
   收不到 ACK（MAX_RT）⇒ 启动 1ms 计时                 │
   （遥控器 bsp_pn298.c:451-457）                      │
```

**为什么这件事重要**：它把"心跳"从"我猜你还活着"升级成了"**你回了话，所以我确定你活着**"。
在通信工程里这叫**确认机制**（acknowledgement）。代价是：链路的可靠性现在取决于**双向**都通
（如果飞机能收、但回不去 ACK，遥控器会判失联 —— 而飞机自己认为一切正常）。
本工程两侧阈值差 5 倍（1000ms vs 5000ms），恰好给这种"单边通"留了缓冲：遥控器先报警，
飞机 5 秒后才动作。🟡 **通说（这条因果是我推的）**：代码里没有注释说明这是有意设计，
所以只当"效果上如此"，不当"设计意图"。

🟢 **确证（噪声不会冒充心跳）**：刷新时间戳的位置在**双重校验之后**（`deal_pack.c:154` 的
`rx_buff[0]==0xaa && rx_buff[1]==device_ID`），所以"收到噪声字节"**不算**收到心跳。
这一点手册 7.3 已强调过，这里补一句它的代价：**校验越严，误判失联的概率越高**
（比如旁边的遥控器用了同一个 device_ID，或者飞机换了遥控器但没重新对码）。

#### 7.1.3 心跳 ≠ 看门狗（最容易混的一对）

| | **看门狗（Watchdog）** | **心跳（Heartbeat）** |
| --- | --- | --- |
| 判断谁 | **自己**有没有卡死 | **对方**还在不在 |
| 谁在计时 | 硬件计数器（IWDG 由 LSI 驱动，事实清单：参考手册第 339 页） | 软件时间戳（`connection_nowtime`） |
| 触发后谁动手 | 硬件**复位芯片** | 软件执行**安全动作**（降落） |
| 本工程阈值 | 约 0.5 秒（事实清单：LSI 32768/32/512） | 5 秒（`main.c:462`） |
| 本工程的"喂"点 | `main.c:414` `HAL_IWDG_Refresh()`，每约 101ms 一次 | `deal_pack.c:257`，每收到一个合法包一次 |
| 失效的后果 | 芯片复位 → 电机停转 → 掉下来 | 自动降落 → 有机会软着陆 |

**记法**：看门狗是"**我要按时报到**"，心跳是"**你要按时出声**"。
两者在工程里是**互补**的：遥控器死了（对方问题）心跳管；主循环卡死了（自己问题）看门狗管。

### ④ 实现方法有哪些（取舍对照表）

**这一节回答什么问题**：想把"对方还活着"这件事判断出来，业界有哪几条路？本工程走的是哪条？

| 方案 | 怎么做的 | 优点 | 代价 / 什么情况下会骗你 | 本工程 |
| --- | --- | --- | --- | --- |
| **① 每帧都算心跳**（隐式心跳） | 不发专门的心跳包，把"收到数据帧"直接当心跳 | 零额外带宽、零额外代码；数据本身越密，判断越快 | ① 只有"有数据可发"时才有效 —— 对**空闲时不说话**的链路（如应答式、事件式协议）无效；② 数据停了就分不清"没话说"还是"人没了" | **✅ 本工程就是这个**（`deal_pack.c:257`） |
| **② 独立心跳包** | 固定周期发一个专门的短包，只表示"我在" | 语义清晰；与业务数据解耦（业务空闲也能证明存活）；可以做得比数据包更短更鲁棒 | 占用带宽；多一套包类型要维护；心跳周期与数据周期两套节拍 | ❌ 本工程没有独立心跳包 |
| **③ 序号 + 时间戳** | 每包带递增序号和/或发送时刻，接收方据此算丢包率和延迟 | 不仅能判生死，还能**量化链路质量**（丢包率、抖动）；能识别"乱序/重复" | 每包多几个字节；需要两端时钟关系（或只比差值）；序号回绕要处理 | 🟡 部分等价物：PN298 硬件层带 **2 位 PID**（事实清单：手册第 19 页）用于识别重发包；`OBSERVE_TX(08)` 有 `PLOS_CNT`/`ARC_CNT` 丢包与重传计数（手册第 35 页）—— **但飞控代码没有读它** |
| **④ 看门狗式**（只在"一段时间没数据"时报警） | 不做周期判定，只挂一个"最后收到时间"，超时就报警 | 实现最省；天然容忍抖动 | 报警时**已经晚了**（等于把 N 设成了唯一参数）；阈值必须拍一个数，拍不准就误报/漏报 | ✅ 本工程失效保护就是这个形态（`main.c:462`），但阈值取得较长（5s） |

**本工程的选择**：

- 用 **①（每帧都算）** 当心跳，因为遥控器本来就以 ~10ms 的节奏连续发包（见 7.3 的推算），
  数据流足够密，**没有必要再单独发心跳**；
- 用 **④（超时报警）** 当判据，因为动作是"降落"这种重量级操作，宁慢勿误；
- **③ 的能力被硬件免费提供了一部分**（**CRC**（Cyclic Redundancy Check，循环冗余校验）、扰码、PID、重传计数都在 PN298 里，事实清单第二节），
  但**固件没有消费这些统计量** —— 这是一处"想做得更好时可以从哪下手"的位置。

> **🟢 顺带一个可以自己验证的检查点**：`bsp_pn298_read_reg(OBSERVE_TX)` 就能拿到
> `PLOS_CNT`（丢包计数）和 `ARC_CNT`（重传计数）。如果将来要做"链路质量指示"，
> 这是最便宜的数据源 —— 不用改协议，只读一个寄存器。

### 7.1 小结（三句话）

1. 心跳要解决的是"**发送方死了**"与"**链路暂时断了**"无法区分的问题；
2. 区分手段是"**周期性信号 + 超时判定**"，三个要素：周期 T、本地时钟、阈值 N；
3. 本工程的心跳是**寄生在数据帧上的隐式心跳**，并且靠 **ACK 载荷**做了一次双向确认，
   顺带当遥测下行通道。

## 7.2 软定时器（Soft Timer）

> **这一节回答什么问题**：芯片只有有限几个硬件定时器，而程序有几十个不同周期的任务，
> 这个矛盾怎么解决？

### ① 它是怎么出现的

🟢 **确证（本工程的硬件现实）**：`_术语事实清单.md` 的"本工程的实际配置"表里，
这个 48MHz 的 PY32F030 已经用掉了四个定时器干四件完全不同的事：

| 定时器 | 分频/重载 | 实际频率 | 用途 |
| --- | --- | --- | --- |
| TIM16 | `/48` → 1MHz（不用中断） | 1µs 分辨率 | 自由计数器（给 `micros16()` 用） |
| TIM17 | `/480/100` → 1kHz | **1ms** | 整个飞控的控制节拍（心跳） |
| TIM3 | `/3/1000` | 16kHz | 四路电机 PWM（脉宽调制） |
| TIM1 | `/4/600` | 20kHz | RGB 灯 PWM |

而程序实际需要的**周期任务**有多少？看主循环就够了：

🟢 **确证（本机实测）**：`user/main.c:371-489` 的主循环里，按周期分派的任务至少有
**6 个不同节拍**：收遥控（~11ms）、空翻状态机（~5ms）、定高（每圈 + 20ms 高度环）、
姿态控制（每圈，内部再限 1.25ms）、喂狗+灯语（~101ms）、读电压（~1.001s），
再加上气压计自己的 ~25ms/5ms 两档节拍（`user/common.c:496/510/514/540`）。

**如果给每个周期任务配一个硬件定时器**：4 个任务就把芯片的定时器用光了，
而且每个定时器还要占一个中断向量、一段初始化代码、一份 NVIC（Nested Vectored Interrupt
Controller，嵌套向量中断控制器）优先级配置。**这就是软定时器出现的直接原因。**

### ② 它要解决什么问题（没有它会怎样）

> **软定时器的核心思想一句话：把"时间的度量"和"时间的消费"分开。**
>
> **一个**硬件时基负责"度量"（每 1ms 打一拍），**任意多个**软件计数值负责"消费"
> （每个任务自己数到几算到点）。

没有它会怎样？只有两条更难走的路：

| 替代方案 | 具体形态 | 为什么在本工程行不通 |
| --- | --- | --- |
| **中断里直接干活** | 每 1ms 在 TIM17 中断里把姿态解算、PID、串口打印全跑掉 | 🟢 `bsp_timer.c:48-51` 的注释写明理由：中断里跑耗时函数会**破坏 1ms 节拍**，而且功能函数会访问外设，与主循环**重入冲突** |
| **一个任务一个硬件定时器** | 收遥控用 TIM14、喂狗用 TIM15…… | 定时器数量不够（本工程已用 4 个）；中断优先级只有 4 级（事实清单：参考手册第 119 页），优先级不够分 |

### ③ 我该怎么理解它


**这个结构的三个要点**：

1. **中断短、主循环重**（🟢 `bsp_timer.c:48-51` 注释）：中断里只有自增；耗时的解析、
   控制、打印全在主循环。所以中断不会打乱节拍。
2. **任务天然串行**（🟢 `main.c:41-43` 注释）：因为都在一个 `while(1)` 里顺序执行，
   **不需要考虑重入和竞态**。代价是"任务耗时相加 = 最小循环周期"。
3. **优先级靠代码顺序**（🟢 `main.c:371-489`）：写在前面的分支先被检查。
   这跟 RTOS 的抢占式调度是两回事。

#### （c）"实际周期是 N+1 ms"是怎么来的（🟢 可自己验算）

```text
图 5　N+1 的由来：判断、清零、和"中断不会停"三者叠加

 时刻(ms)   0    1    2    3    4    5    6 ...
 中断       ↓    ↓    ↓    ↓    ↓    ↓    ↓      每 1ms 无条件 +1
 _cnt4ms    1    2    3    4    5→0  1    2
                 ▲         ▲
                 │         │
                 │         └─ 第 5 次中断：主循环这一圈看到 _cnt4ms==5
                 │            条件成立 → 清零 → 跑 Mode_Controler()
                 │            （注意：中断在这 1ms 内已经把 4 加成了 5）
                 └─ 第 4 次中断后 _cnt4ms==4，但主循环这一圈**还没轮到**
                    读它（或者读到时中断又加了一次）

 结论：`if(_cnt >= N) { _cnt = 0; ... }` 的实际周期是 (N+1) 个时基
       —— 不是代码写错，而是"清零发生在判断之后、而中断永不停止"的必然结果
```

🟢 **确证（工程自己也承认了）**：`main.c:365-367` 的注释原文写着
"_cnt4ms>=4 实际约 5ms、_cnt100ms>=100 实际约 101ms、_cnt1s>=1000 实际约 1.001s"。

🟢 **确证（这处偏差真的被下游处理了）**：`user/flip.c` 里的 `dt` 不是写死 4ms，
而是按"两次调用间隔"实测取值（`main.c:367` 注释明确指出这一点）。
**这是本工程里值得学的一处工程习惯：时间敏感的地方要实测，不要假设标称值。**

#### （d）为什么 `_cnt1s` 是 `uint16_t` 而其它是 `uint8_t`（🟢 可从回绕边界推出）

```text
图 6　计数器位宽与回绕边界（决定"选 uint8_t 还是 uint16_t"的唯一理由）

  uint8_t 上限 255：
   · _cnt10ms  需要数到 10+  → 只需 4 位，用 8 位很宽裕
   · _cnt4ms   需要数到 4+   → 只需 3 位
   · _cnt100ms 需要数到 100+ → 只需 7 位（余量 2.5 倍）

       —— "读电池电压"这个任务会彻底不执行，而且不报错）

   → 255 格 = 5.1 秒就回绕
   → 所以 calibrationEnbTimer / powerupTimer 只能用于"几秒内"的判断
```

#### （e）**这些计数器都不是 volatile**（🟢 本机实测，这是本节最该警惕的一条）

🟢 **确证**：`bsp_timer.c:113-116` 的定义里**没有** `volatile`；
`main.c:205-208` 的 `extern` 声明里也**没有**。`main.c:199-203` 与 `bsp_timer.c:83-96`
的注释都**主动承认了这一点**，并解释"为什么现在还能跑"：

> 主循环里是"**读一次、比较、然后赋值 0**"的写法（不是空转等待），
> 编译器没有机会做那种跨语句的缓存优化 —— 属于"**侥幸正确**"。

**风险场景（🟢 注释里点名的两种）**：

| 场景 | 会发生什么 |
| --- | --- |
| 把判断改成空转等待（如 `while(_cnt10ms < 10);`） | 编译器可能只读一次内存、缓存在寄存器里反复比较 → **死等**，中断改了也看不到 |
| 提高优化等级（GCC `-O2/-O3`、Keil `-O2`） | 同样的缓存优化可能被启用 → 代码逻辑完全正确但**不工作**，且极难查 |

🟢 **另一条同样重要的事实（`bsp_timer.c:99-109` 注释）**：**`volatile` 不保证原子性**。
`_cnt10ms++` 在 Cortex-M0+ 上是"读 → 加一 → 写回"三条指令；
如果主循环的 `_cnt10ms = 0`（`main.c:387`）恰好插在中断的"读"和"写回"之间，
中断加的那一次会被主循环的写回**覆盖**（丢失更新）。本工程靠"中断只加、主循环只清零"
这种**单向约定**侥幸避开，但这是**约定**不是**语言保证**。

```c
}
/* 三档阈值：触发测量后等 25（≈25ms）；等数据就绪时 1；读完再等 5 进下一轮
   —— common.c:496 / :510 / :514 / :540
   注释推算的测量周期 ≈ 25+5 ms（约 30~40Hz），对定高足够 */
```

**这演示了软定时器的一个进阶用法**：把"节拍值"变成**状态机的参数**，
就得到了一个"可变周期的软件定时器"，不需要动硬件。

### ④ 实现方法有哪些（取舍对照表）

**这一节回答什么问题**：除了"软件计数"，还有哪些做法？各自的代价是什么？

| 方案 | 怎么做的 | 优点 | 代价 | 适用规模 | 本工程 |
| --- | --- | --- | --- | --- | --- |
| **① 软件计数（本工程）** | 一个时基中断 + N 个全局计数值，主循环轮询阈值 | 代码最短、零额外 RAM、完全可预测（没有调度器） | ① 精度受主循环周期限制；② **忘记清零就永久失效**；③ 任务多了以后主循环变成一长串 `if`，可读性下降 | 几个 ~ 十几个周期任务 | **✅ `bsp_timer.c` + `main.c` 主循环** |
| **② 滴答链表（tick list）** | 每个待执行任务挂一个"到期时刻"，中断里只递减最近的一个 | 中断开销与任务数无关；经典 RTOS 做法 | 需要链表/有序插入的代码；插入删除要临界区保护 | 几十个任务 | ❌ |
| **③ 时间轮（timing wheel）** | 把"未来 N 拍"做成一个环形数组，中断只推进指针 | O(1) 插入与触发；任务数很大时仍然快 | 实现比链表更绕；需要处理"跨圈"任务 | 几百个以上 | ❌ |
| **④ RTOS 软件定时器** | 交给 RTOS 的定时器服务任务（如 FreeRTOS 的 `xTimerCreate`） | 有优先级、有阻塞/唤醒、API 规范 | 要引入 RTOS：内核占用 Flash/RAM（本工程 Flash 已用到 95%，`bsp_timer.c:110-111` 注释提到）；调度开销与不确定性 | 中大型项目 | ❌ 本工程是纯裸机超级循环 |
| **⑤ 硬件定时器阵列** | 一个任务一个硬件定时器/比较通道 | 精度最高（不受主循环影响）、可硬件触发 | 定时器数量硬限制；中断向量与优先级有限（事实清单：参考手册第 119 页，**4 个可编程优先级**） | 少数高精度需求 | 🟡 部分采用：真正需要"硬精度"的地方用了硬件 —— TIM17 做 1ms 时基、TIM16 做 1µs 自由计数、TIM1/TIM3 直接由硬件产生 PWM 波形 |

**本工程的取舍一句话**：**用一个 1ms 硬件时基 + N 个软件计数器，换掉 N-1 个硬件定时器；
代价是"周期不精确（N+1）"和"精度受主循环限制" —— 并且这个代价值得，
因为需要精度的三个场合（1ms 节拍、1µs 计时、PWM 波形）都已经用了硬件。**

### 7.2 小结

1. 软定时器解决的是"硬件定时器数量有限 vs 周期任务有几十个"的矛盾，
   办法是**一个时基扇出多个计数值**；
2. 代价是三条：**精度受主循环限制**、**实际周期是 N+1**、**忘记清零就永久失效**
   （本工程还有第四条：**没加 `volatile`**）；
3. 本工程的实测形态：`_cnt10ms/_cnt4ms/_cnt100ms`（`uint8_t`）与 `_cnt1s`（`uint16_t`）
   每 1ms 自增（`bsp_timer.c:113-116`、`:180-183`），主循环读阈值清零
   （`main.c:374/390/411/445`），**都不是 `volatile`**；
4. 位宽不是随便选的：`_cnt1s` 必须 16 位（8 位数不到 1000），`_cnt20ms` 因为 20ms 一格，
   8 位只能表示 5.1 秒，所以 `calibrationEnbTimer`/`powerupTimer` 不能当长时间计时用。

## 7.3 失效保护 / 失控保护（Failsafe）

> **这一节回答什么问题**：当判据说"失联"之后，飞机**应该做什么**？
> 以及**判据的阈值该取多长**？

### ① 它是怎么出现的

🟡 **通说**：遥控链路一定会断，只是迟早的问题。断的原因至少有四类：

1. **发射端没电**（遥控器电池耗尽、被误关）；
2. **超出距离**（2.4GHz 的视距链路，距离/遮挡一变就差很多）；
3. **环境遮挡/多径**（人体、树、建筑、机身碳纤维）；
4. **同频干扰**（2.4GHz **ISM**（Industrial, Scientific and Medical，工业/科学/医疗免许可）频段拥挤 —— 事实清单：PN298 在 2400~2483MHz，
   手册第 8 页，并且带 CRC + 自动扰码就是为这个场景准备的，手册第 9 页）。

**如果什么都不做**：飞控会**保持最后一次收到的舵量**继续输出。
这在"最后指令是悬停"时看起来没事，但只要最后一帧是"油门 60% 向前"，
飞机就会**沿着那个方向一直飞**直到撞上什么 —— 这就是俗称的"放风筝"。
🟡 **通说**：这是早期多旋翼最典型的一类事故原因。

→ 所以必须有**失效保护**：把"通信故障"这个**信息层**的事件，翻译成"安全动作"这个**物理层**的事件。

### ② 它要解决什么问题（没有它会怎样）

失效保护要同时解决两个问题，而且这两个问题的答案是**互相冲突**的：


**第一个问题：阈值取多长？**（判据的灵敏度）

| 阈值取向 | 会怎样 | 具体到本工程 |
| --- | --- | --- |
| **太短**（比如 50ms） | 一次遮挡、一次重传就把飞机判失联 → **误触发**。对"降落"这种不可逆动作来说，误触发本身就是事故 | 🟢 按本工程遥控器发包节奏（约 10ms 一包）推算，50ms ≈ 5 个包；而射频芯片本身允许重传 3 次（事实清单：手册第 33 页 `ARC=3`），一次遮挡就可能丢掉十几个包 |
| **太长**（比如 30s） | 飞手已经彻底失去控制，飞机还在按最后舵量飞 → **危险窗口大**。手册 7.3 原话："飞机还会按最后指令飞 5 秒" | 🟢 本工程取 5000ms |
| **合适** | 要同时满足"容忍正常抖动"与"危险窗口可接受" —— 这是个**工程判断**，没有公式 | 🟡 见下面的推算 |

🟢 **确证（本工程的阈值，两个数差 5 倍）**：

| 侧 | 阈值 | 代码位置 | 计时对象 | 动作 |
| --- | --- | --- | --- | --- |
| **飞控侧** | **5000ms** | `user/main.c:462` `if (HAL_GetTick() - connection_nowtime > 5000)` | "多久没收到合法包" | `bLanding=1`（自动降落）+ 200ms 快闪 + 射频切接收（`main.c:464-470`） |
| **遥控器侧** | **1000ms** | `遥控器/user_driver/tim16.c:76-87` `if (sign_timer_cnt >= 1000)` | "多久没收到 ACK" | `signal_lost_flag=1` + LED2 200ms 快闪 + 重新初始化射频（`bsp_pn298_re_sign_init()`）+ 串口打印"信号丢失（超过1秒无响应）" |

🟢 **确证（时间戳的唯一刷新点）**：`connection_nowtime` **只在**这里被赋值：

```c

```

🟢 该函数内**没有**第二处赋值（我已全文检索 `connection_nowtime`：定义在 `deal_pack.c:91`，
刷新只有 `:257`，判断只有 `main.c:462`，声明只有 `main.c:92`）。
**这就是手册 7.3 强调的那个关键细节的完整证据**：判据不是"收到任意字节"，
而是"收到**校验通过的完整包**"。

🟡 **通说（阈值为什么是 5 秒，我的推算，非代码注释）**：
按遥控器实际发包节奏推算（见下），5 秒 ≈ **几百个**心跳周期。
这个数量级说明设计意图是"**只在链路真的死了才动作**"，而不是"丢几个包就报警"。
对"自动降落"这种不可逆动作，这个取向是合理的；代价是危险窗口确实长。

> **🟢 顺便推算一下发包节奏**（可自行核对）：遥控器的发包标志由 TIM16 中断产生，
> 中断周期 1ms（`遥控器/user_driver/tim16.c:25-26`：Period=1000-1、Prescaler=48-1，
> 而遥控器的系统时钟也是 HSI 24MHz × PLL 2 = 48MHz，见 `遥控器/user_driver/board.c:29-38`）。
> 但 `loop50HzCnt++` 在同一个回调里**连续出现了两次**（`tim16.c:51-61`），
> 所以 `>= 20` 实际是 **10ms** 一次，而不是变量名暗示的 20ms。
> → **按代码推算：约 10ms 一包（≈100 次/秒）**；
> → 5000ms ≈ **500 个发包周期**，1000ms ≈ **100 个**。
> 变量名 `loop50HzCnt`（50Hz）与推算值（100Hz）不一致，这里**只记录不改动** ——
> 它的绝对数值不影响本章任何结论，只影响"阈值相当于多少个心跳"的换算。

#### 7.3.1 两套判据、两个动作，方向不同（🟢 本机实测）

**这张图想让你记住的一件事**：**阈值不是一个技术常数，而是"动作代价"的函数。**

#### 7.3.2 保护动作的选择（🟢 本工程选了"缓降 + 落地停机"）

🟢 **确证（动作链条，可逐行核对）**：飞控侧失联后**不是**立刻停桨，而是：

1. `main.c:465` 置 `fc.flags.bLanding = 1`；
2. `imu/decode.c:123-134` 的状态机接管：

```c
/* imu/decode.c:123-134 —— bLanding 的实际后果 */
if(fc.flags.bLanding) {
    fc.flags.bVelocityControl = 1;
    setVelocity = -650;                 /* 目标垂直速度 -650（缓降，不是自由落体） */
    if(setVelocity < VELOCITY_SPEEDDOWN_MAX) setVelocity = VELOCITY_SPEEDDOWN_MAX;
    if(accgyro.accData[2] > 6500)       /* Z 轴加速度 > 6500 ⇒ 判定"已经落地" */
    {
        fc.flags.motorArmed = 0;        /* 这时才停机 */
        fc.flags.motorIdle  = 0;
        fc.flags.bLanding   = 0;
    }
}
```

🟢 **确证（同一个"降落"出口还接了一路低电保护）**：`user/adc.c:234-251` 检测到电池电压
连续 6 次偏低（注释推算约 6 秒，`adc.c:240-243`）后，也会置 `fc.flags.bLanding = 1`
并写回传标志 `temp_buff[1] = 2`。
**所以 `bLanding` 是一个"多源汇入、单点执行"的安全动作出口** —— 这是很好的设计：
新增一种危险来源时，只需要"置这一个标志"，不用再写一套降落逻辑。

🟢 **确证（一处值得你自己评估的细节）**：`main.c:466-468` 的注释指出，
工程里**没有任何地方把 `bLanding` 清回 0**（只有 `decode.c:133` 在"判定落地"那一支里清它，
以及 `decode.c:94/103` 在手动上锁/解锁时清）。

- 对失效保护来说，**方向是安全的**：一次失联触发后不会自动恢复飞行；
- 但手册 7.3 的检查点 3（"恢复通信后能不能自动解除"）的答案就是：
  **只有在判定已经落地之后才会清掉降落状态**，通信恢复本身不会取消降落。

#### 7.3.3 `HAL_GetTick()` 相减写法的坑（🟢 事实清单可证）

🟢 **确证**：事实清单记明本工程 SysTick 校准为 1ms 时基（参考手册第 119 页 12.1.2）。
于是 `HAL_GetTick()` 是 32 位毫秒计数，`2^32 ms ≈ 49.7 天`回绕一次。

```text
图 10（小卡）　为什么必须写成"当前 - 上次"

  ✅ 正确：HAL_GetTick() - connection_nowtime > 5000
     无符号减法天然按 2^32 取模：
       回绕瞬间  当前=5, 上次=4294967000
       差值 = (5 - 4294967000) mod 2^32 = 296 ≈ 296ms  →  判"正常" ✅

  ❌ 错误：HAL_GetTick() > connection_nowtime + 5000
     回绕瞬间  4294967000 + 5000 溢出成很小的数
       → 条件是"真"  →  刚上电就判失联 ❌

  ❌ 错误：用有符号差值 if ((int32_t)(now-last) > 5000)
     只要间隔小于 2^31 ms 其实也对，但一旦超过就翻符号
     —— 本工程用无符号，读者不要"顺手优化"成有符号
```

### ④ 实现方法有哪些（取舍对照表）

#### 表 7-3-1　保护动作的选择（发现失联之后干什么）

| 动作 | 具体做法 | 优点 | 代价 / 风险 | 适用场景 | 本工程 |
| --- | --- | --- | --- | --- | --- |
| **① 保持最后舵量** | 什么都不做，继续输出上一帧指令 | 零代码 | 飞机会**沿着最后方向飞走**（"放风筝"）；单旋翼会持续带坡度盘旋 | ❌ 任何场景都不该作为默认 | ❌ |
| **② 回中 / 回水平** | 姿态通道回 0，油门不动 | 姿态不会继续倾斜 | 高度不受控：可能一直爬升或一直下沉 | 有定高功能的机型 | ❌ |
| **③ 缓降（受控下降）** | 目标垂直速度设成一个小的负值，等落地判定后停机 | 有软着陆机会；可逆性最好；对人和物最安全 | 需要高度估计可靠（气压计/加速度计融合，见 8.5） | 多旋翼，有高度环 | **✅ 本工程**（`decode.c:127` `setVelocity = -650`） |
| **④ 自动返航（RTH, Return To Home）** | 用 **GPS**（Global Positioning System，全球定位系统）/光流导航回到起飞点 | 飞机能回来 | 需要**位置估计**（本工程没有 GPS）；返航路径本身有撞障碍风险 | 带 **GNSS**（Global Navigation Satellite System，全球导航卫星系统）的机型 | ❌ 本工程无位置传感器 |
| **⑤ 切断动力（停桨）** | 立刻把四个电机置停转 | 最简单、最"安全"（不会飞走） | 从空中**自由落体** → 摔机；如果失联是误判（一次遮挡）损失更大 | 极少数场景（如室内桨叶防护良好的小机） | ❌ 只在"落地判定通过"后才停机（`decode.c:131`） |

🟢 **手册 7.3 与本节的结论一致**：手册写"通常是**降低油门/停转电机/自动降落**"；
本工程的实际选择是 **③ 缓降 + 落地后停机**，并且代码注释（`main.c:50-51`）
明确写了设计意图："比直接切电机更安全（骤然停桨会摔机）"。

#### 表 7-3-2　判据的实现方法（"失联"这件事怎么判出来）

| 方案 | 判据 | 优点 | 代价 | 本工程 |
| --- | --- | --- | --- | --- |
| **① 超时计数** | 一个时间戳 + 一个阈值 | 最简单；行为完全可预测 | 阈值只能拍；丢了几个包和彻底失联用同一个判据 | **✅ 两侧都是这个**（`main.c:462`、`遥控器 tim16.c:79`） |
| **② 序号/计数判定** | 连续 N 个周期没收到序号递增 | 不依赖绝对时间，抗时钟漂移 | 需要一个"周期"的概念（数据必须周期性）；序号回绕要处理 | 🟡 硬件层有 PID 位可识别重发包（事实清单：PN298 手册第 19 页），固件未消费 |
| **③ 信号质量 + 超时** | 结合 RSSI（接收信号强度）/丢包率，分档处理 | 能在"快要失联"时提前降级（比如先限高、先返航） | 需要读芯片的 RSSI/丢包统计并做分档策略 | ❌（但 `OBSERVE_TX` 的 `PLOS_CNT`/`ARC_CNT` 是现成的数据源，事实清单：手册第 35 页） |
| **④ 双向确认** | 只有收到 ACK 才算对方活着 | 能发现"单向通"（能收不能发）这种隐性故障 | 链路的两端都必须能发；一侧坏了会被另一侧判失联 | **✅ 遥控器侧就是靠 ACK 判活**（`遥控器 bsp_pn298.c:424-431`） |
| **⑤ 分级失效保护** | 按"失联多久"分档：短 → 警告、中 → 悬停/限高、长 → 降落 | 危险窗口与误触发可以同时优化 | 状态多、调参复杂 | ❌ 本工程是"单阈值单动作"，无分档 |

### 7.3 小结与检查清单

**手册 7.3 留了三个检查点，这里给出本工程的答案（🟢 全部可核对）**：

| 检查点 | 本工程的答案 |
| --- | --- |
| 1. 超时阈值是多少 | 飞控 **5000ms**（`main.c:462`）；遥控器 **1000ms**（`遥控器 tim16.c:79`）。对飞控来说偏长，意味着遥控器关掉后飞机还会按最后指令飞 5 秒 |
| 2. 触发后具体做什么 | 闪灯（200ms）+ `bLanding=1` → **缓降**（目标垂直速度 -650）→ 落地判定（`accData[2]>6500`）→ 停机。**确实动了油门，不是只闪灯** |
| 3. 恢复通信后能不能自动解除 | **不能自动取消降落**（只有判定落地后才清 `bLanding`，`decode.c:133`）；但失联**报警灯**会随通信恢复而清除（`main.c:486`），且射频已切回接收模式（`main.c:470`）会自动重连 |

**本节的四句话总结**：

1. 失效保护存在的唯一理由是：**遥控失联时飞行器不能保持最后的舵量继续飞**；
2. 判据的阈值不是技术常数，而是**动作代价的函数**（可逆动作可以敏感，不可逆动作必须保守）；
3. 本工程的动作是**缓降而非直接停桨**，并且"降落"这个动作有**两个触发源**
   （失联 `main.c:465` / 低电 `adc.c:244`）汇入同一个标志；
4. 判据的可靠性来自**时间戳只在合法包处刷新**（`deal_pack.c:257`）——
   这是整个失效保护链条上最关键的一行。

# 第 8 章　传感器、姿态、滤波、姿态解算

> **本章主线**：这一章讲的是"**飞机怎么知道自己是什么姿态、在什么高度**"。
> 它比第 7 章更"物理"，因为这里所有麻烦都来自**传感器本身的缺陷**：
> 陀螺仪会漂、加速度计会抖、气压计会受气流影响。整章可以概括成一句话 ——
>
> **没有任何一个传感器是好用的，姿态与高度都是"两个都不完美的传感器互相纠正"的结果。**
>
> - **IMU（第 8.1 节）**：提供两个互补的传感器（一个短期准、一个长期准）；
> - **量程/分辨率/零偏/校准（第 8.2 节）**：把"传感器输出"变成"可信的物理量"；
> - **姿态解算（第 8.3 节）**：把两组测量融合成一个姿态（本工程用 Mahony）；
> - **滤波（第 8.4 节）**：把"振动噪声"和"真实运动"分开；
> - **气压计与定高（第 8.5 节）**：把"气压"变成"高度"，再和加速度计融合。

## 8.1 IMU（Inertial Measurement Unit，惯性测量单元）

> **这一节回答什么问题**：飞机要知道自己的姿态，为什么不直接装一个"角度传感器"，
> 而要装两个都测不准的东西？

### ① 它是怎么出现的

🟡 **通说**：姿态估计这件事，历史上一直是靠**外部参照**解决的 —— 看地平线（光学）、
看磁北（罗盘）、看星星。这些手段各有各的死穴，在小型飞行器上尤其致命：

| 外部参照 | 能给出什么 | 死穴 |
| --- | --- | --- |
| **GPS（Global Positioning System，全球定位系统）** | 位置、地速（对地速度）、时间 | 🟡 更新率远低于控制周期（典型 5~10Hz 量级）；**不给姿态角**；室内/遮挡环境直接失效 |
| **磁力计（罗盘）** | 航向（相对磁北），可给出偏航的绝对参考 | 🟡 怕磁干扰：电机电流、电调、扬声器、铁质螺丝、附近钢筋都会让读数偏掉；靠近地面/室内更明显 |
| **气压计** | 高度（相对气压面） | 见 8.5 —— 噪声、气流、天气漂移 |
| **视觉/光流** | 位置、速度 | 🟡 依赖光照与纹理，算力开销大 |

→ 剩下的路只有一条：**用惯性器件自己"算"出姿态**。
惯性器件的最大优点是**不依赖外界**（不受遮挡、不受磁干扰、不依赖光照），
最大缺点是**没有绝对参照**（所以会漂）。这就是 IMU 出现的理由。

### ② 它要解决什么问题（没有它会怎样）

IMU 里为什么要放**两个**传感器？因为**这两个传感器的误差特性恰好相反**：

```text
图 12　陀螺仪与加速度计的误差特性对比（这是整章的物理基础）

 误差
  ▲
  │   【陀螺仪：短期准、长期漂】
  │                                          ╱
  │                                        ╱   ← 积分漂移：随时间线性增长
  │                                      ╱       （零偏 × 时间）
  │                                    ╱
  │  ────────────────────────────────╱───────────► 时间
  │       ↑ 短时间（1 秒内）几乎贴着 0
  │
  │   【加速度计：长期准、短期抖】
  │
  │        ╱╲    ╱╲        ← 噪声：高频抖动，但**均值为 0**
  │  ╱╲  ╱  ╲  ╱  ╲  ╱╲
  │ ╱  ╲╱    ╲╱    ╲╱  ╲
  │ ─────────────────────────────────────────────► 时间
  │      ↑ 只要静止，长时间平均下来**不会跑偏**（因为测的是重力方向）
  │
  └──────────────────────────────────────────────────────────────────────

 🟢 两条说法在本工程代码里的落点：
   · 陀螺仪会漂  → 所以要"校准零偏"（accgyro.c:201-248），
                    还要在解算里用加速度计"慢慢修正"（imu.c:288-290 的叉积误差）
   · 加速度计有噪声 → 所以要先滤波（accgyro.c:71 的 30Hz 双二阶），
                    再用"是否接近 1g"来判断它当次是否可信（imu.c:354-368）
```

**一句话概括**：🟡 **陀螺仪短期准、长期漂；加速度计长期准、短期抖 —— 两者互补，
所以必须融合。** 这句话是第 8.1、8.3、8.5 三节的共同主线（加速度计在这里的角色，
与气压计在 8.5 里的角色**完全对称**：都是"低频准、高频差"的那个）。

### ③ 我该怎么理解它

#### 8.1.1 本工程用的是 ICM-42688-P（六轴，无磁力计）

🟢 **确证（逐条可核对）**：

#### 8.1.2 加速度计在这里的真正作用：提供"重力的方向"

🟢 **确证**：本工程判断加速度计数据是否可用，用的判据是**模长是否接近 1g**：

```c
/* imu/imu.c:354-368 —— 只看模长，不看方向 */
accMagnitude = Σ (accSmooth[axis]²) * 100 / acc_1G²;
return (81 < accMagnitude) && (accMagnitude < 121);   /* 即 0.90g ~ 1.10g */
```

- 静止时，加速度计测到的**只有重力**（1g），方向朝上 → 据此可以算出"倾斜了多少"；
- 一旦**真的在加速**（比如猛推油门、急停），测到的就是"重力 + 运动加速度"，
  模长就偏离 1g → 此时它的"重力方向"不可信，**宁可不修正**（`imu.c:431-433`）。

🟡 **通说**：这条门限（0.9g~1.1g）是飞控里的常见做法，本工程的取值与注释一致
（`imu.c:365-367` 的注释就写 "Accept accel readings only in range 0.90g - 1.10g"）。
**注意它只判"模长"，不判"方向"** —— 所以飞机在持续匀速倾斜加速的极端情况下仍会误信，
这属于该判据的固有局限（🟡 通说，不是本工程的 bug）。

#### 8.1.3 没有磁力计的后果（🟢 可以从代码直接看出来）

🟢 **确证**：`imu/pid.c:245-247` 把这句做成了显式动作：

```c
/* 强制偏航角为 0：本项目不做航向锁定（没有磁力计做绝对航向），
 * 偏航只做角速度控制，所以把偏航角清零避免它参与角度环计算。 */
angle[2] = 0;
```

**意思是**：俯仰/横滚有重力当绝对参照（所以能长期准），
**偏航没有任何绝对参照** —— 陀螺仪积分出来的偏航角只会一直漂。
所以本工程干脆**放弃偏航角**，偏航只做"角速度控制"（你打舵 → 它就转，松手就停转，
但"转到哪个朝向"它不知道也不关心）。这是无磁力计方案的标准取舍。

### ④ 实现方法有哪些（取舍对照表）

| 方案 | 组成部分 | 能得到什么 | 代价 / 得不到什么 | 本工程 |
| --- | --- | --- | --- | --- |
| **① 单陀螺仪** | 3 轴陀螺 | 姿态**变化率**（角速度），短期内姿态可积分出来 | 零偏让角度**持续漂移**，几分钟就偏几十度（见 8.2 的定量）；没有绝对参照 | ❌ |
| **② 六轴 IMU（本工程）** | 3 轴陀螺 + 3 轴加速度计 | 俯仰/横滚可长期稳定（重力当参照）；偏航只能做角速度控制 | 偏航无绝对参照；加速度计在"真加速"时不可用 | **✅ `accgyro.c:64-66`、`imu.c:261`** |
| **③ 九轴（六轴 + 磁力计）** | 再加 3 轴磁力计 | 偏航有绝对参照 → 可以做航向锁定、可以自动返航时保持航向 | 磁干扰要标定/补偿；室内与近铁件环境不可靠；多一套校准流程 | ❌ |
| **④ IMU + 气压计 + GPS 组合导航** | 再加气压计、GNSS（Global Navigation Satellite System，全球导航卫星系统） | 位置、高度、地速、航向都能给；可做自动返航、航线飞行 | 传感器多、融合算法复杂（通常要 EKF）；依赖卫星可见性 | 🟡 **部分**：本工程有 **IMU + 气压计**（8.5），**没有 GNSS** |

**本工程的取舍一句话**：**用"六轴 + 气压计"覆盖了室内小四轴的刚需
（姿态稳定 + 定高），主动放弃了"航向"和"位置"这两件需要额外传感器的事。**

## 8.2 量程、分辨率、零偏、校准

> **这一节回答什么问题**：传感器输出的是"数字"（比如一个 int16），
> 这个数字怎么变成可信的物理量？以及为什么必须先校准才能用？

### ① 它们各自是怎么出现的 / 解决什么问题

| 概念 | 它解决什么问题 | 没有它（或选错它）会怎样 |
| --- | --- | --- |
| **量程 / FSR**（Full Scale Range，满量程） | "我能测多大的范围" —— 决定了**不削顶**的安全边界 | 选小了：飞机翻滚/急加速时加速度计**饱和削顶**，读数卡在最大值 → 姿态解算拿到错误的重力方向；选大了：见下一行 |
| **分辨率 / LSB**（Least Significant Bit，最低有效位） | "我能分辨多小的变化" —— 决定了噪声地板与最小可测变化 | 分辨率太粗：静止时的微小振动全部落进同一个码值（量化噪声），滤波后仍然粗糙 |
| **零偏（Bias / Offset）** | "静止时输出不为 0"这个**系统误差**要被减掉 | 陀螺零偏会被**积分**成角度 → 角度持续漂移（这是最致命的一条）；加速度零偏会让"水平"判断整体偏掉 |
| **校准（Calibration）** | 把零偏（以及比例误差）**测出来、存起来、每次都减掉** | 每次都手动修正；或者干脆带着零偏飞 |
| **噪声密度** | 决定"滤波参数该怎么选"（截止频率、平滑窗口） | 滤得太狠 → 相位滞后大（飞机发飘、响应慢）；滤得太少 → 噪声进 PID 的 D 项（电机抖、发热） |

### ② 为什么量程和分辨率是矛盾的（🟢 可自行验算）

**关键前提**：传感器内部是"物理量 → 模拟电压 → **固定位数的 ADC**（Analog-to-Digital
Converter，模数转换器）→ 数字量"。位数是固定的（这类 **MEMS**（Micro-Electro-Mechanical System，微机电系统）惯性器件通常是 16 位输出），
所以**同一个位数的码值空间要摊到整个量程上**：

```text
图 13　量程与分辨率的"跷跷板"（同一个 16 位 ADC）

   16 位有符号输出： -32768 ................................ +32767
                     │                                          │
                     │◄──────────── 码值空间固定 ─────────────►│
                     │                                          │
 【量程 ±8g】        ├──────────────────────────────────────────┤
   灵敏度 = 32768 / 8 = 4096 LSB/g
   1 LSB ≈ 0.244 mg            ← 分辨得细，但只能测到 ±8g

 【量程 ±16g】       ├──────────────────────────────────────────┤
   灵敏度 = 32768 / 16 = 2048 LSB/g
   1 LSB ≈ 0.488 mg            ← 能测到 ±16g，但分辨粗了一倍

 【量程 ±4g】        ├──────────────────────────────────────────┤
   灵敏度 = 32768 / 4 = 8192 LSB/g
   1 LSB ≈ 0.122 mg            ← 更细，但 4g 很容易削顶
                               （四轴机动时加速度冲到 3~4g 很常见 🟡通说）
```

🟢 **确证（本工程的两个数正好互为印证）**：

```c
/* imu/accgyro.c:35-36 */
int16_t acc_1G = 4096;                                  /* 1g 对应的原始值 */
float gyroScale = 1.0f / 16.4f * (M_PI / 180.0f);        /* 原始值 → 弧度/秒 的比例 */
```

- `acc_1G = 4096` → 32768 / 8 = 4096 → **正好对应 ±8g 档**（配置处 `accgyro.c:64`）🟢
- `1/16.4` → 32768 / 2000 = 16.384 → **正好对应 ±2000dps 档**（配置处 `accgyro.c:65`）🟢

**这两个常量不是"魔法数字"，是"量程选完以后算出来的"** —— 这也是读传感器代码的通用方法：
看到 `LSB/g` 或 `1/16.4` 这类常量，先反推它的量程档，再回寄存器配置处核对。

🟢 **一个容易忽略的点：分辨率 ≠ 有效分辨率**。`4096 LSB/g` 只说明"刻度多细"，
但传感器**本底噪声**可能有好几个 LSB 大。所以真正决定"能分辨多小变化"的是
**噪声密度**（单位通常是 `μg/√Hz` 这类），而不是 LSB。
🟡 本工程对应的处理是：用滤波把带宽压下来，噪声随之下降（滤波的收益是 √带宽 关系）——
这条是信号处理的通说，不是本机实测。

### ③ 我该怎么理解零偏：把"漂移"算成一个数

🟢 **确证（算术部分）**：本工程陀螺的换算比例是 **16.4 LSB 对应 1°/s**（`accgyro.c:36`）。
于是：

```text
图 14（小卡）　陀螺零偏 → 角度漂移的定量换算（算术，不是实测）

  残留零偏 16.4 LSB   →  1 °/s   →  60 秒后角度漂移 60°
  残留零偏  8.2 LSB   →  0.5 °/s →  60 秒后漂移 30°
  残留零偏 50   LSB   →  3.05 °/s →  60 秒后漂移 183°

  🟢 拿本工程自己的阈值做参照：GYRO_CALI_DIFF_LIMIT = 50（accgyro.c:222）
     —— 这个 50 就是"校准期间允许的静止抖动上限"。
     换句话说：**如果校准做坏了、残留 50 LSB 的零偏，一分钟就能漂 180°。**

  🟡 假设说明：上面假设"零偏在校准后是恒定的"。真实器件的零偏还会随温度变化，
     所以工程上要么做温度补偿，要么靠姿态解算里的积分项慢慢吃掉残余（见 8.3）。
```

**这张卡片的用途**：它解释了为什么手册 8.2 把"零偏"和"校准"放在同一节 ——
**零偏的危害不是"读数不准"，而是"被积分以后无限放大"**。
加速度计的零偏只造成一个固定偏差（不累积），陀螺仪的零偏造成**随时间增长的漂移**，
两者的危害量级完全不同。

### 8.2 小结

1. **量程**决定"不削顶"，**分辨率**决定"能否分辨小变化"，这两者在同一 ADC 位数下**互相矛盾**
   （本工程两个常量 `4096`、`1/16.4` 就是 8g / 2000dps 两档量程算出来的）；
2. **零偏**的危害不对称：陀螺零偏被积分 → 角度**持续漂移**；加速度零偏只造成固定偏差；
3. **校准**的前提是"**静止且水平**"，本工程用"陀螺输出抖动 < 50 LSB"当静止判据，
   采 512 次平均，结果写 Flash 供下次上电恢复（`accgyro.c:201-304`、`main.c:332-335`）；
4. 本工程**没有**温度补偿；在线零偏估计只有 Mahony 的积分项（8.3）。

## 8.3 姿态解算（Attitude Estimation）

> **这一节回答什么问题**：为什么不能"直接读角度"？如果不能，那要用什么表示姿态、
> 用什么算法把它算出来？

### ① 它是怎么出现的

🟢 **确证（从代码的换算比例就能看出来）**：本工程的陀螺仪原始值要先乘一个比例才变成角速度：

```c
/* imu/imu.c:439 —— 陀螺仪数据乘 gyroScale 后送进 Mahony */
gyroData[0] * gyroScale, gyroData[1] * gyroScale, gyroData[2] * gyroScale,
/* imu/accgyro.c:36 —— 而 gyroScale 里面带着 (M_PI / 180.0f) 的角度→弧度换算 */
float gyroScale = 1.0f / 16.4f * (M_PI / 180.0f);   /* → 弧度/秒 */
```

**MEMS（Micro-Electro-Mechanical System，微机电系统）陀螺仪输出的是"角速度"（deg/s），
不是"角度"（deg）。** 想要角度，只有一条路：**对角速度积分**：

```text
   角度(t) = 角度(0) + ∫ 角速度 dt          ← 连续形式（物理事实）
   角度[n] = 角度[n-1] + 角速度[n] × dt     ← 代码里的离散形式（imu.c:323-334）
```

🟢 **而积分必然漂移**：只要角速度里含有一个极小的恒定误差 `b`（零偏），
积分出来就是 `b × t`，**随时间线性增长**。8.2 的定量卡片已经算过这个量级：
残留 50 LSB ≈ 3°/s → 一分钟 180°。
**这就是"不能直接读角度、而且不能只靠陀螺仪积分"的全部理由。**

### ② 它要解决什么问题（没有它会怎样）

姿态解算要同时解决两个子问题，缺一个都不行：

| 子问题 | 不用它（只积分陀螺）会怎样 | 不用它（只用加速度计）会怎样 |
| --- | --- | --- |
| **① 用最快的信号跟踪姿态变化** | — | 加速度计有噪声且带宽低，跟不上快速机动；而且**偏航完全测不到** |
| **② 用一个"不会漂"的参照纠正漂移** | 角度几分钟就漂几十度，飞机越飞越歪 | — |

→ 于是有**互补滤波**这一类思路：**让陀螺仪负责"快"，让加速度计负责"不漂"**。
🟢 本工程用的 **Mahony** 就是互补滤波的一种具体实现形态（名字可以照实写；
本文件不写"谁在哪年提出"，因为那类信息本机无法核实）。

### ③ 我该怎么理解它

#### 8.3.1 三种姿态表示，各自的"病"（🟢 结构性事实 + 🟡 工程评价）

**这个回路要看出的一点**：Mahony 与"互补滤波"是**同一件事的两种写法**。
互补滤波的经典形式是"低频用加速度计、高频用陀螺仪"两个滤波器相加；
Mahony 把这件事写成"**用误差去修正陀螺仪的输入**"，
好处是**修正作用自动作用在四元数积分上**，不需要额外设计两个滤波器。
🟡（这条等价性说明属通说。）

🟢 **积分项就是"陀螺零偏估计器"**：`integralFB` 累加的是 `Ki × 误差 × dt`（`imu.c:300-302`），
而误差在姿态稳定后**主要来自陀螺零偏**。所以这个积分项会慢慢收敛到"能抵消零偏的量" ——
这正是 8.2 表里"运行时在线估计"的那一格在本工程的**部分实现**。
它只能估 3 个陀螺零偏，不能估加速度计零偏。

**外环输出与内环反馈的量纲并不一致**：

```c
/* imu/pid.c:259-261 —— 外环：角度误差（单位"度×100"）→ 目标"角速度" */
target_angle = constrain(20*rcCommand[axis], -30000, +30000) + rcCommandTrim[axis] - angle[axis];
target_rate  = target_angle * pidconf.PAngleToRate[axis];      /* PAngleToRate = 1.0 */

/* imu/pid.c:304-306 —— 内环：反馈直接用陀螺仪的原始 LSB（≈16.4 LSB 每 °/s） */
current_rate = accgyro.gyroData[axis];
rate_error   = target_rate - current_rate;
```

- `target_rate` 的量纲实际上是"**度×100**"（1 度误差 × 1.0 → 100 个单位）；
- `current_rate` 的量纲是"**LSB ≈ 16.4 × °/s**"；
- 两者相减得到一个"量纲混合"的误差 → 内环增益 `PRate = 0.10` 之类的数值
  （`pid.c:241`）实际上同时承担了"单位换算"和"增益"两个职责。

按代码数值粗算：满舵（`rcCommand=500`）→ `target_angle=10000` → `target_rate≈10000`；
而真实转 300°/s 时 `current_rate ≈ 4920`。
所以这个环在数值上"能对上"，飞起来也能用（否则原作者不会这样写），
但它**不是教科书意义上的标准串级**：单位没统一，外环的"期望角速度"尺度是隐含的。
如果你要改参数，请把这一条先想清楚 —— **改 `PAngleToRate` 时不能按"角度→角速度"的物理意义去算**。

### 8.3 小结

1. **不能直接读角度**：MEMS 陀螺输出的是**角速度**，要积分才有角度，而积分必然漂
   （🟢 本工程换算比例 `1/16.4 × π/180`，`accgyro.c:36`）；
2. 三种姿态表示各有各的病：**欧拉角有万向节死锁**、**矩阵有冗余与正交化负担**、
   **四元数不直观且必须归一化**；工程上的常规组合是"四元数当状态、矩阵当工具、欧拉角当输出"；
3. 本工程用 **Mahony**（`imu.c:261`，Kp=0.25 / Ki=0.0025），
   靠**加速度计提供的重力方向**纠正陀螺漂移，并有**三重保护**
   （加速度计健康判据、快转停积分、上电 2 秒快收敛）；
4. 可选算法有互补滤波 / Mahony / Madgwick / EKF / DCM，
   取舍在"计算量 vs 精度 vs 调参难度"三维上（本工程选最省算力的那一档）。

## 8.4 滤波（Filter）

> **这一节回答什么问题**：为什么必须滤？"滤多狠"这个参数怎么定？
> 以及**本工程到底用了哪几个滤波器、什么参数、滤波器放在哪一级**？

### ① 它是怎么出现的

🟡 **通说（本节最核心的一条经验结论）**：**机架振动频率远高于姿态解算带宽，
不滤掉会被积分成假角度。** 展开成推理链条：

```text
   电机/桨叶转动 → 机架结构振动（高频，几十~几百 Hz 量级 🟠此处不给具体数字）
        ↓ 通过减震/硬连接传到 IMU
   陀螺仪读到的是"真实角速度 + 振动引起的角速度抖动"
        ↓ 姿态解算要做积分：角度 = ∫ω dt
   振动是"高频振荡"，积分的**均值**接近 0 → 所以它对角度的长期影响有限
        ↓ 但它是**高频大幅值**信号：
   ① 进 PID 的 D 项（微分）→ 被放大成电机的高频抖动 → 电机发热、机身嗡响（🟡）
   ② 与采样混叠（aliasing）后可能落到低频 → 变成"看起来像真实运动"的假信号（🟡）
   ③ 大幅值振动可能触发姿态解算里的各种门限（如本工程的 0.9g~1.1g 判据）→ 让算法
      "以为"传感器坏了/在加速
        ↓
   ⇒ 必须在**积分和微分之前**把振动带滤掉
```

🟢 **确证（工程自己的说法）**：`imu/filter.c:10-14` 的注释写了同一件事：

> "陀螺仪/加速度计本身有噪声，电机振动也会串进来。PID 的 D 项是'误差的变化率'，
> 对噪声极其敏感：一点点噪声经过微分就被放大成电机的高频抖动，表现为飞机'嗡嗡'响、
> 电机发热、甚至姿态发散。所以滤波是飞控能否稳定飞行的前提。"

🟢 **确证（D 项确实会放大噪声，可从代码验证）**：`imu/pid.c:331-338`：

```c
delta = rate_error - last_rate[axis];       /* 相邻两次的差 */
last_rate[axis] = rate_error;
delta /= deltaT;                            /* 再除以 dt → 噪声被 dt 放大 */
deltaSum = delta1[axis] + delta2[axis] + delta;   /* 3 点滑动和（做一次简易平均） */
d = deltaSum * pidconf.DRate[axis];
```

**看那个 `/= deltaT`**：采样周期越小（1.25ms 量级），噪声被放大的倍率越大
（🧮 这是数学必然：差分 = 高频增益 ∝ 1/dt）。

### ② 不滤会怎样 / 滤过头会怎样（一对反向的代价）

| | 滤得不够 | 滤得过头 |
| --- | --- | --- |
| 表现 | 电机高频抖动、发热、机身嗡响；D 项输出乱跳；🟡 严重时姿态发散 | **相位滞后** → 飞机"发飘"、响应迟钝；🟡 严重时控制环路相位裕度不足，出现低频振荡 |
| 原因 | 振动带落在通带里 | 截止频率低于了控制带宽 |
| 本工程的对应参数 | — | 陀螺 PT1 240Hz（`accgyro.c:72`）、加速度 30Hz（`accgyro.c:71`） |

### ③ 我该怎么理解"截止频率"（🟢 定义 + 🟡 选取经验）

```text
图 18　滤波器频响示意（通带 / 截止 / 阻带）

   增益
   1.0 ┤━━━━━━━━━━━━━━━━━━┓
       │   通带（保留）    ┃

       │                  ┃
   0.7 ┤ ·················╋············· ← 截止频率 f_c：增益降到 0.707（-3dB）

  ★ 两个必须记住的取舍（🟡 通说）：
    ① 截止频率要 **低于振动频率**（否则振动照样进积分/微分）
    ② 截止频率要 **高于控制带宽**（否则连真实运动都被滤掉 → 相位滞后 → 发飘）
        · "控制带宽"指的是姿态环真正需要响应的频率（手指打舵的频率量级，几 Hz）
        · 这两条之间通常有**很宽**的余量，所以截止频率不是"卡在中间"，
          而是"尽量高一点、只要能把振动压下去"
    ③ 阶数越高滚降越陡（一阶 -20dB/十倍频、二阶 -40dB/十倍频），
       但**相位滞后也越多** —— 这就是本工程"陀螺用一阶、加速度用二阶"的原因之一
```

"经验：陀螺仪常用 80~150Hz，具体看机架振动情况" ——
而本工程实际用的是 **240Hz**（`accgyro.c:72`），比这条注释建议的更高。
🟡 我不去猜"哪个是对的"：`filter.c` 的注释是**通用建议**，
`accgyro.c:72` 是**本工程的取值**，两者不一致本身就是一个"值得你自己想清楚"的点
（240Hz 更少滞后，但对振动的抑制更弱）。

#### （a）陀螺仪：PT1 一阶低通，240Hz，dT = 1.25ms

🟢 **确证**：

```c
/* imu/accgyro.c:72 —— 初始化（三轴各一个，accgyro.c:30 定义数组） */
pt1FilterInit(&gyroFilter[axis], 240, 1.25e-3);   /* 截止频率 240Hz，dT = 1.25ms */
/* imu/accgyro.c:127 —— 应用 */
accgyro.gyroData[axis] = pt1FilterApply(&gyroFilter[axis], accgyro.gyroValue[axis]);
```

🟢 **递推式与 RC 的关系**（`imu/filter.c:83-99`）：

```c
filter->RC = 1.0f / ( 2.0f * M_PI_FLOAT * f_cut );                    /* RC = 1/(2π·f_cut) */
filter->state += filter->dT / (filter->RC + filter->dT) * (input - filter->state);
```

**怎么读这个式子**：每次把输出往输入方向"挪一小步"，
挪的比例 `dT/(RC+dT)` 越小 → 越平滑但跟随越慢。
`RC = 1/(2π×240) ≈ 0.663ms`，而 `dT = 1.25ms`，所以 `dT/(RC+dT) ≈ 0.65`
—— 每步挪 65%，**这已经是很"轻"的滤波**（240Hz 截止对 800Hz 采样率来说偏高，
属于"只压高频、尽量不引入滞后"的取向）。

#### （b）加速度计：biquad 二阶低通，30Hz，采样周期写 1250µs

🟢 **确证**：

```c
/* imu/accgyro.c:71 */
biquadFilterInitLPF(&accFilter[axis], 30, 1250);   /* 截止 30Hz，sampleDeltaUs = 1250µs */
/* imu/accgyro.c:126 */
accgyro.accData[axis] = biquadFilterApply(&accFilter[axis], accgyro.accValue[axis]);
```

🟢 **为什么加速度计用二阶、陀螺用一阶**（`imu/filter.c:16-21` 的原文理由）：
二阶（biquad，双二阶）滚降 **-40dB/十倍频**，比一阶陡一倍，
能把"振动带"压得更干净；代价是计算量更大、相位滞后更多。
加速度计的信号带宽需求低（它只用来判断重力方向），**多滞后一点无所谓**，
所以用二阶；陀螺仪直接进 PID 的内环，**滞后要尽量小**，所以用一阶。

🟢 **实现细节（filter.c:118-231）**：用**直接 II 型**结构，只存两个状态量 `d1`、`d2`
（相当于省掉四个历史值）—— 在 8KB SRAM 的芯片上这个优化有意义（`filter.c:126-129` 注释）；
系数在初始化时算一次（含 `sinf/cosf`，`filter.c:141-142`），运行时只有乘加。

#### （c）气压计：中值 + 滑动平均 + 低通 + 死区（四件套）

🟢 **确证**：

| 环节 | 参数 | 位置 |
| --- | --- | --- |
| **中值滤波** | 5 点（`PRESSURE_SAMPLES_MEDIAN = 5`） | 宏：`altitude.c:19`；调用：`altitude.c:88-90`；实现：`mlib.c:134-143`（7 次比较） |
| **滑动平均** | 窗口宏 `BARO_TAB_SIZE_MAX = 7`，实际除数 6 | 宏：`altitude.c:18`；求和与平均：`altitude.c:123-139` |
| **高度低通** | `BaroAlt = BaroAlt*0.1 + BaroAlt_tmp*0.9` | `altitude.c:169` |
| **垂直速度低通** | `baroVel = baroVel*3/4 + (BaroAlt-lastBaroAlt)*8` | `altitude.c:174` |
| **速度限幅 + 死区** | ±2000 mm/s；死区 100 mm/s | `altitude.c:176`、`:180` |

🟢 **顺带核出一个"宏与代码自洽"的细节**：注释说"窗口大小 7"，但平均时除以 6
（`altitude.c:137` `baroPressureSum / (BARO_TAB_SIZE_MAX - 1)`）。
我按环形缓冲区的加减顺序验算了一遍：稳态下求和里**确实只有 6 个样本**
（写第 `i` 个时同时减掉第 `i+1` 个，即最老的那个）→ **除数 6 是对的**，
不是笔误。这类"宏名字大 1、除数小 1"的地方，读代码时容易误判成 bug。

🟡 **中值滤波的代价（通说）**：N 点中值的输出相对于输入有一个 `(N-1)/2` 个样本的延迟
（5 点 → 约 2 个样本）。按本工程气压计约 30ms 一个样本（`common.c:537-539` 注释推算
"≈25+5 ms，约 30~40Hz"）算，中值 5 点带来 ~60ms 延迟，
再加上 6 点滑动平均（~180ms 跨度）—— **气压通道的总滞后是百毫秒量级**。
这正是"定高要用加速度计补高频"的原因（8.5）。

#### （d）还有一个"藏在 PID 里"的滤波（🟢）

🟢 **确证**：`imu/pid.c:335-338` 对 D 项做了一次**3 点滑动和平均**：

```c
deltaSum = delta1[axis] + delta2[axis] + delta;   /* 连续三次微分值相加 */
delta2[axis] = delta1[axis];
delta1[axis] = delta;                             /* 用移位代替数组，省 RAM */
d = deltaSum * pidconf.DRate[axis];
```

🟡 严格说这是"**3 点滑动和**（sum）"而不是"平均"（差一个 1/3 的系数），
但这个 1/3 被吸收进了 `DRate` 参数里（`pid.c:243` 的 `DRate = 0.0012`）——
**效果等价于"三点平均 + 增益"**。这类"常数吸收进增益"的写法在嵌入式里很常见，
读的时候要意识到"参数里可能藏着归一化系数"。

#### （e）**陷波器：代码里有，本工程没有用**（🟢 本机实测）

🟢 **确证**：`imu/filter.c:160-169` **实现**了陷波（`FILTER_NOTCH`）的系数公式：

```c
case FILTER_NOTCH:    /* 陷波：只掐掉 filterFreq 附近很窄的一段 */
    b0 =  1;  b1 = -2 * cs;  b2 =  1;
    a0 =  1 + alpha;  a1 = -2 * cs;  a2 =  1 - alpha;
    break;
```

但**全工程只有一个 biquad 初始化调用点**：`biquadFilterInitLPF()`（`accgyro.c:71`），
而它固定传 `FILTER_LPF`（`filter.c:193-196`）。
→ **结论：陷波器是实现完整但未被调用的功能**（属于"预留能力/移植自其他工程"）。

> **⚠ 手册对照**：手册 8.4 的表格里，"陷波（Notch）"一行的"你工程里的地方"写的是
> `FILTER_NOTCH` 类型。这句话**字面上没错**（类型确实存在），
> 但容易让读者以为"工程里正在用陷波"。
> 建议（**我不改手册**）在附录 D 里记为"表述可更精确"一类。

#### （f）一个真实的"参数与假设不一致"（🟡 推理，但依据是代码事实）

🟢 **代码事实**：

| 事实 | 位置 |
| --- | --- |
| IMU 的 **ODR（Output Data Rate，输出数据率）配成 200Hz** | `accgyro.c:64-66`（宏取值 `Icm426xxDefs.h:750/801`，注释 "200 Hz (5 ms)"） |
| 但滤波器的**采样周期按 1250µs（=800Hz）** 初始化 | `accgyro.c:71-72`（`1250` 与 `1.25e-3`） |
| 而姿态/PID 的执行门限是 **1.25ms** | `fc.c:82` `if(deltaT >= 0.00125f)` |
| 而主循环一圈的耗时注释值是 **4.6~7.3ms** | `main.c:399-402`（altitude_ctrl 2.1~3.873ms + flight_ctrl 2.493~3.446ms） |

🟡 **推论（我推的，未在硬件上测）**：
滤波器系数是按 800Hz 采样率算出来的，但**真实的新数据只有 200Hz**（每 5ms 一个），
而 `accgyro_update()` 被调用得更快（每 1.25ms 一次门限，实际受主循环限制可能是 5~7ms 一次）。
两种情况都会让"滤波器每一步的输入"与"系数假设"不匹配：

- 若调用比 ODR 快 → **同一份采样被反复滤波多次** → 等效截止频率**低于**标称值（更钝）；
- 若调用比 ODR 慢（主循环被拖慢时） → 部分采样被跳过 → 等效截止频率**高于**标称值（更少滤波）。

**这一段的意义不在于"算出一个正确的截止频率"**（那需要示波器/日志实测），
而在于记住一条工程习惯：**滤波器的系数是"采样率"的函数**。
改 ODR、改主循环周期、改调用频率时，**滤波器参数必须跟着复核** ——
否则你会看到一个"参数写着 240Hz、实际行为是别的值"的系统，
而且**任何调试都会变得没有依据**。

### ④ 实现方法有哪些（取舍对照表）

| 滤波器 | 原理一句话 | 计算量 | 相位滞后 | 最擅长 | 最不擅长 | 本工程 |
| --- | --- | --- | --- | --- | --- | --- |
| **一阶 IIR（PT1）** | 输出每步往输入挪一小步（等价于 RC 低通） | **最低**（1 乘 2 加） | 小 | 高频噪声、要求低滞后 | 需要陡滚降的场合（-20dB/十倍频太缓） | **✅ 陀螺 240Hz**（`accgyro.c:72`） |
| **二阶巴特沃斯（biquad LPF）** | 二阶 IIR，通带最平坦、无纹波 | 中（5 乘 4 加） | 中 | 需要陡滚降、又不允许纹波 | 相位敏感的环路 | **✅ 加速度 30Hz**（`accgyro.c:71`，Q=1/√2） |
| **FIR 滑动平均** | 取最近 N 个样本的平均 | 低（可用滑动和优化到 1 加 1 减） | **N 个样本的一半**（与 N 成正比） | 简单、线性相位 | 延迟要求高的场合 | 🟡 **部分**：`imu.c:426` 的 8 点指数滑动；`altitude.c:123-139` 的 6 点滑动和 |
| **中值滤波** | 取 N 个样本的中间值 | 低（5 点 7 次比较、7 点 13 次比较；`mlib.c:134/146`） | (N-1)/2 个样本 | **剔除突发野值**（尖峰、毛刺），线性滤波做不到 | 高斯噪声（效率不如平均） | **✅ 气压 5 点**（`altitude.c:19/88-90`） |
| **陷波（Notch）** | 只在某个窄频段挖一个"坑" | 中（与 biquad 同级） | 窄带外很小 | 掐掉已知的**单频**振动（如电机转速基频及其倍频） | 频率会漂移的振动（转速变化时坑要跟着动，需要"动态陷波"） | ❌ 代码有（`filter.c:160-169`）、**未调用** |
| **卡尔曼滤波** | 用模型预测 + 观测更新，按不确定性加权 | 高（矩阵运算） | 取决于模型，"最优" | 多传感器融合、能同时估零偏；🟡 在模型正确时理论最优 | 计算资源紧张、模型难建的场合 | ❌（本工程用互补滤波代替，见 8.5） |

**本工程的取舍一句话**：**"按信号特性分别下药"** ——
陀螺要低滞后 → 一阶；加速度要压振动 → 二阶；气压要抗野值 → 中值 + 平均 + 低通。
**没有一处用卡尔曼**，因为这套方案在 M0+、8KB SRAM、Flash 已用 95% 的约束下更划算。

### 8.4 小结

1. 必须滤波的核心理由（🟡）：**机架振动频率远高于姿态带宽，不滤会被积分/微分放大**；
2. 低通/高通的直观含义与截止频率的三条选取原则（低于振动、高于控制带宽、阶数换滚降）；
3. **本工程实测（🟢）**：陀螺 **PT1 240Hz**（`accgyro.c:72`，应用点 `:127`）；
   加速度 **biquad LPF 30Hz**（`accgyro.c:71`，应用点 `:126`）；
   气压 **中值 5 点 + 滑动平均 6 点 + 低通 α=0.1 + 速度低通 3/4 + 死区 100mm/s**
   （`altitude.c:19/88-90/123-139/169/174/180`）；PID 的 D 项另有 **3 点滑动和**（`pid.c:335-338`）；
4. **陷波器实现了但没有被调用**（`filter.c:160-169`，唯一的初始化调用点是 LPF 版本）；
5. 一个必须记住的隐患：**滤波器系数是按 800Hz 采样率算的，而 ODR 配的是 200Hz**
   （`accgyro.c:64-66` vs `:71-72`）—— 改采样率时滤波器参数必须复核。

## 8.5 气压计与定高

> **这一节回答什么问题**：气压为什么能当高度用？它的问题是什么？
> 为什么必须和加速度计融合？**本工程到底是怎么算出高度、怎么控制高度的？**

### ① 它是怎么出现的（物理链条，🟢）

🟢 **物理事实链条（每一环都可独立验证）**：

```text
   ① 大气压随高度上升而下降（因为越高，头顶的空气柱越短）
        ↓
   ② 低空近似：每升高约 8.5 m，气压下降约 1 hPa
      （精确值随高度与气温变化；本工程用的公式在**海平面附近**给出 8.33 m/hPa，见下）
        ↓
   ③ 所以反过来：测出气压 → 就能推出高度
        ↓
   ④ 但"气压 → 高度"不是线性的（越往高处，同样的高度差对应越小的气压差），
      所以要用**国际标准大气（ISA, International Standard Atmosphere）**的公式，而不是简单乘法
```

🟢 **本工程的公式与"8.33 m/hPa"的来历（可自行验算）**：

```c
/* imu/altitude.c:150 与 :164 —— 同一套公式，一处算地面基准、一处算当前高度 */
baroGroundAltitude = (1.0f - baro_pow_0p295((baroGroundPressure / 10.0f) / 101325.0f)) * 44330000.0f; //in mm
BaroAlt_tmp        = (1.0f - baro_pow_0p295(((float)baroPressureAvg)    / 101325.0f)) * 44330000.0f; //in mm
```

验算：

| 项 | 数值 | 说明 |
| --- | --- | --- |
| 海平面标准气压 `P0` | **101325 Pa** | 代码里直接写死，与 ISA 一致 |
| 系数 | **44330000 mm = 44330 m** | 与手册 8.5 里那个更常见的写法 `44330000 × (...)`（单位 mm）一致 |
| 指数（代码里叫 `baro_pow_0p295`） | **0.190295** | 而 `1/5.2559 ≈ 0.19026` —— 即 ISA 对流层公式里的 `R·L/(g·M)` 的倒数；代码取 0.190295 |
| 低空灵敏度（对公式求导） | `44330 m × 0.190295 / 101325 Pa ≈ 0.0833 m/Pa` | 换成 hPa：**≈ 8.33 m/hPa**（与手册说的"约每 8.5m 降 1hPa"同量级，差异来自取整） |

🟢 **确证（工程为了省 Flash 做了替换）**：`imu/altitude.c:1-7` 的注释说明，
`powf` 一旦被链接就会把 libm 里 4KB 以上的代码拉进固件，而 Flash 只有 64KB
（"实测正好差 200 字节装不下"），所以用了一个**自研的窄区间幂函数**
`baro_pow_0p295()` 代替。🟢 这一条同时解释了 `main.c` 里那句
"本工程 Flash 已用到 95%"（`bsp_timer.c:110-111`）的处境。

### ② 它要解决什么问题（没有它会怎样）/ 它自己的问题

| 气压计的固有难题 | 具体表现 | 本工程的应对（🟢） |
| --- | --- | --- |
| **噪声大** | 单次读数抖动会让高度跳几十厘米 | 中值 5 点（`altitude.c:88-90`）+ 滑动平均 6 点（`:123-139`）+ 高度低通 α=0.1（`:169`） |
| **受气流影响** | 🟡 螺旋桨下洗气流、开关舱盖、手挡住进气孔都会让气压**突变** | 中值滤波专门去这种"突发野值"（`mlib.c:103-108` 注释就写了这点）；原厂驱动侧还有 IIR 系数 3（`common.c:402`）压螺旋桨气流抖动（`common.c:367` 注释明确写了这个用途） |
| **天气变化导致基准漂移** | 🟡 天气系统过境时海平面气压一天内可变化几个 hPa → 对应几十米的高度误差；**绝对高度不可靠** | **只算相对高度**：起飞前用地面积累的 `baroGroundPressure` 当基准（`altitude.c:144-157`），之后 `BaroAlt_tmp -= baroGroundAltitude`（`:167`） |
| **对姿态敏感** | 机身倾斜时，桨盘气流与机身遮挡都会改变局部气压 | 高度环只在 `tiltAngle < 8000`（即 80°）时才计算（`altitude.c:295`），注释写明理由"确保推力方向基本向下" |
| **安装/朝向敏感** | 进气孔朝向、泡棉、风道都会影响读数 | 🟢 硬件层：BMP390 与 IMU 共用一个 SPI（`common.c:142-143`），片选 PB7（`main.c:262` 注释） |

🟢 **确证（"起飞点当基准"的实现）**：

```c
/* imu/altitude.c:144-157 —— 只在"校准阶段或未解锁"时更新地面基准 */
if ((calibratingB>0) || (!fc.flags.motorArmed && !fc.flags.motorIdle)) {
    if(calibratingB == BCALIBRATING_BARO_CYCLES) baroGroundPressure = baroPressureAvg * 10;
    baroGroundPressure -= baroGroundPressure / 10;    /* 递归平均（10 倍时间常数） */
    baroGroundPressure += baroPressureAvg;            /* 新样本权重 1/10 */
    baroGroundAltitude = (1.0f - baro_pow_0p295((baroGroundPressure / 10.0f) / 101325.0f)) * 44330000.0f;
    vel = 0;  accAlt = 0;                             /* 顺带把速度和加速度积分清零 */
    if(calibratingB > 0) calibratingB--;              /* BCALIBRATING_BARO_CYCLES = 50（altitude.c:15） */
}
```

- `*10` / `/10` 是**定点技巧**：用整数放大 10 倍来保留一位小数（`baroGroundPressure` 的
  有效精度因此提高一档）；
- 只在"未解锁"或"校准期"更新，**起飞后基准冻结** —— 这是"相对高度"的关键。

### ③ 为什么要和加速度计融合（🟢 结构 + 图）


🟢 **确证（权重与"时间常数"）**：
`accAlt = accAlt*0.985 + BaroAlt*0.015` 是一个一阶低通形式的互补滤波，
它的"纠正时间常数" ≈ 1/0.015 ≈ **67 个更新周期**。
而 `getEstimatedAltitude()` 由 20ms 节拍驱动（`altitude.c:416`）→ 约 **1.3 秒**。
含义：**气压计用大约 1 秒多的时间尺度去"纠正"加速度积分的漂移**，
而这个时间尺度远慢于真实的高度变化（所以不会把真实运动当漂移滤掉）——
这一条是互补滤波参数选取的通用思路（🟡 通说），不是本机实测。

🟢 **确证（速度环的互补权重更"信任加速度"）**：`vel = vel*0.995 + baroVel*0.005`
→ 时间常数 1/0.005 = **200 个周期 ≈ 4 秒**。速度比高度更"信加速度"，
因为气压算出来的速度（`baroVel`，`altitude.c:174` 由高度差分放大 8 倍）
噪声更大。

### ⑤ 实现方法有哪些（取舍对照表）

| 方案 | 组成 | 能得到什么 | 代价 / 局限 | 本工程 |
| --- | --- | --- | --- | --- |
| **① 只用气压** | 气压计 + 低通 | 实现最简单；高度**不随时间漂**（相对基准） | 噪声大、滞后大；气流/遮挡会造成误动作；无法跟踪快速高度变化 | ❌（本工程用了气压，但**不是只用**气压） |
| **② 气压 + 加速度互补（本工程）** | 气压计 + 加速度计 + 两组互补权重 | 计算量极小（几次乘加）；既有气压的长期稳定，又有加速度的短期响应 | 权重靠调；加速度的二次积分对零偏极敏感（漂移 ∝ t²）；模型简单，抗扰能力一般 | **✅ `altitude.c:259/268`** |
| **③ 卡尔曼滤波** | 状态 = [高度, 垂直速度, 加速度零偏]，用气压当观测 | 理论上最优；能同时**估计加速度零偏**（这是互补滤波做不到的）；可以给出置信度 | 计算量大（本工程无 FPU、Flash 已 95%）；Q/R 参数难调；模型错就发散 | ❌ |
| **④ 超声波辅助** | 向下打超声波测距，近地面精度高 | 🟡 近距离（几米内）精度高、不受气压影响；常用来做"低空定高/着陆缓冲" | 🟡 作用距离短、受地面材质与倾角影响、易受桨气流与噪声干扰；多一个传感器与接口 | ❌ |
| **⑤ 激光定高（LiDAR/ToF）** | 激光飞行时间测距 | 🟡 精度高、指向性好、距离比超声波远 | 🟡 成本高；对反射率/灰尘/强光敏感；室外远距离受限 | ❌ |
| **⑥ GNSS 高度** | 卫星定位给出海拔 | 绝对高度、可全局使用 | 🟡 垂直精度远差于水平精度；更新率低；室内无效 | ❌（本工程无 GNSS） |

**本工程的取舍一句话**：**"气压 + 加速度互补"是"零额外硬件 + 极低算力"下能做到的最好方案；
它的天花板由两件事决定 —— 气压计的噪声（滤波能压，但会引入滞后）
和加速度计的零偏（互补滤波压不住长期漂移，只能靠气压慢慢拉回）。**

### 8.5 小结

1. **气压能测高度的物理链条**：气压随高度下降（低空约 8.5 m/hPa；本工程公式在海平面给出
   **8.33 m/hPa**，可自行求导验算）→ 反过来由气压推高度，但必须用**非线性**的 ISA 公式
   （`altitude.c:150/164`，系数 44330000 mm、指数 0.190295）；
2. **气压计的问题**：噪声、气流/遮挡、天气导致的基准漂移 —— 本工程的应对是
   "中值 + 平均 + 低通" + "**用起飞点气压当基准、只算相对高度**"（`altitude.c:144-167`）；
3. **必须与加速度计融合的理由又是一次"互补"**：气压长期准、短期噪声大；
   加速度短期准、积分会漂 —— 融合就是 `altitude.c:259/268` 的两行互补滤波；
4. **本工程的实测参数**：BMP390（`common.c:397-414`，气压 8X / 温度 2X / IIR 3 / FORCED）、
   高度环 20ms（`altitude.c:416`）、位置环 P=1.1 + 速度环 P/I/D=1.25/0/3.0
   （`altitude.c:303-306`）、油门基准 1500+BaroPID（`pid.c:122`）。

### D-1（第 8.2 节，手册第 931-933 行）引用的代码片段与代码不符


**两处差异**：

1. **数值**：40 → 实际是 **50**；
2. **注释**：手册引的那句"实测静止时陀螺仪抖动 < 20，取 2 倍余量"**在代码里不存在**

### D-2（第 8.2 节，手册第 923 行）"分辨率"一行的示例值与本工程量程不符

**手册原文**：

> | **分辨率 / LSB** | 每个数字量对应的物理量（如 2048 LSB/g） | 换算原始值 → 物理量 |

**当前代码**：本工程加速度计量程是 **±8g**（`accgyro.c:64`），
对应常量 **`acc_1G = 4096`**（`accgyro.c:35`），而不是 2048。
`2048 LSB/g` 对应的是 **±16g** 档（32768/16 = 2048）。

**影响**：该行的第三列标题是"**你工程里的体现**"，读者容易把 2048 当成本工程的换算值。
建议改成 4096 LSB/g（±8g）；另外陀螺侧的对应值是 **16.4 LSB/(°/s)**（`accgyro.c:36`）。

**附一条术语层面的小意见**（🟡 我的看法，供参考）：把"每个数字量对应的物理量"叫
"分辨率"其实是**灵敏度**（sensitivity）的定义；"分辨率"更常用于指"能分辨的最小变化量"。
两者在传感器手册里常被混用，但在教学文本里分开更清楚。

### D-3（第 8.4 节，手册第 965 行）陷波器一行容易被读成"工程在用它"

**手册原文**：

> | **陷波（Notch）** | 只掐掉某个窄频段（如电机转速对应的振动） | `FILTER_NOTCH` 类型 |

**当前代码**：

- 也就是说：**陷波器是实现完整、但未被任何代码调用的功能**。

### D-4（第 8.3 节，手册第 951-952 行）欧拉角的来源写成了四元数

**手册原文**：

> **欧拉角**：最终给人看的"俯仰/横滚/偏航"角度，由四元数换算而来
> （`imuUpdateEulerAngles()` → 全局 `angle[]`，单位是"度×100"）。

**当前代码（`imu/imu.c:372-377`）**：

```c
void imuUpdateEulerAngles(void)
{
    angle[ROLL]  = (int32_t)(atan2_approx(rMat[2][1], rMat[2][2]) * (18000.0f / M_PI));
    angle[PITCH] = (int32_t)(((0.5f * M_PI) - acos_approx(-rMat[2][0])) * (18000.0f / M_PI));
    angle[YAW]   = (int32_t)((-atan2_approx(rMat[1][0], rMat[0][0]) * (18000.0f / M_PI)));
```

`imuUpdateEulerAngles()` 是从**旋转矩阵 `rMat`** 算的，不是直接由四元数算的。
工程里**确实有**一个"四元数 → 欧拉角"的函数 `to_euler()`（`imu.c:161-185`），
但它只被 `imuCalculateAcceleration()` 内部使用（`imu.c:200`），**不产生全局 `angle[]`**。

**影响**：结论（角度的最终表示、单位、给人看）都对，只是"由谁换算"指错了函数。
严格说法是："`rMat`（由四元数每帧重建，`imu.c:348`）→ `imuUpdateEulerAngles()` → `angle[]`"。

### D-5（第 8.5 节，手册第 988 行）"串级（高度环 + 姿态环）"的措辞

**手册原文**：

> **定高的控制结构**：**串级**（高度环 + 姿态环）

**当前代码**：本工程有**两个各自独立的串级**，它们在**油门混控**处相加，不是互相嵌套：

1. 高度通道内部的串级是**位置环 → 速度环**（`imu/altitude.c:312-314` → `:367-383`），
   输出 `BaroPID`；
2. 姿态通道内部的串级是**角度环 → 角速度环**（`imu/pid.c:259-261` → `:304-338`），

3. 两者在 `PIDMIX()` 里相加（`imu/pid.c:118-127`）。

**影响**：把"高度环 + 姿态环"称为串级（cascade）会让读者以为姿态环是高度环的内环。
实际是**两个并列的通道，输出在混控层叠加**（这也正是 `PIDMIX` 存在的意义）。

# 附录 F　如果只记五句话

1. **心跳**：接收方没有直接手段判断"对方活着"，只能用"**周期性信号 + 超时阈值**"
   把"这一帧没收到"升级成"连续 N 次没收到"；本工程的心跳是**寄生在数据帧上的隐式心跳**
   （`deal_pack.c:257`），还靠 **ACK 载荷**做了一次反向确认（`bsp_pn298.c:1202-1206`）。
2. **软定时器**：一个 1ms 硬件时基扇出多个软件计数值（`bsp_timer.c:113-116`、`:178-190`），
   换来"任意多个周期任务"；代价是**实际周期是 N+1**、**精度受主循环限制**、
   **忘记清零就永久失效**，而且这四个计数器**都没加 `volatile`**。
3. **失效保护**：阈值不是技术常数而是"**动作代价的函数**" —— 飞控侧 **5000ms**
   对应不可逆的"自动降落"（`main.c:462-465`），遥控器侧 **1000ms**
   对应可逆的"报警 + 重连"（`遥控器 tim16.c:79-86`）。
4. **姿态**：MEMS 陀螺输出的是角速度，积分必然漂；所以用**加速度计的重力方向**
   当不漂的参照（Mahony，`imu.c:261`，Kp=0.25/Ki=0.0025）；
   姿态用**四元数当状态、矩阵当工具、欧拉角当输出**；无磁力计 ⇒ 偏航角被强制清 0（`pid.c:247`）。
5. **滤波与高度**：一切都围绕"**互补**"两个字 ——
   **陀螺短期准/长期漂 ↔ 加速度长期准/短期抖**（滤波：陀螺 PT1 240Hz、加速度 biquad 30Hz），
   **气压长期准/短期噪 ↔ 加速度短期准/长期漂**（`altitude.c:259/268` 两行互补滤波）。
   **没有任何一个传感器是好用的 —— 这就是整章的全部内容。**
