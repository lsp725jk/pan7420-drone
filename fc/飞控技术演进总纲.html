顺序错误现象为什么
spi_init() 放到 accgyro_init() 之后IMU 读不到数据，姿态角永远是 0外设没初始化，等于对着空气说话
bsp_rfspi_init() 放到 bsp_pn298_init() 之后射频寄存器读回全 0xFF，永远收不到对码包软件模拟 SPI 用普通 GPIO，没配模式就推不动电平
SystemClock_Config() 放到 bsp_init() 之后波特率/PWM/心跳全按 8MHz 算（约 6 倍偏差）所有分频系数都相对 PCLK1
WDG_init() 放到对码循环之前约 0.5s 复位一次，"灯一直闪、就是配不上"IWDG 停不掉，而对码循环里没喂狗
WDG_init() 放到主循环之后看门狗根本没启动 → 完全没有兜底少调一次就是少一层保护
tim16_init() 放到 flight_ctrl() 之后deltaT 算成 0 或巨大值 → PID 不收敛时间戳外设没启动

1.4 "坏了会怎样"速查表#

层一句话职责典型失效现象
① 电源供电反复重启、射频距离骤短、ADC 读数乱跳
② 时钟定节拍串口乱码但换波特率就好；PWM 频率不对；控制周期不对
③ 内核执行指令HardFault → 死循环 → 看门狗复位 → 飞机周期性重启
④ 外设让硬件重复干活定时器不中断、SPI 读不出、ADC 值不变
⑤ BSP引脚与顺序寄存器读回全 0 或全 0xFF
⑥ 驱动型号专有配置数据削顶、ODR 不匹配、校准失败
⑦ 传感器/射频感知与通信姿态不响应、遥控无反应
⑧ 姿态解算与滤波原始值→姿态角悬停时飞机慢慢歪；对振动敏感
⑨ 控制律误差→修正量电机嗡嗡响、机身发抖（D 大）或低频摆（P 小）
⑩ 执行输出数字→推力解锁后电机无反应，或突然狂转
⑪ 遥控与失效保护断链后的安全动作遥控关机，飞机不降落，一直飞走

🟢 设计品味：选时钟频率优先选能被整除的值 —— 48MHz 之于 1ms 很舒服，47.5MHz 不是。 本工程 48MHz 能被 48/480/4800/32 整除，所以能凑出整数微秒/毫秒（main.c:111-112）。

🟢 "选量程"本身是一次取舍：±8g 时分辨率 ≈ 8g/32768 ≈ 0.00024 g/LSB； 改 ±16g → 分辨率差一倍，但剧烈机动不削顶；改 ±2g → 分辨率更好，但稍大的振动就饱和， 姿态解算的输入变成方波（滤波器还以为是真的）。

🟢 校准的物理前提是"静止且水平"：陀螺仪静止时输出不为 0，这个非零值叫零偏， 随温度和时间缓慢变化，必须现场测出来再减掉（accgyro.c:121）。 代码用"陀螺仪输出抖动是否足够小"判断静止（GYRO_CALI_DIFF_LIMIT = 40）。 校准时飞机在动 → 把"运动"当成零偏减掉了 → 一解锁就往一个方向偏。

量程配错但换算系数没跟着改实际倾斜 30°，代码认为 15°
没有零偏校准陀螺积分持续漂移（见 2.5）
忘了做安装方向校正横滚与俯仰装反：想往前倾实际往右滚 → 一起飞就翻

🟢 截止频率是"两头都会出事"的参数：选高（400Hz）→ 响应快、手感跟手，但振动滤不掉， D 项放大噪声；选低（80Hz）→ 干净、电机凉，但相位滞后大 → 飞机发飘、修正不及时， 严重时振荡发散。没有标准答案，必须按机架实测。

🟢 一个必须记住的前提：滤波器的系数是按采样率算的。 本工程 ODR 配 200Hz，而两个滤波器按 1250µs（=800Hz）设计（accgyro.c:65-66 vs :71-72） → 同一份采样被重复滤波，等效截止频率偏离标称的 30Hz / 240Hz （术语手册 11.5 节 B 组第 1 条）。改了 ODR 或调用周期，必须回来复核滤波参数。

🟡 为什么加速度计用 Biquad 而陀螺用 PT1：加速度计噪声更大、对振动更敏感， 需要更陡的衰减（Biquad 是 −40dB/十倍频，PT1 只有 −20dB）； 而陀螺仪是内环反馈信号，相位滞后直接吃掉稳定裕度，所以用滞后更小的 PT1。

失效现象
完全不滤波电机高频啸叫 + 机身发麻；D 项在正负之间狂跳
截止频率设太低飞机"迟钝"、修正滞后；大幅机动后回正很慢，像泡在水里
只滤姿态角、不滤陀螺原始值内环（角速度环）仍然吃噪声 → 抖动依旧

2.5 怎么由角速度得到姿态（积分漂移 → 互补 / 卡尔曼）#

示意图
 【只用陀螺仪：短期准、长期漂】
   angle(t) = ∫角速度 dt，零偏 b 也被一起积分 → angle(t) = 真实角度 + b·t
   b 哪怕只有 0.1°/s：1 分钟 = 6° 误差，10 分钟 = 60° 误差
   现象：刚起飞还行，飞一会儿开始自己往一边歪，而且【越修越歪】
        —— 因为飞控以为自己在歪，其实是它算错了

 【只用加速度计：长期准、短期抖】
   静止时能测出重力方向 → 绝对倾角，不会漂
   但它同时也测到"运动加速度"和"振动"

🟢 为什么用四元数而不是欧拉角：欧拉角在俯仰接近 ±90° 时万向节死锁 （横滚与偏航的旋转轴重合，数学上退化），而飞控要做空翻（flip.c）， 必然经过 ±90°；四元数无死锁，只需 4 个数，且更新过程不需要三角函数 —— M0+ 没有 FPU 也扛得住。最终给人看时再换算成欧拉角。

失效现象
完全不融合，只积分陀螺飞机越飞越歪，最终侧翻；重新上电又正常（零偏重新校准了）
融合权重太重（太信加速度计）一加速就抖；机架振动被当成姿态误差
融合权重太轻（几乎只信陀螺）退化成"只积分"，漂移照样发生
加速度计失效（如 SPI 断了）却仍参与纠正姿态角被错误的重力方向拉走 → 突然自旋或侧翻
deltaT 保护缺失计数器回绕算出 65ms 的巨大 deltaT → 四元数跳变 → 姿态角瞬间跳几十度

2.6 怎么根据姿态决定动作（控制律、周期、限幅）#

没有这一步会怎样：飞机只是一个"会飞的姿态显示器"，必须全程手动修正，风一吹就翻。

示意图
 遥控摇杆 rcCommand[axis]（−500~+500）
   │ ×20 → −10000~+10000（对应 ±100 度，因为 angle[] 是"度×100"）
   ▼
 期望角度 = constrain(20·rcCommand, ±30000) + trim − angle[axis]   ← 减去实际角度 = 角度误差
   │ × PAngleToRate（ROLL/PITCH=1.0，YAW=0.3）
   ▼
 期望角速度 target_rate            ← 外环（角度环）的输出
   │ − accgyro.gyroData[axis]      ← 陀螺仪直接测出的真实角速度
   ▼
 角速度误差 → P（×PRate）+ I（×IRate×deltaT，限幅）+ D（限幅）
   ▼
 各轴修正量 → PIDMIX 混控 → motorPWMValue[4]

🟢 "为什么串级"的物理理由：单环（只有角度环）也能飞，但响应慢 —— 等角度真的偏了才修，修的时候风已经把它推得更远。 内环用陀螺仪做反馈，每 1ms 就有新值，比角度环快得多。 外环负责"该转到什么角速度"，内环负责"立刻达到这个角速度"。

🟢 控制周期是本工程最容易被误解的地方：

示意图

   fc.c:82 的 1.25ms 门槛只防"同一周期被重复执行"，
   它压不到 1.25ms —— 因为主循环本来就跑不了那么快。

这个事实带来三个结果：① PID 里的 deltaT 必须实测，不能写死 1ms （代码正是这么做的，fc.c:79-81）；② 周期抖动直接体现在 I/D 项上 —— altitude_ctrl() 耗时在 2.1~3.873ms 间浮动，意味着 deltaT 有约 1.8 倍抖动量； ③ 想让姿态环真跑 1kHz，得把控制链搬进中断，但那会带来重入、栈、阻塞等新问题。

🟢 限幅为什么必须有：积分饱和（windup） —— 目标角速度长期达不到（比如被风顶住）时 积分项会一直累加，条件一反转就要很久才"退掉" → 猛冲过头再慢慢回来 （本工程限幅 _imaxPR=350、_imaxYaw=228，pid.c:316-319）。 输出限幅 —— motorPWMValue 是 uint16_t 千分比，混控算出负值再赋给无符号数会回绕成 65436 → PWM 满油门。本工程只在 bsp_pwm.c:152 兜住上界，没兜下界 （bsp_pwm.c:203-208 有明确说明）。

没有这一步会怎样：算得再对也不动；或者更糟 —— 四路不一致导致机身瞬间抖一下。

示意图

   ▼

🟢 为什么"四路必须连续写完"：本工程 AutoReloadPreload = DISABLE（bsp_pwm.c:100）， 写 CCR 立即生效，不等下一个 PWM 周期。如果分四次写、中间被打断， 在那个瞬间四个桨的推力组合既不是旧姿态也不是新姿态 → 机身"抽搐"一下。 16kHz 下周期只有 62.5µs，这个风险窗口相对更大。

🟡 为什么是 16kHz：太低（50~400Hz）→ 控制延迟大、电流纹波大，电机"啸叫+抖动"； 太高（>32kHz）→ 部分电调不认、MOS 开关损耗上升。8~16kHz 是通行区间（多数数字电调支持）。

失效现象
PWM 频率算错（按 24MHz 而非 48MHz 算）实际频率差一倍，部分电调不认 → 电机不转或间歇转

3.1 第一次跃迁：从"能飞"到"能自主" —— 为什么需要姿态解算#

示意图
 【跃迁前：人在回路里当控制器】
  飞手眼睛 ─看姿态─► 飞手大脑 ─算修正量─► 摇杆 ─► 飞控 ─► 电机
     ▲                                                    │
     └────────────── 飞机姿态变化 ◄────────────────────────┘
  优点：飞控极简单。  缺点：飞手必须【持续】修正。

 【跃迁后：飞控当内环控制器，人只给意图】
  飞手 ──给意图（要多斜/多快）──► 飞控 ──► 电机
                                  ▲  │
                                  │  ▼
                            姿态解算 ◄── 陀螺仪 + 加速度计（毫秒级闭环）
  人负责"去哪里、多快"（慢回路，秒级）；飞控负责"保持这个姿态"（快回路）

🟢 为什么"人当控制器"撑不住：人的反应时间约 0.2~0.3 秒（🟡 生理学通说）。 在这段时间里，一阵 3m/s 的侧风足以让小四轴倾斜十几度，而这十几度会继续带来水平速度 —— 误差是累积的。更本质的是：飞手看到的是"结果"（姿态歪了）， 而修正需要"原因"（角速度多少、要抵消多少），人脑做这个反推有延迟， 延迟在闭环控制里直接降低稳定裕度。在持续扰动（风）下，"人当控制器"的闭环带宽不够 —— 这不是飞手技术问题，是物理限制。

🟢 为什么这一步必然要求姿态解算：要闭环控制姿态，先得测出姿态。 陀螺仪给角速度、可积分但会漂；加速度计给绝对倾角、不漂但噪声大且受运动加速度污染。 两个都不够用 → 必须融合 → 这就是"姿态解算"这一层存在的必然性。 换句话说：姿态解算不是"有人发明了一个算法"，而是"想要快回路闭环"逼出来的产物。

连锁需求：滤波（内环吃噪声 → D 放大 → 电机抖）、精确时基（积分微分都要 dt）、 零偏校准（不然积分必漂）、安装方向校正（芯片焊向与机体轴不一致）、 限幅（积分饱和与输出回绕）、更高主频（浮点 + 三角函数，且无 FPU）—— 对应本工程 filter.c、TIM16.c 的 micros16()、accgyro.c 的校准与 CW90_DEG、 pid.c:316、main.c:120 的 48MHz。

🟢 "跳频"在本工程的实际状态（需要澄清）：main.c:80 初始化 ch_change_arr[2] = {36, 36}（两个值相同，看起来不跳频）， 但 main.c:265 会把 ch_change_arr[1] 覆盖成 Flash 里存的对码信道。 所以本工程确实会跳频 —— 两个候选频点分别是"出厂默认 36"和"对码时协商的信道"。 代码结构保留了"每 500ms 换一次信道扫描"的能力（main.c:82-88）。

失效保护阈值是"两头都错"的取舍（见 2.9 的表）

示意图

去掉哪一层立刻出现的故障
CRC噪声字节被当合法包 → 舵量随机跳 → 失控
ACK发送方不知道包丢了 → 遥控"偶尔失灵"，且飞控不知道
重传一次丢包就是一次指令缺失 → 指令序列出现空洞
PID 去重重传包被当新包执行两次 → 舵量被重复施加
心跳链路断了飞控不知道 → 一直用旧指令
失效保护知道断了但什么也不做 → 照样飞走
看门狗判断"失联"的代码本身卡死 → 失效保护也不会执行

"纵深防御"的工程含义：每一层都假设下面那层会失效。 这不是不信任，而是可靠性设计的基本姿态 —— 各层失效模式不同， 叠加起来能覆盖的故障类型远比单层多。

5.1 系统时基：硬件定时器中断 / SysTick / 主循环计数 / RTOS tick#

做法解决什么适用场景代价本工程
硬件定时器中断精确、独立的周期节拍周期要确定、抖动要求高占一个硬件定时器；优先级要安排；中断里不能长跑✅ TIM17 → 1ms 任务节拍（main.c:235）
SysTick内核自带，不占外设HAL 时基、一般超时计时只有一个；HAL 占了就不能另作他用✅ HAL_GetTick() 的 1ms（py32f0xx_it.c:141）
主循环计数零硬件成本对时间精度要求极低精度取决于循环负载，负载变则周期变⚠ 本工程的 _cnt* 属"中断计数 + 主循环判断"，介于两者之间
RTOS tick统一节拍 + 抢占，给所有任务任务多、有优先级与阻塞需求栈内存、切换开销、可重入要求、优先级反转❌ 未采用（py32f0xx_it.c:121-126 明确裸机）

🟢 为什么本工程同时用 TIM17 和 SysTick 两个都是 1ms 的节拍： 都用 SysTick → HAL_Delay() 阻塞时会污染任务节拍；都用 TIM17 → HAL 的超时逻辑全依赖 HAL_GetTick()，改掉要动整个 HAL。两个独立节拍 = 互不污染的"两个时钟"， 代价是多占一个定时器 + 一次中断开销（py32f0xx_it.c:158-161 写了这个理由）。

失效现象（如果合成一个）：初始化阶段（还没进主循环）若调用了 HAL_Delay()， 两个节拍合一时任务计数器会被"凭空推快"，表现为"上电后第一次控制周期异常短" → deltaT 异常 → 积分项第一次就冲高。

5.2 任务调度：超级循环 + 软定时器 / 时间片轮询 / RTOS 任务 / 中断驱动#

做法解决什么适用场景代价本工程
超级循环 + 软定时器用最少资源跑多个周期任务任务数少、耦合松、无阻塞需求慢任务拖慢全部；周期精度受负载影响；共享变量要自己保证安全✅ 就是本工程（main.c:371-489）
时间片轮询每任务轮流得到固定时间片任务粒度均匀、要"公平"需保存/恢复上下文；片太小则开销大❌ 未采用
RTOS 任务抢占式优先级、阻塞/唤醒语义任务多、优先级明确、需要同步原语RAM（每任务一份栈）；切换开销；可重入与优先级反转；调试更难❌ 未采用
中断驱动事件一来立刻响应，延迟最小硬实时、事件稀疏中断里不能长跑；共享数据要原子；嵌套要设计部分（TIM17/SysTick 只计数）

5.3 传感器读取：阻塞轮询 / 中断触发 / DMA / 定时器触发#

做法解决什么适用场景代价本工程
阻塞轮询实现最简单，时序完全可控低速传感器、初始化阶段、单任务环境CPU 空转等待；外设不响应就可能永久卡死✅ 主路径（accgyro.c:96；射频也是轮询，config_rf.h:72）
中断触发（DRDY）CPU 不用等，数据到了才醒采样率不高、需要对采样时刻多占一个引脚 + 一个中断❌ 不用（accgyro.c:16 的 USE_CLK_IN = 0）
DMA外设与内存自动搬数据，CPU 不参与高速/大批量传输占 DMA 通道；缓冲一致性与半传输中断要处理；调试更抽象❌ 不用（芯片只有 3 通道 DMA，参考手册第 20 页图 3-1）
定时器触发采样时刻由硬件决定，抖动最小需要严格等间隔采样（滤波系数按固定采样率设计）需要定时器 + 触发路由；采样率被硬件固定❌ 不用

🟢 本工程的量级不匹配（必须知道）：传感器 ODR 配的是 200Hz（accgyro.c:65-66） ＝ 每 5ms 一个新数据，而代码按主循环节拍（≥4.6ms）去读 → 有时读到同一个样本，有时跳过样本。 后果：滤波器按"1250Hz 采样率"初始化（accgyro.c:71-72），而实际读取节拍是"主循环节拍"， 两者不一致；imu.c:426 的滑动平均在数据没更新时等于把同一个值重复平均，平滑效果比预期强。 这不是 bug 报告，而是"选了轮询就得不到严格等间隔采样"的必然结果。

5.4 姿态解算：互补滤波 / Mahony / Madgwick / EKF / 余弦矩阵#

做法解决什么适用场景代价本工程
一阶互补滤波最简单地融合"快的陀螺"与"准的加速度计"只要横滚/俯仰、MCU 极弱只能处理两轴（欧拉角表示）；漂移抑制有限；有万向节死锁❌ 姿态不用（但 altitude.c:259 的高度融合是同一思路）
Mahony（互补 + 四元数）四元数表示 + PI 反馈纠正陀螺漂移需要 3 轴姿态、无磁力计或磁力计不可靠要调 dcm_kp/dcm_ki；偏航无绝对基准（缓慢漂）✅ 本工程用它（imu.c:261）
Madgwick梯度下降求最优姿态，收敛快需要更好动态性能、计算资源稍宽裕比 Mahony 多几步运算；增益也要调❌ 未采用
EKF显式建模噪声，理论最优估计传感器多（磁力计/GPS/光流）、需要协方差矩阵运算（无 FPU 时代价极大）；参数多难调；代码量大❌ 未采用
余弦矩阵（DCM）直接更新用旋转矩阵表示，配合正交化需要避免四元数归一化漂移9 个元素 vs 4 个；每次要正交化部分（imu.c:6 的 rMat 由四元数算出，不是独立更新）

🟢 为什么选 Mahony 而不是 EKF：① 本芯片没有 FPU（数据手册第 6 页特性表整段未提 FPU）， EKF 的矩阵乘法与求逆全是软件浮点，时间与 Flash 都撑不住（本工程 Flash 已 95%+）； ② 本工程没有磁力计（ICM42688 是 6 轴），偏航无绝对基准 —— 本工程的应对很干脆：pid.c:247 直接 angle[2] = 0，偏航只做角速度控制。

🟢 "没有磁力计"的完整后果链：6 轴 → 偏航无绝对参考 → 只能靠陀螺积分 → 持续漂移 → pid.c:245-247 把 angle[2] 强制清零，偏航只做角速度控制 → 飞机不能"锁头" （不能保持朝向），但能正常飞，因为偏航本来就靠目视手动修正。 这不是"缺了个功能"，而是硬件选型决定的能力边界。

5.5 高度融合：只用气压 / 互补 / 卡尔曼 / 超声辅助#

5.6 通信可靠性：单发 / ACK+重传 / 跳频 / 心跳+失效保护#

做法解决什么适用场景代价本工程
单发延迟最低、最简单允许丢包，或有别的机制兜底丢包无人知道部分（飞机侧基本只被动收 + 回 ACK，bsp_pn298.c:952）
ACK + 重传让发送方知道"到了没有"指令类数据（不能丢）应答窗口时序紧（bsp_pn298.c:1168 用 delay_us(30)）；重传延迟不确定✅ ARD=250µs、ARC=3（手册第 33 页）
跳频避开被占用的频点、抗窄带干扰ISM 等拥挤频段双方必须同步跳频序列；切换期间无法通信✅ 出厂 36 + 对码协商信道（main.c:265）
心跳 + 失效保护确认链路"整体"还在，并定义断了之后做什么任何无人值守的遥控系统空口时间占用；阈值两头都错的取舍✅ 5 秒超时 → 自动降落（main.c:462）

🟢 "重传 3 次"意味着什么延迟：ARD=250µs、ARC=3（手册第 33 页）⇒ 最坏 3 次重传 = 4 次发送尝试，单包最坏延迟 ≈ 3×250µs + 4 次传输时间（1Mbps 下每包几十 µs） ≈ 1ms 量级。这与本工程"主循环 ≥4.6ms"同数量级 ⇒ 一次重传对控制节拍几乎无感； 但若 ARC 设成几十次，延迟就会明显到影响手感。

6.2 怎么用"故障反推法"读别人的飞控代码#

核心思想：不要从 main() 顺着往下读（会被细节淹没）， 而是先找安全机制，再找算法。因为安全机制的位置是被约束死的， 它们像"骨架上的关节"，找到了就能定位整个结构。

示意图
 第 1 步：找失效保护
   关键词：failsafe / bLanding / connection / timeout / 超时
   本工程：main.c:462 的 HAL_GetTick() − connection_nowtime > 5000
   ★ 一找到它就知道：系统有"链路健康"这个概念 → 心跳一定在某处刷新
     → 刷新点就是"合法包解析成功"处（deal_pack.c:257）
     → 触发后干什么 = "安全动作"的定义

   关键词：IWDG / WWDG / Refresh / 喂狗 / WDG_init
   本工程：WDG.c:63 的 WDG_init()、main.c:414 的 HAL_IWDG_Refresh()
   ★ 一找到它就知道：启动时机 = 初始化流程的终点；喂狗位置 = 调度结构的"一圈结束"；

8.1 《术语解析手册》正文中可能存在的事实问题（仅记录，未改动任何文件）#

说明：下面是本文档在核对代码时发现的、与《术语解析手册》正文表述不一致的地方。 本文档没有修改任何现有文件，只在此列出，供你自行判断与处理。 判断依据一律给出 文件名:行号。

#手册位置手册原文要点代码事实依据
1第 8 章开头（fc.c 相关表述）「本文件只有 33 行，但它是整个飞控的"心脏起搏器"……flight_ctrl() 每 1 毫秒执行一次的完整控制链路」fc.c 实际 115 行（不是 33 行）；更关键的是控制环不在 1ms 中断里：flight_ctrl() 由主循环每圈调用，主循环一圈至少约 4.6ms，并有 deltaT >= 0.00125f 限频保护fc.c 全文 115 行；main.c:402 调用 flight_ctrl()；main.c:399/:402 注释标注耗时 2.1~3.873ms / 2.493~3.446ms；fc.c:82 限频门槛
2第 9 章 其它常见术语速查（PWM 行）「PWM …… 电调标准 1000~2000µs」本工程不是 1000~2000µs 舵机/电调标准脉宽，而是 16kHz 固定频率 + 0~1000 千分比占空比。main.c:244 的 Advanced_Timer3_PWM_Init(3-1, 1000-1) → 48MHz/3/1000 = 16kHz；占空比由 CCR 直接写main.c:244；bsp_pwm.c:150-185（CCR = NewDuty*1000/1000）；术语手册 11.1 节自己也记了"8kHz vs 16kHz"这条
3第 5.4 节 喂狗位置 后的反面教材「bsp_pn298_tx_data() / tx_data_ack() 里有 while(!(状态 & TX_DS_FLAG)); 这种无超时的死等」。用来论证"飞机侧会卡死在这里"该死等确实存在（bsp_pn298.c:965），但它在飞机侧的实际收包主路径上不会被调用：飞机侧用的是 bsp_pn298_rx_data_ack_fix()，文件头明确写"飞机侧从不主动发数据（只回 ACK）"。所以"飞机侧会卡死在这里"的说法偏重bsp_pn298.c:965（死等确实存在）；bsp_pn298.c 文件头第 27-30 行与第 952 行（"被动收包 + 顺路回 ACK，几乎不主动发包"）；config_rf.h:72 __CHIP_TYPE = 0x00（轮询方式）
4第 7.2 节 软定时器 表格「_cnt4ms …… 实际周期 ≈5ms」等 N+1ms 说明这条手册是对的（与 main.c:366-367 一致）。本文只补充一点：主循环一圈本身 ≥4.6ms，与"约 5ms"同量级 → 该任务真实周期的抖动比"5ms"更大main.c:366-367（作者自己的说明）；main.c:399/:402（耗时实测区间）
5第 10.1 节（时钟类对照表，与 11.1 节的纠错条目对应）「main.c vs adc.c：一处说 PCLK1=48MHz、一处说 24MHz → 48MHz」结论手册是对的（RCC_HCLK_DIV1）。但同一处错误在 bsp_pwm.c 的注释里也出现了一次（写"PCLK1 = 24MHz"），手册的纠错表没有收录 bsp_pwm.c 这一处main.c:166 APB1CLKDivider = RCC_HCLK_DIV1；bsp_pwm.c:33、bsp_pwm.c:69-70 的 24MHz 注释
